# Helper API

Omarchy's shell starts the helper and talks to it over its stdin and stdout with [JSON-RPC 2.0](https://www.jsonrpc.org/specification), one JSON object per line. The helper exits when stdin closes or on SIGTERM.

```sh
oma-messenger-service [--data-dir DIR] [--db FILE] [--version]
```

The protocol version is `4`.

## Methods

| Method | Params | Result |
| --- | --- | --- |
| `hello` | | `{protocol, version, unreadTotal, unreadByService, services}`; `unreadByService` is `{whatsapp: N, telegram: N, …}`, omitted entries meaning zero; `services` is `[{id, name}]`, the messaging services available to add an account for |
| `accounts.list` | | `[Account]`, each with an added `attachmentLimit`: the largest file its connector currently accepts to send, in bytes - Telegram's 2 GiB cap, doubled to 4 GiB for a Premium account, or WhatsApp's 2 GiB document cap (see `media.attach`'s own, kind-specific figures) |
| `accounts.add` | `{service, apiId, apiHash, options}` | `Account`. `apiId` and `apiHash` are Telegram's own API keys, kept for compatibility; `options` is the general form, a map of a provider's own setup values (Telegram reads the same two keys from it as `apiId`/`apiHash` strings). Without either, the account uses OmaMessenger's own keys |
| `accounts.remove` | `{accountId}` | `{}`; signs out and deletes the account's session, credentials and messages |
| `accounts.setAlias` | `{accountId, alias}` | `Account`; saves the display name the user chose for the account, such as "Personal WhatsApp", shown instead of its plain name wherever it is identified. An empty `alias` clears it, falling back to the plain name again |
| `auth.submit` | `{accountId, step, value}` | `{}`; answers an `auth.step`: `phone`, `code` or `password` |
| `contacts.list` | `{accountId, query}` | `[Contact]`; a `Contact`'s own `verified` mirrors a `Message`'s own `senderVerified` for its `name` - a real saved contact (always `true` for Telegram's own `contacts.getContacts`) rather than a bare, self-chosen name synced with no saved contact behind it, which is all WhatsApp's own contact list is built from today unless a better, saved or verified business name is already known locally for the same person |
| `contacts.block` | `{conversationId}` | `Conversation`; blocks the contact behind a direct conversation, through the service. Fails with invalid params for a group, or a service that refuses, such as one that offers no block API at all |
| `contacts.unblock` | `{conversationId}` | `Conversation`; the reverse of `contacts.block` |
| `conversations.list` | `{query}` | `[Conversation]`, newest first; `match` holds the newest matching message, and `matchMessageId`/`matchSender` identify it and who sent it, for a caller that wants to open and highlight that exact message rather than just the conversation (the unified command palette's "Messages" section); `matchSenderVerified` mirrors a `Message`'s own `senderVerified` for `matchSender` (see below), since the palette shows it as a search result's own label. `blocked` is set once the contact behind a direct conversation has been blocked (see `contacts.block`); always `false` for a group. `notificationSound` is `"custom"` once a conversation has its own notification sound (see `conversations.setNotificationSound`), `""` (omitted) otherwise |
| `conversations.open` | `{accountId, contactId}` | `Conversation`, created if needed |
| `conversations.markRead` | `{conversationId}` | `{}`; also the command palette's "Mark as read" |
| `conversations.markUnread` | `{conversationId}` | `Conversation`; the command palette's "Mark as unread". Local to this computer only, never reported to the service: it gives the conversation an unread count of 1, and does nothing when it already has an unread count of its own, so this can never lower a real count the service reported |
| `conversations.setMuted` | `{conversationId, muted}` | `Conversation` |
| `conversations.setNotificationSound` | `{conversationId, path}` | `Conversation`; re-encodes path (any audio format the system ffmpeg decodes - MP3, WAV, Ogg, M4A and FLAC all work) to an uncompressed WAV inside the sandbox, the same way `media.fetch`'s `play` does for a voice note, copies the result into the helper's own sound store, and gives the conversation its own notification sound, overriding whatever its service or the global default setting plays. `notificationSound` on the result (and on every other `Conversation` this conversation appears in) is `"custom"` once set, `""` otherwise; the sound's own bytes never cross the protocol - see `sounds.fetch`. Fails with invalid params for a missing file, or one ffmpeg itself cannot decode as audio at all, naming no detail about the file itself |
| `conversations.resetNotificationSound` | `{conversationId}` | `Conversation`; the command palette's "Reset notification sound": clears a conversation's own sound back to inheriting whichever one applies at the service or global default level, and removes the file `conversations.setNotificationSound` stored for it |
| `conversations.setPinned` | `{conversationId, pinned}` | `Conversation`; `conversations.list` always orders pinned conversations first, then by `pinOrder` (see `conversations.movePin`). Pinning is local and unlimited; a service with its own limit on pinned chats (WhatsApp's own app allows three) fails with invalid params past it, but the local pin still stands. Any other service failure, once the local pin already stands, also fails with invalid params, naming whether it was a pin or an unpin, rather than the generic internal error - except when the service can never verify its own synced copy right now, which succeeds with the local pin standing and an `account.notice` in its place (see that event, below) |
| `conversations.movePin` | `{conversationId, direction}` | `Conversation`; moves a pinned conversation one place up or down (`direction: "up"` \| `"down"`) among the other pinned conversations, swapping places with whichever pinned neighbor is already there. A no-op at either edge of the pinned group. Fails with invalid params for a `direction` other than `"up"`/`"down"`, or not found (`-32001`) for a conversation that is not currently pinned. Local reordering only, never reported to a service: both conversations' new summaries arrive as `conversation.updated` events, this call's own result being the one named in `conversationId` |
| `conversations.setArchived` | `{conversationId, archived}` | `Conversation`; `conversations.list` still returns archived conversations, the UI hides them by default. Archiving a conversation this account had pinned also unpins it, for a service whose own archiving does the same (WhatsApp; Telegram keeps a separate pinned list per folder and is left alone); unarchiving it again restores that pin, both here and with the service, rather than leaving the chat unpinned for good. The local change always stands even if the service call fails; that failure fails with invalid params, naming whether it was an archive or an unarchive, rather than the generic internal error - except when the service can never verify its own synced copy right now, the same `account.notice` exception `conversations.setPinned` has (see that event, below) |
| `conversations.setHidden` | `{conversationId, hidden}` | `Conversation`; local to this computer only, never reported to the service. `conversations.list` still returns hidden conversations, the UI hides them by default |
| `conversations.setReminder` | `{conversationId, at}` | `Conversation`; snoozes until `at` (Unix milliseconds), or clears the reminder when `at` is `null`. Local to this computer only, never reported to the service. The helper fires it at `at`: a `conversation.updated` event (`reminderAt` now in the past) and a desktop notification, "Reminder: `<title>`" unless notifications are set to "Nothing". The reminder is not cleared automatically once due; `conversations.setReminder` with `at: null` clears it |
| `conversations.members` | `{conversationId}` | `{members}`: `[{id, name, verified}]`, a group's current members, for the composer's @-mention picker; `verified` mirrors a `Message`'s own `senderVerified` for `name` (see below). Empty for a direct chat or a service that does not list members |
| `conversations.reportSpam` | `{conversationId}` | `Conversation`; reports a direct conversation's contact as spam through the service when it offers a report of its own, then blocks the contact and hides the conversation from the standard list, matching what the official apps do. Fails with invalid params for a group. WhatsApp's own API has no spam report, so only the block and hide happen there; a service that fails the report itself fails the whole call rather than blocking anyway |
| `messages.list` | `{conversationId, before, limit}` | `{messages, hasMore, historyUnavailable}`, oldest first; `limit` 1–200, default 50. Past the oldest stored message it fetches older history from the service, which arrives as `message.added` too. `historyUnavailable` (omitted when false) is set when that fetch could not reach the service right now, such as a WhatsApp account whose phone never answered an on-demand request in time; the page already loaded is returned either way |
| `messages.send` | `{conversationId, text, attachment, replyTo, mentions}` | `Message`; status `failed` if the service refused it. `attachment` is optional: `{path, name}` names a file to send, with `text` as its caption (`text` may then be empty); an attachment over the conversation's own account limit is rejected (2 GB by default; see `media.attach`, which already refuses the same file earlier, at attach time). `path` should be the `path` a prior `media.attach` or `media.paste` call returned, not a raw path straight from a file picker (see `media.attach`); `name`, also optional, overrides the attachment's display name for a `path` like that, whose own base name carries an internal id rather than the name the user picked - omitted, the display name falls back to `path`'s own base name, right for a plain disk path from an older UI. `replyTo`, also optional, is the local id of a message in the same conversation this one answers; it works together with `attachment`. `mentions`, also optional, is `[{userId, name, offset, length}]`, the "@name" tokens in `text`: `offset` and `length` are in UTF-16 code units, the same unit a JavaScript string already indexes by |
| `messages.retry` | `{messageId}` | `Message`; only for failed outgoing messages. The helper also retries a failed message on its own - once its account reconnects, and otherwise on a backoff for up to a day - so this is for a retry the user asks for sooner; it always starts that backoff over |
| `messages.react` | `{messageId, emoji}` | `Message`; sets the user's reaction to `emoji`, or clears it when `emoji` is `""`. Fails with invalid params if the service does not support reactions |
| `messages.vote` | `{messageId, optionIds}` | `Message`; casts the user's vote in the message's poll, replacing any previous vote. `optionIds` names `domain.PollOption.ID` values from the poll's own `options`. Fails with invalid params for a message with no poll, a closed poll, or a service that does not support voting |
| `messages.delete` | `{conversationId, messageIds, forEveryone}` | `{}`; deletes messages for everyone, through the service, when `forEveryone` is true, or only for this account otherwise. A failed message that never reached the service is deleted locally with no connector call at all, `forEveryone` ignored, and drops its outgoing attachment, if any. Fails with invalid params if the service refuses, such as "for everyone" on a message that is not yours, or "for me" where only "for everyone" is possible - except when the service can never verify its own synced copy right now (WhatsApp's "for me" patch only), which deletes the message locally regardless, with an `account.notice` in place of a failure (see that event, below). Removal arrives as `message.removed`, the same as a deletion the service reports on its own |
| `messages.edit` | `{conversationId, messageId, text}` | `Message`; changes an outgoing text message's words, updating the store at once and telling the service. Only a message you sent, with no attachment, that has already reached the service (it has a remote id) can be edited. Fails with invalid params for anything else, for an empty `text`, or if the service refuses, such as past its own time limit to edit a message; a refusal reverts the message back to its original text. The service's own later echo of a successful edit arrives as `message.updated`, same as any other |
| `messages.schedule` | `{conversationId, text, sendAt}` | `ScheduledMessage`: `{id, conversationId, text, sendAt, created}`. Queues a text-only message to send at `sendAt` (Unix milliseconds), which must be in the future; fails with invalid params for empty or over-length `text`, or a `sendAt` not in the future. Attachments are not supported in this first version. The helper sends it through the normal send path once `sendAt` comes, even if the helper was not running right at that moment (it sends anything overdue once, on its next start); a failed send is retried automatically, exactly like any other failed send, and arrives as `message.added` followed by the usual `message.updated` status changes, not as another `scheduledMessage.*` event |
| `messages.listScheduled` | `{conversationId}` | `{messages: [ScheduledMessage]}`, soonest due first. `conversationId` is optional: omitted or `""` lists every message queued anywhere, for the "Scheduled messages" command; given, only that conversation's own, for its own pending list |
| `messages.editScheduled` | `{scheduledId, text, sendAt}` | `ScheduledMessage`; changes a queued message's text and send time, validated the same way `messages.schedule` validates a new one. Not found (`-32001`) once it has already been sent or cancelled |
| `messages.cancelScheduled` | `{scheduledId}` | `{}`; removes a queued message before it sends. Not found (`-32001`) once it has already been sent |
| `messages.sendScheduledNow` | `{scheduledId}` | `Message`; sends a queued message right away instead of waiting for `sendAt`, through the normal send path, the same as a message due now. Not found (`-32001`) once it has already been sent or cancelled |
| `media.fetch` | `{messageId, auto, play}` | `{path, playPath, playable, risky, width, height}`: the message's photo, video, file, voice note or audio message. For a message you sent, its own local copy is returned at once; otherwise it is downloaded into the media cache the first time, cached under a name built from the message's own id and an extension chosen from the downloaded bytes themselves (sniffed, from a fixed allow-list; an unrecognised type gets `.bin`) for every kind but a photo or video, which always get `.jpg`/`.mp4` - never from the message's own claimed file name, which a sender fully controls (see `docs/decisions.md`). `path` is always the original: the downloaded bytes for a video, voice note, audio message or file, or - for a photo or sticker only - a display copy decoded and re-encoded from it (`<id>-view.jpg` or `<id>-view.png`, whichever the re-encode actually produced, or a sandboxed still-frame re-encode for a format Go cannot decode at all, such as an animated WebP sticker), built once and reused on every later fetch; this is the one file the UI ever loads into an `Image`, but never what it plays. `width` and `height`, set for a photo or sticker, are that display copy's own real dimensions, confirmed by the helper's own decode of it (see `imagesafe.Reencode` and `app.Commands.displayCopy`): the UI must size its decode of `path` from these, never from the message's own `media.width`/`media.height`, a sender's claim that need not match what the file actually decodes to (see docs/decisions.md). Omitted for every other media kind. `play`, optional and defaulting to `false`, asks the helper to also prepare the in-window play copy for a video (including a "GIF video"), voice note or audio message - never a photo or sticker, which has none - by re-encoding the original with the system's own ffmpeg, run inside a sandbox with no network access (see `docs/decisions.md`); omitted or `false`, the fetch only downloads, as fast as before. `playPath`, set only when `play` was `true` and that transcode actually succeeded, is the one file the UI may ever load into its in-window video or voice player - never `path`, a sender's own bytes. `playable` is `true` exactly when `playPath` is set, kept only so the result's shape still carries a boolean there. A transcode failing, timing out, being unavailable (ffmpeg or bubblewrap missing - see `helper.doctor`), or the message's own claimed duration already being over the profile's cap, is never an error: `playPath` is simply omitted, and the UI falls back to opening `path` externally. `risky`, omitted (`false`) for everyday media, is `true` when the downloaded bytes are active or executable content - a web page, a vector image carrying a script, or anything this helper does not recognise at all - sniffed fresh from `path`'s own bytes every time, never the message's claimed file name or kind; the UI must ask the user to confirm before opening a file this names risky with anything but its own built-in viewers, offering "Save to Downloads" as the safe default, and must never decide this for itself. `auto`, optional and defaulting to `false`, is `true` for a fetch the UI made on its own, with no click from the user - a photo, sticker or voice note shown as a message's row comes into view - which bounds the download to a far smaller size than a deliberate fetch (`false`, including every click, the viewer opening, and a retry of something an automatic fetch already refused) is trusted with; a video never auto-fetches at all (see `ui/components/InlineVideo.qml`), only a click does, and `play` is never combined with `auto`. A download failure answers `-32603` with `data: {reason}`, one of `not-found`, `expired`, `download`, `decrypt`, `too-large`, `cache` or `timeout`, safe to show; the helper also logs the same category to stderr. `expired` is WhatsApp-specific: it means the CDN link had aged out and the primary phone, asked to re-upload it, confirmed the media is gone or never answered. `too-large` means the file's declared or actual size exceeded the limit that applied (the automatic cap, the larger user-requested one, or the media cache's own overall limit) |
| `media.save` | `{messageId}` | `{path}`: the message's media, fetched first if need be, then copied into the user's downloads directory. The saved name's stem is the sender's own claimed file name, sanitized (control and Unicode bidi/format characters stripped, whitespace collapsed, length capped) and shown only, never used to decide how the file is cached or opened, or a fixed fallback stem when sanitizing leaves nothing usable; its extension always comes from the downloaded bytes' own sniffed content type, never the sender's claim, with " (2)", " (3)", … added before it rather than overwriting a file already there. Fails with invalid params if the helper has no downloads directory to save into (no `HOME` when it started), or with the same reasons `media.fetch` can fail |
| `media.copy` | `{messageId}` | `{}`: a message's photo, sticker or video, fetched first if need be - for a video, its own in-window play copy, prepared on demand the same way `media.fetch`'s `play` does - put on the system clipboard through `wl-copy` with a fixed argv and the file given to it on stdin, under its MIME type freshly sniffed from the copied bytes. Only ever copies this helper's own output, never a sender's bytes directly; every other media kind fails with invalid params. Fails with the same reasons `media.fetch` can fail |
| `media.paste` | | `{path, kind, width, height}`: an image copied off the clipboard into the outgoing media area, for the composer to attach to the next message sent; fails with an invalid-input error when the clipboard holds no image |
| `clipboard.readText` | | `{text}`: the clipboard's text/plain offer, read through the helper's own bounded `wl-paste` (size and time capped the same way `media.paste` is, but far smaller); fails with an invalid-input error when the clipboard holds no text. The UI inserts `text` at the focused field's own cursor itself - this never touches Qt's own in-process clipboard reader, which has no size or time limit of its own, so Ctrl+V and Shift+Insert go through this everywhere in the UI instead of a field's own built-in `paste()`: the composer's own fallback once a pasted image is not found (`ComposerController.paste`), and, for every other editable field, `Panel.qml`'s own router dispatching straight to it through `ClipboardPaste.qml` (see `docs/decisions.md`) |
| `media.attach` | `{path, accountId}` | `{path, name, kind, width, height, size, limit}`: a file the user picked from disk, copied into the outgoing media area and, when it looks like a photo, sanitized with imagesafe's own full-size profile, the same check a downloaded or pasted photo already gets, before the composer ever shows anything built from it. `accountId` is the open conversation's account, read to look up its connector's own attachment limit; omitted (an older UI), it falls back to the 2 GB default below. `path` is the new, already-sanitized copy to send through `messages.send`'s `attachment.path`; `name` is the file's own picked name, for `attachment.name`. `kind` is `photo`, `video` or `file`, sniffed from the file's own bytes, never guessed from its name; the composer shows a decoded preview only when it is `photo`, the one kind this has actually sanitized. `width`/`height` are set only for a photo. `size` is the file's own byte count; `limit` is the cap it was checked against - Telegram: 2 GB, or 4 GB for a Premium account; WhatsApp: 16 MB for a photo or video, 2 GB for a file; 2 GB for any other service or one not yet connected - so the UI can show both without a second round trip. A file over `limit` fails outright with an invalid-input error naming the limit, the same as one that reaches `messages.send` straight from disk always has; a missing or unreadable file, or an oversized or unsafe photo, fails the same way |
| `files.pick` | `{purpose, title}` | `{path}`, omitted when the user cancelled the dialog (never an error): opens a file-choosing dialog through `xdg-desktop-portal`'s own `FileChooser`, over D-Bus, out of this process entirely - never the native, in-process GTK dialog that once crashed the whole Omarchy shell (see `docs/decisions.md`). `purpose` is `"attach"` (images, video and any other file, for the composer) or `"sound"` (audio files, for a conversation's notification sound), deciding the filters offered; `title` is shown in the dialog. Fails with an internal error carrying `data: {reason: "unavailable"}` when the portal cannot be reached or shown at all, the UI's own cue to fall back to a different, non-native file picker of its own rather than retrying the portal or falling back to the native one |
| `links.open` | `{url}` | `{}`; opens url with the user's own default handler (typically a browser) through `xdg-desktop-portal`'s own `OpenURI`, over D-Bus, instead of starting `xdg-open` with url as one of its own command-line arguments, which any other local user could read through `/proc` (see `docs/decisions.md`). `url` is re-checked against the same scheme allow-list the UI already applies to a message's own link before this is ever called. Fails with invalid params for a disallowed scheme, or with an internal error carrying `data: {reason: "unavailable"}` when the portal cannot be reached or the open itself fails - the UI's own cue to show a fixed message ("Couldn't open the link: no desktop portal") rather than falling back to `xdg-open` |
| `files.open` | `{path}` | `{}`; opens the local file at path with the user's own default handler for its kind, through the portal the same way `links.open` does: a message's own already-downloaded photo, video or file, or a file the user owns outside any message, such as this plugin's own `keys.conf`. path must resolve, once its own symlinks (if any) are followed, inside the media cache, the outgoing attachment area or the downloads directory, or be exactly the key-bindings file; fails with invalid params for an empty path or one outside every one of those, and with an internal error carrying `data: {reason: "unavailable"}` when the portal cannot be reached or the open itself fails |
| `ui.setFocus` | `{conversationId, windowActive}` | `{}` |
| `sounds.fetch` | `{conversationId}` or `{service, path}` | `{path}`, omitted when nothing playable was found: the one method the UI calls to actually play a notification sound, once its own precedence between a conversation's, a service's and the global default sound has already picked a winner (see `ui/lib/NotificationSound.js`). `{conversationId}` resolves that conversation's own sound, stored by `conversations.setNotificationSound`; `{service, path}` ("whatsapp", "telegram" or "default", with `path` the matching manifest setting's raw value) validates and copies that file the same way, on the UI's behalf, since a manifest setting is never pre-validated the way a conversation's own sound is. Either way, the result's `path` is a local WAV file this helper's own sandboxed transcode already produced; an invalid or missing file resolves to no `path` at all, never an error, since a notification sound is never worth failing a request over |
| `ui.getWindowOpen` | | `{open}`: whether the window was last left open rather than deliberately closed, `false` for a fresh install. The UI reopens it once on the next start when this is `true` and the "Reopen after restart" setting is on (see `ui.setWindowOpen` and `docs/decisions.md`) |
| `ui.setWindowOpen` | `{open}` | `{}`; records whether the window is currently open. The UI calls this with `true` whenever it shows the window, and with `false` only when the user deliberately closes it - never when a shell restart or plugin reload tears the window down without asking first, which is exactly the case this exists to survive |
| `whatsNew.getSeenVersion` | | `{version}`: the version the user last saw the in-app "What's new" list for, `""` for a fresh install |
| `whatsNew.setSeenVersion` | `{version}` | `{}`; records version as seen, so the UI's one-time update hint does not show again for it |
| `settings.apply` | `{notifications, notificationPreview, notificationDetail, readReceipts, spellCheck, spellLanguage}` | `{}`; `notificationDetail` is `nameAndMessage`, `nameOnly` or `none`, and takes over from the older `notificationPreview` boolean when sent (`true` behaves as `nameAndMessage`, `false` as `nameOnly`). `readReceipts` is incognito mode when `false`: `conversations.markRead` still clears the local unread count, but `MarkRead` never reaches the connector, so the service, and any other device signed into the same account, keep showing the chat unread. `spellCheck` turns the composer's English spell check on or off (on by default); `spellLanguage` picks its dictionary: `auto` (from the locale environment, the default), `en_GB` or `en_US` |
| `helper.doctor` | | `{checks: [{name, ok, detail}]}`: the helper's own health report (version, data permissions, the database, the media cache, the outgoing media area, each account's connection, the notification service's reachability, whether ffmpeg and bubblewrap were both found at startup for in-window playback, and any recent error categories). Every field is safe to show: states and categories, never a path, a name or a token, except for a plain count where it helps, such as how many failed messages are waiting in an over-limit outgoing media area |
| `spell.check` | `{text}` | `{misspellings: [{start, end, word}]}`: the misspelled words in text, skipping URLs, `@mentions`, email addresses, numbers and `` `code spans` ``. `start` and `end` are UTF-16 code units, the same convention a mention's offset uses. Always `{misspellings: []}` while spell check is off. `text` is checked only up to `domain.MaxTextLength` (4096 characters), the same cap `messages.send` enforces on outgoing text; anything past it is never scanned. The result never carries more than 200 entries, however many a huge pasted string's own unrecognised words would otherwise produce |
| `spell.suggest` | `{word}` | `{suggestions: [string]}`: up to five replacement words for word, best match first. `word` longer than 64 Unicode code points is never a dictionary word, so the result is always `{suggestions: []}` rather than reaching the dictionary's own suggester |
| `spell.addWord` | `{word}` | `{}`; adds word to the user's personal dictionary, so it is never flagged again. Fails with invalid params for an empty word, or one longer than 64 Unicode code points |
| `fake.inject` | `{conversationId}` | `Message`; only in the test build |

## Events

Events are JSON-RPC notifications: `{"jsonrpc":"2.0","method":"<event>","params":<data>}`.

| Event | Data |
| --- | --- |
| `account.updated` | `Account` with the same added `attachmentLimit` as `accounts.list` (see above), so a reconnect's own update never leaves the composer's hint stale; `status` is `connecting`, `connected`, `needs-auth`, `error` or `offline` |
| `account.removed` | `{accountId}` |
| `auth.step` | `{accountId, kind, qr, hint, passwordHint}`: `kind` is `qr` (a base64 PNG to scan; reply with a `phone` to sign in by code instead), `code`, `password` or `linkcode` (WhatsApp's 8-character code, in `hint`, to type on the phone after submitting a `phone` step; no answer needed, it waits for the phone to confirm it). `passwordHint` is set only for a Telegram `password` step whose account has a two-step verification hint to show; omitted otherwise |
| `conversation.updated` | `Conversation` |
| `message.added` | `Message` |
| `message.updated` | `Message`; also sent when the service reports a message edited, or its reactions changed |
| `message.removed` | `{conversationId, messageId}`; sent when the service reports a message deleted |
| `unread.changed` | `{total, byService}`; `byService` is `{whatsapp: N, telegram: N, …}`, a service omitted meaning zero |
| `typing` | `{conversationId, name, verified, active}`; `name` is set only in a group (a direct chat's single header has no room for one); `verified` mirrors a `Message`'s own `senderVerified` for it |
| `notification.clicked` | `{conversationId}`: the user clicked a desktop notification; the UI opens that conversation |
| `scheduledMessage.added` | `ScheduledMessage`; a message was queued, through `messages.schedule` |
| `scheduledMessage.updated` | `ScheduledMessage`; a queued message's text or send time changed, through `messages.editScheduled` |
| `scheduledMessage.removed` | `{conversationId, scheduledId}`; a queued message is no longer pending - cancelled, sent now, or just claimed because its own time came due. The send itself, if any, is reported separately through `message.added` and `message.updated`, not folded into this event |
| `notification.sound` | `{conversationId, service, hasCustomSound}`: sent exactly when a desktop notification is also shown for an arriving message (so never for a muted, missed or already-read one), carrying no sender name, text or file path. The UI decides from this, and its own settings, whether and what to play (see `ui/lib/NotificationSound.js`), then calls `sounds.fetch` for the actual file |
| `account.notice` | `{accountId, message}`: a safe, one-time heads-up about something the account's service cannot do right now - never an error, so the UI shows it in the toast (see `ui/components/Toast.qml`), not the error banner. Sent once per account per helper run, the first time `conversations.setPinned`, `conversations.setArchived` or `messages.delete` finds WhatsApp's own app-state verification permanently failing for that account (see `docs/decisions.md`); the local change stands regardless |

A `Message` may carry `media`: `{kind, …}` where `kind` is `link` (with `url`, restricted to the `http`, `https`, `mailto` and `tg` schemes and omitted otherwise, `siteName`, `title`, `description`), `photo`, `video`, `file`, `voice` (a voice note: WhatsApp's push-to-talk audio, Telegram's voice message), `audio` (an ordinary audio message: WhatsApp's AudioMessage without its PTT flag, Telegram's audio document without its voice flag - played through the same in-window player a `voice` note gets, shown with its own `fileName` and `duration` instead of a voice note's fixed label), `sticker` or `poll`. `thumb` is a small base64 preview sent with the message, decoded and re-encoded by the helper as JPEG, or PNG when it carries any real transparency (a sticker's own cut-out shape, typically, though never guaranteed by its kind alone) - sniff its own leading bytes to tell which, never assume one from the message's kind (see `docs/decisions.md`). `thumbWidth` and `thumbHeight`, set whenever `thumb` is, are that thumbnail's own real dimensions, confirmed by the helper's own parse of it, re-checked and resent on every read regardless of how old the row is (see `docs/decisions.md`): the UI must size its decode of `thumb` from these, never from `width`/`height` below, which describe a full file that may not be downloaded yet and, either way, are only the sender's own claim. `duration` (seconds) is always set on a `voice`, `audio` or `video` media. `animated` is `true` only for a `video` the sending service itself marks as a silent, looping "GIF" (WhatsApp's `gifPlayback`, Telegram's animated document attribute), omitted otherwise; the UI autoplays it muted and looping instead of waiting for a click. A `sticker` carries `emoji`, its associated emoji, shown when there is neither a `thumb` nor a downloaded image to draw: a Lottie or video sticker this UI never tries to decode, so `fileName` is left unset and `media.fetch` has nothing to download. A `poll` carries `poll`: `{question, options, multipleChoice, quiz, closed, totalVoters}`, where `options` is `[{id, text, votes, chosen, correct}]`; `chosen` is the signed-in user's own pick, `correct` is set only for a quiz and only once the user has voted or the poll closed, and there is nothing to `media.fetch`. `edited` is `true` once the service reports the message changed since it was first sent. A `Message` may also carry `replyTo`: `{remoteId, senderId, senderName, senderVerified, text}`, the message it answers, with `senderId`, `senderName`, `senderVerified` and `text` (a short excerpt) filled in once the quoted message is known locally, resolved against a message stored in the same conversation (see `docs/decisions.md`); `senderId` is the UI's own concern only incidentally - the helper uses it to scope a later sender rename to the quote that actually names them. `reactions` is `[{emoji, count, mine}]`, omitted when the message has none; a custom-emoji reaction Telegram sends is left out rather than shown as a misleading placeholder. `mentions` is `[{userId, name, offset, length}]`, omitted when the message mentions no one; `mentionsMe` is `true` when one of them names the signed-in account, so the UI can highlight the message. `formatting` is `[{kind, start, end, url}]`, omitted when the message carries no rich-text formatting: `kind` is `link` (with `url`, restricted to the `http`, `https`, `mailto` and `tg` schemes), `bold`, `italic`, `underline`, `strike`, `code`, `pre` or `spoiler`; `start` and `end` are UTF-16 code units, the same convention a mention's `offset`/`length` uses. Set only by a connector (Telegram's own formatting entities today; WhatsApp's `*bold*`-style markers are not yet mapped), never by the composer. A failed outgoing message may carry `retryAt` (Unix milliseconds): the helper's own next automatic retry attempt, while one is scheduled; omitted once automatic retries have stopped (the failure was permanent, or they have run for as long as they will), leaving it for `messages.retry`. A received message's own `text` is capped at 64 KiB: a sender fully controls it, and the helper cuts anything longer on a valid UTF-8 boundary and appends a fixed `"[message truncated]"` notice, rather than storing or forwarding it unbounded (see `domain.MaxIncomingTextLength` and `docs/decisions.md`); outgoing text sent through `messages.send` keeps its own, much smaller limit (4096 characters).

A `Message`'s own `senderVerified` (omitted meaning `false`), and a `Conversation`'s `titleVerified` (omitted meaning `false`), report whether `senderName` or `title` is a saved contact's name, a service's own verified business name, a group's own name, or this account's own identity (an outgoing message's `senderName` is always `"You"`, always verified) - never a bare, self-chosen name such as a WhatsApp push name or a Telegram profile name with no contact or verification behind it. A stranger can set their own push name to a saved contact's name, such as `"Mum"`, or to `"You"` itself; the UI must mark an unverified `senderName` or `title` (and a reply quote's own `senderVerified`) with a leading `"~"`, the way the official WhatsApp app marks a self-chosen name, rather than show it exactly as it would show a name the user actually saved. The reserved `"You"` label is never applied by comparing a name's text - only a message's `outgoing` flag (or, server-side, the sender's own account id) ever means a message is the user's own, so a self-chosen name of `"You"` on an incoming message still renders marked, as `"~You"`, never as the unmarked label (see `docs/decisions.md`). A `Conversation`'s `phone` (omitted meaning none) is a direct chat's other person's own phone number, formatted `"+<digits>"`, when the service gives one - WhatsApp always does for a chat addressed by a real phone number; Telegram only when that person has chosen to share theirs, which most do not. The UI shows this beside an unverified `title`, the way the official WhatsApp app shows a stranger's own number instead of trusting their self-chosen name; always omitted for a group or the self-chat.

## Errors

| Code | Meaning |
| --- | --- |
| `-32602` | Invalid params or input. The message says what to fix and is safe to show. |
| `-32601` | Unknown method, for example `fake.inject` outside the test build. |
| `-32001` | The account, contact, conversation or message does not exist. |
| `-32603` | Internal error. Details stay in the helper. |

The shapes of `Account`, `Contact`, `Conversation` and `Message` are the JSON fields in [backend/internal/domain/domain.go](../backend/internal/domain/domain.go).

Adding or changing a method updates `server/methods.go`, its test and this file in the same change. Bump `server.Protocol` when an older UI would break; never break an existing method's params or result shape, add an optional field or a new method instead.
