# Decisions

Design choices that are not obvious from the code, and why they were made. Read the relevant entry before reversing one; if you do reverse it, update the entry.

## JSON-RPC over the helper's stdin and stdout

The UI and helper talk JSON-RPC 2.0, one object per line, over the helper's stdin and stdout. The alternative was a Unix socket.

- Quickshell's `Process` gives the UI the helper's stdio for free, and Omarchy's shell already owns the process. With stdio there is no socket file to place, protect or clean up, no address to discover, and no other local process can connect.
- A local pipe is as fast as a local socket. Traffic is a few messages a second at human pace, so neither would be the bottleneck.
- The helper lives exactly as long as the UI's process handle: when the shell stops it, stdin closes and the helper exits.

## sourcegraph/jsonrpc2 instead of our own framing

The helper uses `github.com/sourcegraph/jsonrpc2` rather than hand-written line framing and dispatch. A maintained library handles request ids, concurrent replies and notifications, and the UI speaks a documented standard.

Trade-off: a line that is not valid JSON closes the connection. The UI only sends `JSON.stringify` output, and the UI's service restarts the helper if it exits.

## A failed send is a message, not an error

`messages.send` returns the stored message with status `failed` when the service refuses it, instead of an error. The UI already shows failed messages with a retry action, so an error would report the same thing twice.

## The app layer uses the concrete store

`app` takes `*store.Store` rather than an interface. There is one store, and tests use a real SQLite database in a temporary directory, so an interface would only mirror its methods. Interfaces are used where there are real alternatives: connectors, desktop notifications and the UI connection.

## Real time in code, synctest in tests

There is no clock interface. Code uses the `time` package, and tests of timing (connector restarts, the fake connectors' delays) run inside `testing/synctest`, where time advances instantly and deterministically.

## Release binaries, installed automatically on first open

Helper binaries are published on GitHub Releases with `SHA256SUMS` and build provenance, never committed. `helper-version` names the release, and `scripts/install-helper.sh` downloads and verifies it.

`omarchy plugin add` only clones the repository; by Omarchy's design a plugin has no install hook to run afterwards. Asking the user to then run a script or press a separate "Install helper" button made OmaMessenger a two-step install when every other plugin is one — Omarchy's own Spotify plugin resolves the same gap the same way. So the window now runs the installer itself, the first time it opens and finds the helper missing or pinned to a different version than `helper-version` (a plugin update changes that file, and the launcher looks for a binary named after the new version, so it is "missing" again until the next open installs it). It shows a quiet "Installing the helper…" state and starts the helper on success. A failed install (offline, a bad checksum, no release yet) shows the error with a Retry button, the only remaining manual path; it does not retry on its own on the next open, and it never touches a working helper already in place, since the installer verifies into a version-named temporary file and only `mv`s it over the version-named destination after that check passes.

Verification — a checksum committed in this repository, and the binary's own reported version — stays mandatory either way. Loading the plugin itself still never downloads anything: the trigger is opening the window, never the shell starting. A local `make build` in `bin/dev/` still takes precedence, for development.

## The reviewed commit pins the helper binary, not the release's own SHA256SUMS

The installer used to check a downloaded binary only against the `SHA256SUMS` file downloaded from the same GitHub release, both attacker-controlled together: anyone able to replace a release's assets could swap the binary and its checksum list in the same move, and nothing in the repository the marketplace reviews said which bytes should actually run. `helper-checksums`, committed at the repository root, fixes that: it holds the SHA-256 of the one version's binaries named in `helper-version`, for both architectures, and `scripts/install-helper.sh` refuses a download that does not match the entry committed for the pinned version, before it ever looks at the release's own `SHA256SUMS` (still fetched and checked too, as a cheap sanity check, but never load-bearing on its own). The commit a reviewer or the marketplace verifies now pins exactly which bytes `install-helper.sh` will accept; an attacker who can only replace release assets, not rewrite this repository's git history, can no longer make a tampered binary verify.

This is why the pin lands as a follow-up pull request rather than in the release commit itself. `release.yml`'s `pin-checksums` job can only compute the real hashes after the `release` job has built and uploaded the binaries, so the release-please commit that bumps `helper-version` necessarily lands with `helper-checksums` still pointing at the *previous* version — there is nothing else it could point at yet. `install-helper.sh` treats a committed file with no entry for the pinned version as a hard refusal, never a fallback to the release's own SHA256SUMS, so that gap is a brief "not installable from this exact commit yet", not a security hole: `make marketplace-update` enforces the same thing from the other side, refusing to request a marketplace listing for a HEAD whose `helper-checksums` has not caught up with the latest release. The job opens a pull request instead of pushing straight to main so the pin is an ordinary reviewed diff, like any other change; GitHub never lets a token-authored pull request trigger a check run on itself, so that pull request starts with no CI and the maintainer re-runs or approves it by hand before merging (see the README's release section).

`release-please`'s `extra-files` bumps `helper-version`, `manifest.json` and the compiled-in version on every release, but deliberately never touches `helper-checksums`: a generic version-string bump would just relabel the previous version's (now wrong) hashes as the new version's, which is worse than refusing outright.

## No vendor directory

Go dependencies come from the module cache, pinned by `go.sum`. Committing `vendor/` added about 1,800 files to every review for little benefit.

## Existing tools before custom ones

Lint and coverage rules are configuration for golangci-lint (`.golangci.yml`) and go-test-coverage (`.testcoverage.yml`). The only custom check is `tools/nologcontent`, which keeps message content out of logs, because no existing tool knows which values are private.

## No compositor tests

Automated tests do not start Hyprland or Docker. They were slow and caught little that unit, offscreen QML and helper tests did not. Visual and window-manager behaviour is checked by hand in the installed plugin.

## A typed adapter for Omarchy's theme tokens

Omarchy declares nested token groups (`Style.font`, `Color.popups`, …) as plain `QtObject` properties, so Qt 6 qmllint reports every use as a missing property. `ui/theme/Theme.qml` re-exports them with types, which keeps lint at zero warnings and still catches typos. It is the only file allowed to suppress that warning.

Qt 6.12 added a global QML value type also named `Color`, which shadows an unqualified `Color` identifier wherever it is in scope: `import qs.Commons` followed by `Color.foreground` then silently resolves to the new global type instead of Omarchy's singleton, and every property read comes back `undefined` ("Cannot read property 'foreground' of undefined"), confirmed by running `make build test-qml` against current Arch packages (Qt 6.12.0, quickshell 0.3.2) in a throwaway container. Qualifying the import fixes it because the lookup is no longer an unqualified identifier: `ui/theme/Theme.qml` now writes `import qs.Commons as Commons` and reads `Commons.Color.*`, which resolves to the singleton on both Qt 6.11 and 6.12. Every other file in `ui/` now reads colours from `Theme` (`Theme.foreground`, `Theme.accent`, `Theme.muted`, `Theme.urgent`, `Theme.background`, plus the existing nested groups) and never names `Color` directly; `tests/unit/no-bare-color.test.cjs` scans `ui/` and fails the build on a bare `Color.` outside `Theme.qml`, the same way `textformat-coverage.test.cjs` guards `textFormat`.

This does not fix Omarchy's own `qs.Ui` controls (`Button`, `PanelToolTip`, `PanelActionButton`, …): they still write unqualified `Color.*` in `/usr/share/omarchy/shell`, which this plugin never edits, so they still throw under Qt 6.12 until Omarchy makes the same change upstream. CI's `qml` job keeps pinning Qt 6.11.2 and quickshell 0.3.1 as the required gate; a separate `qml-next` workflow runs the same offscreen tests against unpinned current packages, weekly and on demand rather than on every push, so a new Qt or Omarchy release's own breakage (or a fix) shows up without ever marking a build of this repository as failed over code this plugin cannot change.

## Fake accounts only in test builds

The scripted fake connectors that tests run against are compiled in only with the `fake` build tag (`make build-fake`). Release builds cannot show seeded data, so it can never mix with real messages, and the product has no demo mode to explain.

## Providers behind one interface

Adding an account used to mean `backend/accounts.go` and `app.AddAccount` both knowing Telegram's rules: its credential shape, its app keys, its id prefix. `connector.Provider` moves all of that behind one interface (`Service`, `Name`, `Prepare`, `Connect`, `Forget`) that each service's own package implements. The registry becomes a map of providers, keyed by service id, and `app.AddAccount` only maps a provider's `ErrInvalidSetup` or an unknown service to invalid input; it no longer validates API keys itself.

Prepare takes a plain `map[string]string` rather than a typed options struct, because each service's setup is different (Telegram's API id and hash today, something else tomorrow) and the protocol already carries them as JSON strings. The cost is that a provider must parse its own options and return `ErrInvalidSetup` with a safe message when they are wrong; that cost sits in the one package that knows what valid means for that service, which is the same trade `Provider` makes everywhere else.

`accounts.add`'s `apiId`/`apiHash` fields stay as they were, merged into `options` by the server before they reach `app.NewAccount`, so no existing UI build and no saved Telegram account's `tg-` id prefix breaks. New accounts get an id prefixed with their service name instead, since the registry no longer special-cases Telegram's.

## Clicking a notification: a direct D-Bus call, not notify-send

Superseded: the original choice ran `notify-send -A default=Open -- title body`, relying on its blocking wait (`--wait` is implied once an action is registered) to learn whether the "default" action was chosen. That put a notification's title, body and conversation id in that process's own argv for as long as it ran — up to `notifyTimeout`, five minutes — readable by any other local user on the machine through `/proc/<pid>/cmdline`. The Omarchy marketplace reviewer flagged this before listing.

`notify.Desktop` now calls `org.freedesktop.Notifications.Notify` directly on the session bus, through `github.com/godbus/dbus/v5` (BSD-2-Clause). A notification's title, body and conversation id travel only as that D-Bus call's own argument values, never a command line, so no other local user can read them. The freedesktop "default" action and its meaning to Omarchy's own notification daemon (`/usr/share/omarchy/shell/plugins/notifications/Service.qml`, `invokePopupDefault`) are unchanged; `notify.Desktop` matches the daemon's `ActionInvoked` and `NotificationClosed` signals back to the right notification by the id `Notify` returns, instead of by watching one process's stdout, and still bounds the wait with `notifyTimeout` so a notification that is somehow never closed cannot leak the goroutine. The doctor report's "notify-send availability" check became "is a notification service reachable on the session bus" (`notify.ServiceReachable`, a plain `NameHasOwner` query — states only, never content).

## Sending photos and files

`domain.Media` gained a `Path` field, tagged `json:"-"`, rather than a separate type the server and connectors pass alongside a message. A dedicated field (as the brief suggested as an alternative) would mean threading a second value through `Commands.Send`, `Retry` and every `Dispatcher`, when the local file is really one more thing media about an outgoing message; `json:"-"` keeps it out of the wire protocol (the UI already knows the path it offered; a remote message has none) without adding a parameter everywhere Media already travels.

The outgoing media area (`cache.Outgoing`) names a stored file by the message's id and its original file name (`<id>-<name>`), set before the message is first stored by generating the id in `app` rather than letting the store assign one. `domain.Media.Path` cannot survive a reload from the store (it is deliberately excluded from the JSON column), so `Retry`, which re-reads the message from the store, recomputes the same path from the id and file name it does keep, instead of needing Path to persist.

A captionless attachment reuses the existing placeholder convention for media (`domain.MediaPlaceholder`, the same `"[Photo]"`/`"[Video]"`/`"[File]"` labels a connector already gives incoming media with no caption) rather than allowing an empty stored message. The UI already hides a caption that exactly matches its media's label, so this needed no UI change; the Telegram connector strips the placeholder back to an empty caption before sending, since it is a local display convention, not real text to deliver.

The file chooser is `QtQuick.Dialogs.FileDialog`, used directly from the composer. The plugin's manifest only offers `service`, `panel` and `bar` entry points, not a new Omarchy overlay like `image-picker` (which is also scoped to one fixed directory of images, not an arbitrary file), and `xdg-desktop-portal` is already running on the test machine with a Hyprland and a GTK backend registered; loading `FileDialog` under the offscreen platform showed Qt routing its `open()` straight at that portal (it only failed here on the portal's own sandbox permission check, not on anything Quickshell-specific). `FileDialog` needed no new helper method, so this is the simpler of the two options the brief allowed for.

Pasting an image goes through a new `media.paste` method instead of teaching the UI to read the clipboard, because Qt's QML has no cross-process way to read Wayland clipboard data (only `wl-paste`, a separate process, does); shelling out to it from the helper keeps that logic in one place rather than teaching the UI a second way to reach the clipboard. The composer always intercepts Ctrl+V while composing and asks the helper first; when the clipboard has no image, the composer is told to fall back to a plain native paste, rather than the key router trying to guess the clipboard's contents before deciding whether to intercept the key at all.

`PhotoView`'s "fall back to the blurred preview, or a quiet message when there isn't one" rule only ever triggered off `Image.onStatusChanged` reporting an error, which needs a non-empty `source` to begin with. A photo with neither a thumbnail (common for older or history-synced media) nor yet a successful download has an empty `source` (`""`), so that `Image` never attempts to load anything and never reports an error: the "unavailable" message never showed, leaving a plain empty box forever once the one silent, un-reported auto-fetch attempt (`ConversationController.fetchMedia`) had failed. The fix is a `mediaFailed` flag on the timeline row (`Timeline.row`, `MessageTimeline.setMediaFailed`), set whenever `downloadMedia`'s request errors regardless of whether the user asked for it or a photo was fetching itself quietly, and read by `PhotoView.failed`; `_unavailable` now also triggers off it rather than only off `Image`'s own load failure, so a thumbnail-less photo whose fetch is known to have failed shows "Photo unavailable" instead of staying blank. A photo that does have a thumbnail still falls back to it on the same failure, unchanged.

## Reactions: a Sink method of their own, one reaction per person, custom emoji skipped

Telegram reports a reaction change two ways: a full `UpdateEditMessage`, which carries the message's new text, media and reactions together, and `UpdateMessageReactions`, which carries only the peer, message id and the new reaction counts. The first already fits `Sink.Edited`, since `EditMessage` was going to need a `reactions` argument anyway. The second does not: `Edited`'s contract replaces a message's text and media unconditionally, so feeding it empty values from a reactions-only update would blank out a message's real content. Fetching the full message first to avoid that would cost a network round trip for every reaction click, just to reuse one method. `Sink` already accepts this kind of growth (`Organized` was added the same way for pin and archive sync), so a second method, `Reacted`, carries just the reaction chips, and the store gained `SetReactions` to match: it touches only the `reactions` column.

The UI sends one emoji per `messages.react` call, not a set, and `Reaction` has no way to say "pick several". Telegram's API allows more, but `messages.sendReaction` takes whatever list is given, so sending a single reaction already replaces any previous one from the same person; a second reaction would need its own chip, its own click target and its own place in the picker for a case most chat UIs do not offer either. `Reactions.emojiToSend` (`ui/lib/Reactions.js`) encodes the one-reaction choice: clicking a chip that is already the user's own clears it, and any other pick replaces it.

A custom emoji reaction (`tg.ReactionCustomEmoji`, a sticker rather than a character) is left out of `reactions` entirely rather than shown as a generic placeholder. Telegram's own clients render the actual sticker, which this UI has no way to draw; a placeholder chip would look like a real reaction with the wrong picture, which is worse than one chip fewer.

## WhatsApp's session database uses the same pure-Go SQLite driver as the message store

whatsmeow's `sqlstore.Container` normally opens its own `*sql.DB` by calling `sql.Open` with a dialect string that doubles as the database/sql driver name, which is how its own examples register `mattn/go-sqlite3` (cgo) or `sqlite3-fk-wal`. The helper is built with `CGO_ENABLED=0`, so that path is out. Reading `go.mau.fi/util/dbutil`'s source showed the fix needs no library change: `ParseDialect` only checks that the string has a `sqlite` prefix to pick its SQL quirks, and `sqlstore.NewWithDB` takes an already-open `*sql.DB` and that same string separately, never calling `sql.Open` itself. So the connector opens its own connection exactly as `store.Open` does, with `modernc.org/sqlite`'s pure-Go driver registered under the name `"sqlite"`, and hands both the `*sql.DB` and the string `"sqlite"` to `sqlstore.NewWithDB`; dbutil accepts it as a `sqlite` dialect and generates the right SQL, with no cgo anywhere in the build.

## WhatsApp pairing wraps whatsmeow's client behind a small `device` interface

Unlike gotd/td, which already exposes its lowest-level RPC transport as the `tg.Invoker` interface Telegram's own tests fake, `*whatsmeow.Client` has no such seam: `Connect`, `GetQRChannel`, `PairPhone` and the rest are concrete methods with no public way to substitute a fake network underneath them. `backend/internal/connector/whatsapp/device.go` defines `device`, an interface over exactly the whatsmeow calls the connector and its pairing sequence need (connect, disconnect, close the session database, check whether it is already paired, log out, start a pairing attempt and watch its QR codes, pair by phone, and watch for connected/disconnected/stopped status) so `Connector.Run`, `pair` and their tests drive a hand-written fake instead of ever reaching WhatsApp's servers; `waDevice` is the one production implementation, adapting a real client to it. This is the same shape `connector.Connector` itself and Telegram's `authAPI` already use.

QR and phone pairing share the one `device.qrCodes` channel rather than two separate interface methods, because that is how whatsmeow itself works: `GetQRChannel` keeps running and reports the same final "success" or "error" event no matter which way pairing actually finished, so `pair`'s loop just also watches for a phone number answer on the side and calls `pairPhone` when one arrives, instead of juggling two completion signals for one outcome.

## WhatsApp's account removal logs out the connected device, best effort, then deletes the local session

`connector.Provider.Forget(dir, accountID string) error` still carries no context and no live connection, so it only ever deletes local files, exactly as Telegram's `Forget` does. But a WhatsApp connector that is still running when the user removes it has a live connection worth using: `connector.LogoutOnRemove` is a capability interface with one method, `Logout(ctx) error`, that `Manager.Remove` type-asserts on the connector it is about to stop. When the running connector implements it, `Manager.Remove` calls `Logout` with a bounded `context.WithTimeout` before cancelling the connector's own context, since cancelling first would close the connection `Logout` needs; the result is ignored (commented at the call site), because the local session is deleted either way. WhatsApp's `Connector` tracks the `device` its `Run` is currently using in a mutex-guarded field and implements `Logout` by calling the device's `logOut`. This is why the capability is a new optional interface rather than a change to `Forget`'s signature or to `Connector`: `connector.Connector` and `connector.Sink` stay the stable, published boundary, and a connector that cannot log out (or is not running) just does not satisfy it.

Telegram has no such connection to use here and does not implement `LogoutOnRemove`; its account's session lapses from the server's own view once it stops being used, the same as before.

## WhatsApp's media references live in their own database, not whatsmeow's session

A message's photo, video or file carries a `mediaRef` (direct path, media key, file hashes, length and mimetype) that a later wave's `MediaFetcher` will need to download it, since WhatsApp's end-to-end messages have no server-side copy to re-fetch a reference from the way Telegram's do. This connector saves that reference as soon as a message arrives, in its own SQLite database beside the account's whatsmeow session (`<account>-media.db`, mode 0600, like the session itself) rather than as an extra table inside that session's database. whatsmeow's `sqlstore.Container` owns that schema and upgrades it on its own terms; adding a foreign table to it would work today but ties this connector's data to whatever whatsmeow's own migrations do next. `Provider.Forget` deletes this file alongside the session when an account is removed.

## WhatsApp's reaction and naming caches live in memory for the process's lifetime; pinned and archived no longer do

This entry originally also covered a `remote id -> {pinned, archived}` cache seeded from history sync and updated by `events.Pin`/`events.Archive`; that cache, and the bug class it led to, is gone (see "WhatsApp's pinned and archived state reads from whatsmeow's own chat settings store, not a cache of this connector's own" below).

Reaction chips still work the way this entry always described: WhatsApp reports one person's reaction change at a time, never a conversation's full tally, so a `remote id -> {sender -> emoji}` cache is kept and recomputed into the chip list `Sink.Reacted` expects on every change. Group and contact names resolved to fill in a blank title (see below) are cached too, so a group is never asked for its name twice.

Both caches are fields on `Connector`, surviving a reconnect within the same helper process, but starting empty again after the helper itself restarts, same as Telegram's own `remotes`/`sent` caches. A live reaction event arriving before anything has repopulated the cache reports a fresh tally of just itself; a subsequent history sync corrects it. This was accepted rather than built out further because the store's own copy of reactions is the durable one, and a transient, self-correcting gap right after a restart was judged cheaper than giving this connector a way to read state back out of the store it only ever writes to. Pinned and archived could drop their cache entirely instead of just accepting the same gap, because whatsmeow already keeps a durable, always-current copy of its own that this connector can read.

## WhatsApp's unnamed conversations fall back to a resolved or generic name, never to no name at all

`store.EnsureConversation` drops a conversation with no title rather than creating or updating one, since the UI has nowhere to show a nameless chat. History sync does not reliably carry every conversation's display name: a direct chat's name comes from a separate push name list in the same sync blob (processed first, so it is cached before the conversation list needs it), and a group's name is sometimes missing and has to be fetched with `GetGroupInfo`, bounded by a short timeout and cached so a slow or unreachable group is asked for once. When even that resolves to nothing, a group falls back to the literal title "Group" and a direct chat falls back to its phone number (`"+" + the JID's user part`), the way WhatsApp's own clients show an unsaved contact, unless the JID is a hidden id (a LID) rather than a phone number, which gets the neutral label "Unknown contact" instead: its digits are not a phone number, and showing them as one is worse than admitting the name is not known. The account's own self-chat is a third case, titled with the fixed label "Message yourself" rather than resolved at all, since nobody has themselves saved as a contact. The same resolution runs for a live message's chat when it arrives before any sync has reached it.

A JID on WhatsApp's default server is always a phone number, but one addressed by a LID (`@lid`) is a hidden id the server assigns instead, used increasingly often for both chats and group senders. `device.contactName` resolves a LID to its phone JID through whatsmeow's own LID store (`Store.LIDs.GetPNForLID`) and looks the result up in whatsmeow's local contact store (`Store.Contacts.GetContact`), trying the LID itself first since a few contacts are keyed by LID directly. Both are pure local reads already synced to this device by whatsmeow's own app-state processing; neither does network I/O, so resolving a title or a sender's name never blocks on it. `contactDisplayName` picks WhatsApp's own best name for a resolved contact: its saved full name, first name, verified business name, then its push name, in that order, before this connector's own `senderName` falls further back to the message's own push name and finally the generic "WhatsApp user".

Contacts and push names often finish syncing moments after history sync already titled a chat with a fallback: `events.Contact`, `events.PushName` and `events.AppStateSyncComplete` are handled in `contacts.go` to re-title the affected conversation once a better name is known, without needing to re-pair. A `remote id -> {name, rank}` cache (`Connector.names`, rank one of "push name" or "contact", the latter always winning) makes sure this can only ever improve a title, never replace a good one with a worse one, no matter how many times or in what order a conversation gets re-reported; `AppStateSyncComplete` carries no JID of its own, so it rechecks every direct chat this connector has ever reported (`Connector.chatKinds`), each check a local lookup, never a network call. Existing stored messages whose sender was saved as "WhatsApp user" before their contact resolved are not corrected retroactively: only a new report, live or re-synced, gets the better name, matching how `store.refreshConversation` only ever overwrites what the connector sends it next.

History sync also delivers entries for JIDs that are not a conversation with anyone: the status broadcast, old-style broadcast lists, newsletters, and WhatsApp's own "0" system account (`0@s.whatsapp.net`), which would otherwise title as the meaningless "+0". `isSystemJID` recognises these and they are dropped outright, in both history sync and a live message, rather than ever reaching `Sink.Conversation`.

## WhatsApp's own protocol and system notices, and a few content kinds this UI cannot render yet, never become a visible "[Message]"

WhatsApp's wire format carries many message kinds that are not something a person actually sent: besides a reaction, an edit and a revoke, which were already pulled out as their own events, a `ProtocolMessage` covers ephemeral-setting changes, app-state key shares, history-sync notices and a long tail of similar housekeeping, and a poll vote, a pin-in-chat and a keep-in-chat flag are likewise just state changes on an existing message. None of these carry text, a caption or any media, so without a check they fell through to `mediaPlaceholder`'s default case and showed as the content-free, confusing "[Message]", both as a stored message and as a list preview. `isContentless` recognises every one of these kinds; `historyMessage` drops them the same way it already drops a reaction, an edit or a revoke, and the live dispatch in `live.go` skips them before anything is reported at all, so none of them is stored or shown. A real content kind this UI does not render yet keeps its own specific placeholder instead of the generic one: a poll's question (`"[Poll: …]"`), a shared contact's name (`"[Contact: …]"`) or, with neither, the bare `"[Contact]"`/`"[Poll]"` already in use, and location sharing's existing `"[Location]"`.

## WhatsApp's self-chat ("Message yourself") is a real conversation, not an outgoing echo to skip

Every message in the account's chat with itself is, by WhatsApp's own protocol, "from me": there is no one else to have sent it. The live handler's existing rule — only ensure a chat exists for an *incoming* message, since an outgoing one WhatsApp echoes from another of this account's devices carries no reliable name and was never unread — meant the self-chat's conversation was never created from a live message at all, and a heavily used one (a bot's own notes, in this account's case) could end up with no conversation to store its messages in even once history sync had a chance to deliver it. `device.isSelfChat` reports whether a JID is this account's own phone JID or its LID (either may address it), checked ahead of that `IsFromMe` rule in both `handleContent` and `ensureChat`, and ahead of the regular title resolution in history sync's own `resolveConversation`, so the self-chat is always ensured and always titled with the fixed label "Message yourself" rather than whatever its (nonexistent) contact or push name would otherwise resolve to. Its messages still flow through the ordinary "outgoing, from me" path afterwards: reported as history, carrying `SenderName: "You"`, never counted as unread, exactly as any other message this account sent itself from another device already was. Sending to it goes through the ordinary `Send`, unchanged: WhatsApp addresses it like any other chat, and a message this connector sends is deduplicated against WhatsApp's own echo of it the same way every chat's own echoes already are, by the message's remote id.

## WhatsApp's older history on scroll correlates by chat, one request in flight at a time

Superseded: an earlier wave left `connector.HistoryLoader.LoadOlder` unimplemented for WhatsApp (see git history for that entry's original reasoning). whatsmeow's `Client.BuildHistorySyncRequest(lastKnownMessageInfo, count)` builds the on-demand request mautrix-whatsapp uses for the same purpose, sent to the account's own primary device with `SendPeerMessage` (wrapped as `device.requestOlderHistory`), but it is not a request/response call: the phone replies, asynchronously and without a correlating id, with another `events.HistorySync` of type `ON_DEMAND` whenever it gets to it, indistinguishable at the transport level from any other sync. The seam this needed was a way to match that reply back to the specific chat a `LoadOlder` call is waiting on, which is exactly what a chat's remote id already gives: `Connector.onDemandWaiters` (`history_ondemand.go`) is a `map[string]chan int` guarded by the connector's own mutex, one entry per conversation remote id currently waiting. `LoadOlder` registers its wait, sends the request, and blocks on the channel or `onDemandHistoryTimeout` (30s); `registerOnDemandWaiter` refuses a second registration for the same chat outright (`errHistoryRequestInProgress`) rather than letting two requests queue behind one slot, since whatsmeow gives no way to tell two answers for the same chat apart either.

The answer itself needs no special handling: `handleHistorySync` runs every sync, on-demand or not, through the same `syncConversation`/`syncMessage` path that a bootstrap or periodic resync already uses, so an on-demand backfill is stored as ordinary history (`Sink.History`, never counted unread) exactly like any other. The only addition is that `syncConversation` now returns the chat's canonical remote id and how many of its messages it actually reported, so `handleHistorySync`, when the sync's `SyncType` is `ON_DEMAND`, can call `deliverOnDemandHistory` with that count for whichever chat it just finished reporting. A sync for a chat nobody is waiting on is simply not found in the map and dropped, the same as a stray media-retry answer already is (see `retry.go`, whose waiter table this mirrors almost exactly).

The anchor `BuildHistorySyncRequest` needs — the oldest stored message's id, chat, sender and timestamp — is read back from `message_keys` (see `keys.go`), which every message this connector has ever reported, live or history, already has a row in; `historyAnchor` builds the `*types.MessageInfo` from that row. A timeout waiting for the phone (offline, or just slow) is reported as `connector.ErrHistoryUnavailable`, a sentinel distinct from loading zero messages, which means the phone answered and there is genuinely nothing older; `app.Commands.Messages` maps the former to a `historyUnavailable` flag in its result (additive on the `messages.list` JSON shape) rather than an error, since the page already loaded is still good, and the UI (`ConversationView`'s message list footer, which sits at the visual top for its `BottomToTop` layout) shows a quiet note rather than silently acting as though history had actually run out.

## WhatsApp's mute state from the phone is not synced

`events.Mute` is received and intentionally dropped rather than reported anywhere: `connector.Sink` has no method for it, by design. `Sink.Organized` carries pinned and archived because `store.SetOrganized` keeps both in step with the service; the store's `muted` column has no equivalent sync path at all; `store.refreshConversation`, which `EnsureConversation` uses to update an existing conversation, deliberately never touches it, and the only way to set it is the UI's own local `conversations.setMuted` command. Muted is, by this app's existing design, a local preference rather than a synced one, the same as `hidden`. Adding a new `Sink` method just for WhatsApp's mute changes would be a bigger change than this one connector's wave justifies, given `connector.Sink` is meant to stay stable once a real connector ships; if muting from the phone turns out to matter, it is a Sink change to make deliberately, with Telegram's own mute considered at the same time, not a one-off for WhatsApp.

## WhatsApp's reactions and replies need a message's sender, so that is persisted too, in the same database as media references

Reacting to a message or quoting it needs WhatsApp's own key for that message: its chat, its id, and, in a group, who sent it, since a group reaction or quote has to name the right participant. WhatsApp gives none of that back on demand the way Telegram's message ids alone are enough to build a reply or a reaction; it has to be captured from whichever event first reported the message. `backend/internal/connector/whatsapp/keys.go` adds a `message_keys` table (conversation id, message id, sender id, from-me) to the same per-account database `storage.go` already keeps media references in, rather than a third database file: it is written to from the same three places a media reference is (a live message, a synced one, and a message this account just sent), so sharing the file means one database to open, close and eventually delete per account instead of two. `React` and `Send`'s reply-quoting both read it through `targetKey`, which sets a group's `Participant` only when the message was not sent by this account, mirroring whatsmeow's own `BuildMessageKey`; a direct chat never sets it, since its two parties are already identified by the from-me flag alone.

A message from before this connector tracked keys, or one `putMessageKey` failed to save, has no row to find: `React` reports `errUnknownReactionTarget` rather than guessing at a key, and a reply falls back to quoting by stanza id alone, the way every reply worked before this. WhatsApp still threads that reply correctly, since the recipient's own client already holds a copy of the message being quoted; only the richer quote (participant and a snippet of the quoted text) is lost.

## Release binaries are GPL-3.0; this repository's source stays MIT

whatsmeow (MPL-2.0, WhatsApp support) depends on `go.mau.fi/libsignal`, which is GPL-3.0. Linking it statically into the helper binary makes that binary a combined work, which the GPL-3.0 requires to be distributed under its own terms, regardless of what license the rest of the code carries. MPL-2.0 is compatible with this (MPL-licensed files may be combined into a GPL-licensed work); MIT is permissive enough to be relicensed the same way. So this repository's own source stays MIT (`LICENSE`), since nothing stops it being used under those terms directly from the repository, but each release's built binary is distributed under GPL-3.0 (`LICENSE-GPL-3.0`), because that is what the combined work it contains requires. The corresponding source for a given release is simply this public repository at the tag that release was built from.

`THIRD_PARTY_NOTICES`, generated by `make third-party-notices` (`github.com/google/go-licenses/v2`, pinned in the Makefile, run against `./backend`, which is what the release binaries build) lists every third-party component actually linked into the helper and its license in full, and is published in each release next to the binaries. `make license-check` runs the same tool in `check` mode against an allow-list (MIT, BSD-2/3-Clause, Apache-2.0, ISC, MPL-2.0, GPL-3.0) as part of `make check`, so a newly added dependency with a license outside that list fails the build instead of silently shipping. One dependency, `github.com/segmentio/asm` (pulled in by Telegram's `gotd/td`), is excluded from both: its `LICENSE` file reads "MIT No Attribution", a permissive MIT variant go-licenses' classifier does not recognise, so it reports the package as unclassified rather than guessing. It is covered by hand in `scripts/third-party-notices.tmpl` after reading the file directly, which is the one place go-licenses could not do the job itself.

## Signal and Facebook Messenger: evaluated, parked

Signal was considered alongside Telegram and WhatsApp. Every Signal client builds on either `libsignal` itself (AGPL-3.0) or `signal-cli` (a separate Java process); the only route that stays a single Go process, `mautrix-signal`'s `signalmeow`, does so by wrapping `libsignal`'s own Rust library through cgo, which makes the helper AGPL-3.0 (a stronger copyleft than the GPL-3.0 WhatsApp already brings) and adds cgo and a Rust toolchain to the build and CI. Parked until there is real demand for it.

Facebook Messenger and Instagram have no personal-account API; the only library for them, `mautrix-meta`'s `messagix` (pure Go, no cgo), is AGPL-3.0, sign-in means pasting cookies out of a logged-in browser session rather than any sanctioned flow, Meta is known to flag clients that do this, and pin, archive and mute are unsupported. Declined.

## WhatsApp's self-chat always canonicalizes to its phone JID, never its LID

A real account showed two "Message yourself" conversations: one keyed by the account's own phone JID with its real history, and a stray second one keyed by the account's own LID, empty of messages but wrongly retitled with a resolved contact name. Every place this connector turned a JID into a stored or reported remote id (`remoteID`) treated the phone JID and LID forms of the same self-chat as two different conversations, because nothing compared a JID against both before deciding its id. A bot that replies into the self-chat as another linked device (this account's own, same as any multi-device echo) can address either form depending on which of WhatsApp's internal paths delivered it, so the split was real, not synthetic.

`chatID(ctx, dev, jid)` is the fix: it calls `dev.isSelfChat` first, and when true, returns `dev.selfChatID()` (always the phone JID's remote id, since `Store.GetJID()` is reliably set once paired, unlike `Store.GetLID()`) instead of `remoteID(jid)`. Every call site that used to compute a conversation's remote id from a bare JID — `ensureChat`, the live reaction, revoke, edit, typing, receipt, pin and archive handlers, `receipt`'s outgoing-progress matching, and history sync's `syncConversation` — now goes through `chatID` instead. Message keys and media references, which are keyed by conversation remote id plus message id, automatically follow since they are saved under whatever remote id the caller already computed.

`isSelfChat` itself grew a fallback for the same reason `selfChatID` has to exist: `Store.GetLID()` is this device's own cached copy of its LID, which can still be empty for a while after pairing even once the account's LID is long since assigned; this is almost certainly what produced the stray conversation on first pairing, since `ensureChat`/`resolveConversation`'s self-chat check falls through to ordinary contact resolution when it answers false, which is also is why the stray conversation's title came from a resolved contact. `isSelfChat` now also tries whatsmeow's separate, independently-synced LID mapping store (`Store.LIDs.GetPNForLID`), the same local read `contactName` already relies on, before giving up — recognising the account's own LID a run earlier than relying on `Store.GetLID()` alone would.

Existing accounts that already have the stray LID-keyed conversation keep it: there is no store-level merge or migration in this change, since one would need UI and RPC surface of its own and risks merging two conversations incorrectly if guessed wrong. Going forward the stray conversation receives nothing further from this connector (every report now resolves to the phone JID's id instead), and the user can hide it by hand with the existing `conversations.setHidden` command; it is expected to stop mattering once the account is re-paired, or simply be visibly stale as a hidden leftover with its zero messages and its one wrong title, not the account's own leftover messages.

## `events.Receipt` always runs both lanes, and the connector finally listens for `events.UndecryptableMessage`

Two bugs compounded to make an account's own other-device messages (in particular a bot replying into the self-chat) look dropped. First, `live.go`'s `handleReceipt` — meant to mark a whole conversation read when this account reads it from another of its own devices — was written and tested but never wired into `handleEvents`'s switch on `*events.Receipt`; only `receipts.go`'s `receipt` (lane B: delivery and read progress for a message this account sent) ran. Both are safe to run unconditionally on every receipt, since each checks the one field (`IsFromMe`, or rank-zero for a kind it does not track) that is the other lane's job, so `handleEvents` now calls both for every `*events.Receipt`.

Second, and the more likely cause of messages actually vanishing: whatsmeow reports a message it could not decrypt as `events.UndecryptableMessage`, a case this connector's event switch had no branch for at all, so it fell into the same `default` as a genuinely unhandled event and nothing was ever stored or shown — not even a count. whatsmeow's own doc comment on the type says it already asks the sender to retry, and reports an ordinary `events.Message` with the same id if that succeeds. `handleUndecryptable` now reports a placeholder ("Waiting for this message", matching WhatsApp's own wording style) through the ordinary chat-ensuring and sink-reporting path `handleContent` uses, and records the conversation/message id pair in a new `Connector.undecryptable` set. `handleContent` checks that set first: if the incoming id matches a pending placeholder, it reports the real message through `Sink.Edited` instead of `Sink.Incoming`/`Sink.History`, replacing the placeholder in place rather than storing a duplicate. If whatsmeow's retry never succeeds, the placeholder simply stays, which was judged better than hiding the fact that something arrived at all.

## Diagnostics go straight to the stdlib `log` package, not an injected logger

The brief asked for privacy-safe stderr counters for dropped messages, undecryptable messages and unknown content kinds, "at a debug level the helper already supports" — but no such level exists: `main.go` builds one plain `*log.Logger` for `server.New` and nothing else in the helper takes a logger at all, and `connector.Provider.Connect(account, dir)` has no way to carry one to a connector without changing that interface for every provider, including Telegram, for a WhatsApp-only diagnostic. `backend/internal/connector/whatsapp/diagnostics.go` calls the standard library's package-level `log.Printf` directly instead: it already writes to stderr by default, protocol.md already treats stderr as the diagnostics channel regardless of mechanism, and every line it writes carries only a reason string, a count or a proto field name, never a JID, a name or message text, which `tools/nologcontent` still checks mechanically. If a real leveled-logger seam is built for the helper later, these calls move onto it then; a one-off logger parameter threaded through just this package was judged not worth the inconsistency with every other connector having none.

## Every chat WhatsApp's history sync lists is shown

History sync lists the phone's own chats, so each one is created even when none of its synced messages has anything to display: hiding them made real chats, including WhatsApp's own system chat, go missing. Duplicates are prevented by canonicalising the chat id (see chat_aliases), not by filtering, and titles by resolving the best name under that canonical id.

## Group history messages fall back to this connector's own cached name, and a group's member count is always resolved

Two further symptoms of the same gap: a group's message bubbles kept showing the generic "WhatsApp user" after a fresh pairing even though the conversation list's own preview had the sender's real name, and a group titled straight from history sync's own `DisplayName` showed "0 members" forever. Both come from `resolveGroupName` and `message`/`historyMessage` only ever using what the *current* report carries, never what this connector already resolved from somewhere else.

`resolveGroupName` used to return as soon as it had a name from any source, which also returned whatever member count happened to be cached or synced (often 0, since a synced `DisplayName` with no participant list carries none) without ever asking WhatsApp for the real one; it now resolves name and member count independently, through the new `cachedGroupMembers` helper, and asks `dev.groupInfo` whenever either is still unknown, so a named-but-memberless group still gets a real count, while a group with both already known still never makes the call.

Naming a sender was similarly too narrow: `senderDisplayName` tries a resolved contact, then the message's own push name, but a synced group message's `WebMessageInfo` rarely carries that specific sender's push name the way a live `events.Message` does, even though the account-wide push name list from the same sync (`syncPushnames`, which runs first and populates `Connector.names`) already named that same person. `Connector.improvedSenderName` now checks that cache as a last resort, replacing the message's sender name only when it is exactly `genericSenderName` ("WhatsApp user"), so a message that already resolved a real name is left alone; it is applied after `message`, `edit` and `historyMessage` return, in `handleContent`, `handleEdit`, `handleUndecryptable` and `syncMessage`, rather than threading `Connector`'s own cache into those otherwise-pure normalizers.

## A few more WhatsApp content kinds get their own placeholder or are dropped as housekeeping, found by reading whatsmeow's proto schema

Auditing every field of `waE2E.Message` against what `isContentless`, `messageText` and `sharedContentPlaceholder` already recognised (see the new `unknownContentKind` diagnostic, which reports exactly this gap from a live account without guessing) turned up two kinds of gap. A shared group invite (`GroupInviteMessage`) and a shared sticker pack (`StickerPackMessage`) are real content a person sent, so they get their own placeholders, `"[Group invite]"` and `"[Sticker pack]"`, the same way a shared contact or location already does. WhatsApp has also shipped three more poll-creation versions since V3: V5 and V6 carry a `PollCreationMessage` field directly, like every earlier version, and are just added to `pollCreation`'s switch; V4 is different, wrapping its content in the same forward-compatible `FutureProofMessage` envelope as an ephemeral or view-once message rather than carrying the poll fields itself, so `unwrap` peels it the same way, and whatever poll version turns out to be nested inside falls through to the existing `pollCreation` switch unchanged.

The other gap was kinds that are not content at all but were falling through to the generic `"[Message]"` placeholder instead of being dropped: a call or its log entry (`Call`, `CallLogMesssage`, `BcallMessage`), a history-sync bundle or notice (`MessageHistoryBundle`, `MessageHistoryNotice`), and session or key housekeeping payloads (`PlaceholderMessage`, `SecretEncryptedMessage`, `GroupRootKeyShare`, `RootSecretDistributeMessage`). These are added to `isContentless` alongside the existing poll-vote, pin-in-chat and keep-in-chat cases, so none of them is ever stored or shown. Many further fields on `waE2E.Message` — WhatsApp Business templates, lists, buttons, payments, newsletters, statuses — are left exactly as they were, falling through to the generic placeholder: they were judged too speculative to commit a specific rendering to without a live account actually hitting them, which the new diagnostic line now makes possible to confirm cheaply if they turn out to matter.

## WhatsApp's pinned and archived state reads from whatsmeow's own chat settings store, not a cache of this connector's own

Superseded: an earlier wave found that a real account's pins beyond the first never actually stuck, because `syncConversation` always sent WhatsApp's own synced snapshot of a conversation's pinned and archived flags through `Sink.Organized` unconditionally, and that snapshot is eventually consistent, so a resync arriving moments after `SetPinned` sent its patch could still carry the pre-patch value and revert it. The fix at the time was `Connector.organize` (a `remote id -> {pinned, archived}` cache) plus `Connector.localOrganize` (which remote ids a local change had set more recently than any live confirmation), with a further `pinnedFromAppState`/`archivedFromAppState` flag per field once a second bug surfaced: a pin arriving live, by app state, before its conversation had ever been synced had nowhere to be remembered, since `conv.RemoteID` didn't exist yet to key a cache entry by (see git history for the full original reasoning, in both this entry and "WhatsApp's chat organizing and naming caches live in memory for the process's lifetime" above). Both caches are gone now, along with the races between them (a resync winning against a just-sent patch, a pin arriving before its conversation existed): this connector keeps no copy of pinned or archived at all any more.

This is possible because whatsmeow already keeps its own durable, continuously updated copy: `store.ChatSettingsStore`, the `whatsmeow_chat_settings` SQLite table inside the account's own session database, with `PutPinned`/`PutArchived`/`PutMutedUntil` and `GetChatSettings`. Reading `appstate.go` in the pinned whatsmeow module (`go.mau.fi/whatsmeow`, via `go env GOMODCACHE`) shows exactly when that table gets updated relative to this connector's own code: `Client.SendAppState` sends the patch, and, once the server accepts it, calls `fetchAppState` — *synchronously*, before `SendAppState` itself returns — which re-fetches the server's now-current patches and applies them to `Store.ChatSettings` via the same `Put*` calls a notification-triggered resync uses. Only the *events* collected along the way (`events.Pin`, `events.Archive`, the ones `handlePin`/`handleArchive` hear) are dispatched afterwards, in a separate goroutine, by both `SendAppState` and the ordinary background sync `notification.go` runs when the phone reports a change. So by the time a call to `SendAppState` returns successfully, whatsmeow's own store already has the new value; this connector never needs to track a "pending local change" window at all, because there is nothing left for a resync to race against.

`device.chatSettings(ctx, jid)` is the one read this connector now does everywhere pinned or archived used to come from a cache: `SetPinned` and `SetArchived` (organize.go) send the patch, then read this back and report it (`reportOrganized`); `handlePin` and `handleArchive` do the exact same read-and-report for a live echo, rather than ever trusting the one field the event itself carries — the echo is only WhatsApp's notice that the store already changed, never the new value itself; `history.go`'s `syncConversation` reads it too, in place of ever consulting a synced conversation's own `Pinned`/`Archived` fields, which `conversationFromSync` no longer even sets. With nothing of this connector's own left to disagree with the store, a resync can no longer revert anything, and a pin that arrives live before its conversation exists needs no special handling either: whatsmeow's store already has it by the time history sync finally creates that conversation and reads the store fresh.

The 3-pin limit (`pinLimit`) is counted the same way instead of from a cache: `pinnedCount` calls `device.chatSettings` for every conversation remote id this connector has ever reported (`Connector.chatKinds`, kept for other reasons and untouched by this change), rather than scanning a cache of its own; a chat WhatsApp already has pinned before this connector has reported it is not countable yet, the same limit the old cache had too. Archiving a chat unpinning it is no longer computed here either: `appstate.BuildArchive(target, true, ...)` already bundles the matching unpin mutation into the same patch, so the settings read back afterwards already show `pinned: false` on their own.

No existing account needs to re-pair for this: whatsmeow's chat settings table already existed and was already kept current by the same app-state processing this connector always ran underneath it; this change only stops duplicating that state in the connector's own memory.

## Voice notes: an inline player behind a Loader, played by a controller that outlives the delegate

A voice note (WhatsApp's push-to-talk audio, Telegram's voice message) is its own `domain.Media` kind, `"voice"`, rather than staying `"file"`: both connectors already distinguished it internally (WhatsApp's `AudioMessage.PTT`, Telegram's `DocumentAttributeAudio.Voice`) only to label it, so giving the UI the same distinction costs one more constant and lets it draw a player instead of a generic file row. `domain.Media.Duration` already existed and both connectors already filled it in for a voice note; nothing new was needed there.

In-window playback needs Qt 6's QtMultimedia module (`MediaPlayer`/`AudioOutput`, with its ffmpeg backend decoding Opus/OGG), which is not a published dependency of this plugin: it happens to be installed on some Omarchy machines only because another app pulled it in. A QML file that imports a missing module fails to load outright, so nothing in this feature's main path may import it. The one file that does, `ui/components/VoiceNoteRuntime.qml`, holds nothing but a `MediaPlayer` and the handful of properties/functions callers need (`source`, `playing`, `rate`, `positionMs`, `durationMs`, `ended()`); `ui/controllers/VoiceNoteController.qml` loads it through a `Loader` and reads `Loader.status === Loader.Error` as "QtMultimedia is not here," exposed as `available`. Every playback method is a no-op when `available` is false, and the bubble's own component falls back to the same plain "open externally" row `FileView` already uses for an ordinary file, labelled "Voice message · open" rather than naming a missing dependency the user cannot act on.

The controller, not the message bubble, owns the one `MediaPlayer` and all playback state (`playingId`, `playing`, `positionMs`, `durationMs`), for the same reason `PhotoViewerController` is a controller rather than part of `PhotoView`: a `ListView` delegate is recycled or destroyed as the list scrolls, so a `MediaPlayer` living inside one would stop decoding the moment its row scrolled out of view. `ui/components/VoiceNotePlayer.qml` only ever reads this state through plain properties (`available`, `playing`, `positionMs`, `durationMs`) and reports intent with the same `wanted()`/`opened()` signals `PhotoView`/`FileView` already use; `MessageBubbleContent` and `MessageDelegate` thread a single plain summary object (`voiceNotes: {available, playingId, positionMs, durationMs}`) down from `ConversationController`, never the controller itself, so a view never calls into a controller, only reads data, matching the rest of `ui/components`.

Reusing `mediaWanted`/`mediaOpen` rather than inventing voice-specific signals keeps every file between the bubble and the controller unchanged apart from one added property: `ConversationController.openMedia` already branches on a message's media kind for photos; it gained one more branch that, when a `VoiceNoteController` is available, downloads the note if needed (voice notes are small, so this happens the moment it is seen, like a photo's thumbnail-to-full-image fetch) and calls `toggle(id, path, durationHintMs)`, which starts a different note (pausing whichever was playing), or pauses/resumes the same one, never playing two at once. Enter on a highlighted voice note reaches this through the same `message.open` action a photo or file already uses; `Highlight.hints` only changes its label from "Enter open" to "Enter play" when the highlighted message's media kind is `"voice"`.

Playback is not paused when the conversation closes or another one opens, and does not stop if the playing message's delegate scrolls out of view: both are deliberately left as "still playing," the same as a music player would, rather than adding more state transitions for behaviour nobody asked for. A scrubber drag and a 1x/1.5x/2x speed control were both left out: dragging needs a new signal threaded through every file between the bubble and the controller for an interaction a click-to-open already covers reasonably (seeing the bar fill is enough without being able to grab it), and a speed control needs the same threading for a feature the brief only asked for if cheap.

## A voice note's media is written once, so a message stored before the "voice" kind existed stays `"file"` forever, and the UI, not the helper, now covers for that

A real voice note showed as "Unavailable" after the player shipped: its audio file had actually reached `PhotoView`, which tried to decode it as a photo. `backend/internal/store/messages.go` encodes a message's `domain.Media` to JSON once, at insert, and never re-normalizes a stored row; a WhatsApp voice note received before the "voice" media kind existed was normalized as `domain.MediaFile` with `FileName: "voice-message.ogg"` (see `audioMedia`'s history before the commit that added `domain.MediaVoice`), and that JSON blob is what the row still carries, permanently, on any machine that received it before upgrading. The helper has no mechanism to re-normalize old rows, and `domain.Media` carries no mime type at all for the UI to fall back on instead.

`ui/lib/Media.js`'s `kindFor` covers for this on the UI side: a media item's `kind` is trusted as-is for `"photo"`, `"video"`, `"link"` and `"voice"`, but `"file"` is only taken at face value when the file name's extension is not one the in-window voice player can decode; a recognised audio extension (`.ogg`, `.oga`, `.opus`, `.mp3`, `.m4a`, `.wav`, `.aac`, `.amr`, `.weba`, `.flac`) routes to the voice player instead. This is a deliberate widening beyond just the legacy voice note shape: an ordinary audio file sent as a plain document plays exactly as well through the same player, so there is no reason to make the user leave the app for one. `MessageBubbleContent` and `ConversationController.openMedia` both call `kindFor` rather than reading `media.kind` directly, so the bubble's view choice and clicking it to play always agree.

The decode error itself had a second, independent cause worth fixing the same way: `MessageBubbleContent` bound every media view's `path` straight from the shared `message.mediaPath`, regardless of that view's own `visible`. An invisible `PhotoView` sitting beside the voice player would still pick up the same downloaded path once anything set it, and `Image` loads its `source` whether or not the item is visible — so even a correctly-tagged `"voice"` message was quietly triggering a wasted, logged decode attempt on its own audio file. Each view's `path` and `failed` are now gated on that same view's `visible`, so only the one view actually drawn for a message's media ever receives its downloaded path.


## List row glyphs are plain Unicode symbols, never an icon font's private-use codepoint

`ConversationRow`'s pin marker was an empty string, and its mute marker was a private-use-area codepoint (`U+F1F6`, from an icon font such as Font Awesome) drawn in `Theme.font.family`, the app's ordinary text font: neither renders anything, since the pin glyph was simply missing and the mute glyph's codepoint has no mapping outside the icon font it was copied from. Every other glyph in this UI (the composer's paperclip, the hover toolbar's reply arrow, the voice player's play/pause) is a plain Unicode symbol, which `Theme.font.family` draws through ordinary font fallback the same way it draws any other character; the pin and mute markers now use `"📌"` and `"🔇"` for the same reason, rather than adding an icon font as a dependency for two glyphs. A pinned row also carries a quiet "Pinned" text tag beside the glyph, so a chat sorted to the top of the list is not identifiable by the glyph alone, matching the existing "Hidden"/"Archived" tag a dimmed row already carries for the same reason.

## A placeholder that never gets a redelivery also asks the primary phone, not only the original sender

The earlier fix for `events.UndecryptableMessage` (see "`events.Receipt` always runs both lanes…" above) assumed whatsmeow's own retry-receipt request to the original sender was enough; a real account's self-chat showed this is not always true. A bot replying into the self-chat as another of this account's own linked devices left its placeholder as "Waiting for this message" forever: the diagnostic line showed `unavailable=false`, meaning whatsmeow did send the usual retry receipt, but the bot never answered it, so the redelivery that would replace the placeholder never arrived.

whatsmeow has a second path for exactly this: `Client.AutomaticMessageRerequestFromPhone`, off by default, which — once the first retry receipt goes unanswered for `RequestFromPhoneDelay` (5 seconds) — sends a peer-data request to this account's own primary phone instead, asking it to resend the message from its own copy. The phone's answer reaches this connector as an ordinary `*events.Message` with the same id, exactly like a successful sender retry, except its `UnavailableRequestID` field is set. `openDevice` (`device.go`) now sets this field to `true` on the client; nothing else about `handleContent`'s matching needed to change, since it already replaces a pending placeholder by comparing conversation and message id alone, regardless of which path produced the redelivery. `logPhoneResend` (`diagnostics.go`) logs a privacy-safe line — no JID, name or text — whenever `UnavailableRequestID` is set on a redelivery that resolves a placeholder, so a report of "the placeholder never clears" can be checked against whether the phone ever actually answered.

The reverse direction — another of this account's devices (such as the same bot) failing to decrypt a message *this* account sent, and asking for a resend — needs no code here: whatsmeow's `Client.SendMessage` already caches every outgoing message in a 256-entry in-memory ring buffer (`addRecentMessage`) and answers an incoming retry receipt from that cache automatically, through its own internal node handler, never surfaced as an event this connector would need to subscribe to. `Client.GetMessageForRetry`, the hook for when that cache has already evicted a message, defaults to returning nothing; it was left unset, since the ring buffer already covers a bot's retry window in practice, and wiring a second, persistent cache for the rare miss was not something the evidence in hand called for.

## WhatsApp albums unwrap to their individual photos; four Business kinds get their own text instead of the generic placeholder

The same diagnostic line mentioned above ("A few more WhatsApp content kinds…") turned real-account speculation into a confirmed list: `albumMessage` and `associatedChildMessage` (an album's header and its individual photos/videos), plus the Business kinds `interactiveMessage`, `buttonsMessage`, `templateMessage` and `templateButtonReplyMessage`, were all logged as unknown. An album's header (`AlbumMessage`, just an expected photo/video count) carries nothing a person actually wrote, so it joins `isContentless`'s switch and is dropped exactly like a call log or a history-sync notice; each photo or video in the album arrives as its own message wrapped in `associatedChildMessage` (a `FutureProofMessage`, the same forward-compatible envelope `ephemeralMessage`/`viewOnceMessage` already use), so `unwrap` peels it the same way those are peeled, and the inner image or video then shows, downloads and fetches media exactly like one sent on its own — no new rendering path needed, since the photos were always going to appear individually regardless of the header.

The four Business kinds are real content, so each gets its own visible text instead of falling through to `"[Message]"`: `interactiveMessage`'s body, falling back to its header's title and then its footer's text, since WhatsApp lets a business send any mix of the three and the body is the part actually meant to be read; `buttonsMessage`'s own `ContentText`; `templateMessage`'s hydrated content text, read from whichever of its two possible fields (the dedicated `HydratedTemplate`, or the older `Format` oneof's `HydratedFourRowTemplate`) WhatsApp populated; and `templateButtonReplyMessage`'s `SelectedDisplayText`, the option a person picked. None of these render a template's buttons, a carousel, or an interactive header's own image — only the text a person would actually read was judged worth the specific handling; a business message with none of these text fields set still falls through to the generic placeholder, the same as before.

## An expired WhatsApp CDN link gets one media retry through the primary phone before `media.fetch` gives up

A real account's older voice notes all failed to download with the same generic `reason=download`, logged with nothing to tell a dead link apart from a network blip or a bad hash. WhatsApp's media links age out after some weeks; `go.mau.fi/whatsmeow` reports this as `ErrMediaDownloadFailedWith404`/`...With410` (both a `DownloadHTTPError` whose own `Is` compares status codes, so `errors.Is` finds either). `fetch.go`'s `downloadOrRetry` now sorts every failed attempt into one of four safe classes before logging it (`downloadFailureClass` in `diagnostics.go`: `decrypt`, `expired`, `http` for any other status, `network` for everything else) with a new stderr line, `whatsapp: media download failed (class=%s)` — additive, the existing `app`-level `media: fetch failed (reason=...)` line is unchanged. Only `expired` (404/410) goes further, since whatsmeow's own doc comment on `SendMediaRetryReceipt` describes exactly this case: a media retry receipt asks WhatsApp's primary phone, not the server, to re-upload it.

`retry.go` is the new file that owns that exchange. It builds the `*types.MessageInfo` the receipt needs (chat, sender, from-me, is-group) from whichever `message_keys` row `keys.go` already saved for the message — the same row `React` and a reply's quoting already depend on — so a message with no saved key (should not happen in practice, since a key and a media reference are written from the same three places) is reported as already-expired rather than sending a malformed request. WhatsApp's answer arrives asynchronously as `events.MediaRetry`, matched back to the right `FetchMedia` call by message id through a small table on `Connector` (`retryWaiters`, guarded by the same `c.mu` every other per-run map already is), registered by `registerRetryWaiter` right before the receipt is sent and always cleaned up by its paired `cleanup()`, so two concurrent fetches for two different messages each get their own channel and neither can resolve the other's wait, and a request nobody is listening for any more cannot accumulate in the table. A bounded `context.WithTimeout` (`mediaRetryTimeout`, 30s) covers a phone that is offline or simply never answers. `whatsmeow.DecryptMediaRetryNotification` decrypts the answer with the same media key; a decrypt failure, a non-`SUCCESS` result (the phone reporting `NOT_FOUND`, in particular) and a timeout all become the same `domain.ErrMediaExpired`, a new sentinel alongside `ErrMediaDecryptFailed`, since by that point there is nothing further this connector can do regardless of which of the three it was. A success updates the stored reference's `DirectPath` (`mediaStore.put`, the same upsert `saveMediaRef` already uses) and retries the download exactly once more with it; `app.MediaExpired` and `ui/lib/Format.js`'s `"no longer on the phone"` give the UI its own phrase for this reason, distinct from `not-found`'s "no longer available" (a reference WhatsApp's own servers, not this connector's media store, never knew about at all).

This applies to every media kind FetchMedia handles, not only voice notes: `downloadOrRetry` only ever sees a `mediaRef` and never branches on `mediaKind`, so a photo, video or document's expired link is retried the same way without any kind-specific code.

## Deleting messages: `connector.Deleter`, removal not a tombstone, and WhatsApp's LID mismatch fixed at `chatID`

A deleted message still showed, on both services, for reasons that turned out to be entirely on the connector side: the app and UI halves of the pipeline (`Ingest.Deleted`, the `message.removed` event, `ConversationController._removeMessage`, `Timeline.remove`) already existed and already worked. Telegram's own `UpdateDeleteMessages`/`UpdateDeleteChannelMessages` handling was already correct and already tested. WhatsApp's was not: a real account's own phone revoking or "delete for me"-ing a message often addresses the chat by its hidden id (LID) even when every message in it was stored under the chat's phone JID, the same split already fixed for the self-chat alone (see "WhatsApp's self-chat always canonicalizes to its phone JID, never its LID" above) but not for an ordinary direct chat. `chatID` now resolves any chat JID through `dev.pnForLID` (a thin wrapper over whatsmeow's own `Store.LIDs.GetPNForLID`, the same local, no-network lookup `contactName` already uses) whenever it is not the self-chat and is itself a LID, falling back to the bare LID's own remote id only when no mapping is known yet. Every call site that already went through `chatID` — `handleRevoke` included — gets this for free; no call site changed. The second bug was simpler: WhatsApp's "delete for me" arrives as `events.DeleteForMe`, a case this connector's event switch had no branch for at all, so it fell into the same silent default as a genuinely unhandled event. `handleDeleteForMe` (`delete.go`) reports it through `Sink.Deleted` the same way `handleRevoke` does.

Removal, not a "this message was deleted" tombstone, is how both directions of a delete show up: the store has no tombstone concept, `Ingest.Deleted` already removed the row outright before this change, and Telegram's own delete is already an unconditional removal with no distinction between "for me" and "for everyone" once it reaches a client. Keeping one behaviour for both services and both delete reasons, rather than inventing a tombstone for WhatsApp's "for everyone" alone, was judged simpler and more consistent than the two-rule split the brief offered as an option.

The feature half, deleting from OmaMessenger itself, is a new optional capability, `connector.Deleter`, exactly the shape `Reactor` and `Organizer` already are: `Manager.DeleteMessages` type-asserts for it and fails with `ErrNoDeleter` otherwise, and `app.Commands.DeleteMessages` resolves the UI's local message ids to their service ids (refusing one with no service id yet as "cannot be deleted yet", matching how `React` already refuses a message never sent), asks the Deleter, and on success removes the rows and publishes their removal itself — the same `store.DeleteMessages` call and `message.removed` event `Ingest.Deleted` uses, not a second path. `connector.ErrDeleteUnsupported` is the sentinel a Deleter wraps for a refusal the user can act on (not this account's own message, a channel asked to delete "for me" only, Telegram's own time limit or missing admin rights); `app`'s `deleteError` maps it, and the capability-missing `ErrNoDeleter`, to one fixed, safe `ErrInvalidInput` message, the same shape `reactError` already uses for `ErrNoReactions`.

Telegram's own delete needs no new client-side bookkeeping: `messages.deleteMessages` (with `revoke` for "for everyone") handles a user or basic group, and `channels.deleteMessages` handles a channel or supergroup, which Telegram always deletes for everyone regardless of what the request asks, so "for me" there is refused outright rather than silently doing the opposite of what was asked. A refusal surfacing as an RPC error such as `MESSAGE_DELETE_FORBIDDEN` or `CHAT_ADMIN_REQUIRED` (checked with `tgerr.Is`, the same helper `gotdauth.go` already uses for a sign-in refusal) is mapped to `ErrDeleteUnsupported`; anything else, such as a dropped connection, is wrapped but passed through unchanged, becoming the UI's fixed internal error rather than a specific one.

WhatsApp's own delete reuses exactly the message-key machinery React and reply quoting already built (`keys.go`'s `message_keys` table and `targetKey`): "for everyone" builds a revoke (`waE2E.ProtocolMessage_REVOKE`) from the message's saved key, refusing with `ErrDeleteUnsupported` when the key is missing or records a sender other than this account (an admin revoking someone else's message in a group is out of scope, same as React's own unknown-target refusal); "for me" needs no such restriction, since any message, by anyone, can be removed from this account's own view. Deleting for me has no exposed `BuildDeleteForMe` in the pinned whatsmeow version, only the mutation's index name (`appstate.IndexDeleteMessageForMe`) and its proto message (`waSyncAction.DeleteMessageForMeAction`), so `buildDeleteForMe` constructs the `appstate.PatchInfo` and `MutationInfo` by hand, the same way `appstate.BuildStar` already does for the one other per-message, per-sender app-state action whatsmeow does implement: chat, message id, a `"1"`/`"0"` from-me flag and the sender (or `"0"` when there is none to distinguish) as positional strings in the mutation's index, version 2 to match `BuildStar`'s. This has not been verified against a real account's own "delete for me" patch, since the test suite cannot reach one; if WhatsApp ever rejects or ignores it, the index's field order or version is the first thing to check against a packet capture of WhatsApp Web's own app actually doing it.

## A failed media.fetch is always logged with a safe reason, never left silent, and the fake connector's placeholder is picked by path, not by a kind it is never told

A real account's voice notes showed "Unavailable" with nothing in the helper's log and no warning in the UI: `media.fetch`'s failure was recorded on the message (`mediaFailed`) but never written anywhere a report could point to, so there was no way to tell a missing reference, a failed decrypt, a timeout or a full disk apart after the fact. `app.Commands.FetchMedia` now classifies every download failure into one of five safe categories (`app.MediaFetchReason`: `not-found`, `decrypt`, `cache`, `timeout`, `download`) and writes one stderr line through an injected `app.Logger` (`*log.Logger` already satisfies it; wired in `main.go`'s `wire`), naming the service and the message's media kind but never the error text itself, which could otherwise echo a server detail or file path. The same category travels back to the UI as `*app.MediaFetchError`, which `server/errors.go`'s `rpcError` turns into the existing fixed "internal error" with the category attached as the JSON-RPC error's `data.reason` — additive, so an older UI that ignores `data` sees exactly what it already did. `ui/controllers/ConversationController.qml`'s `downloadMedia` now also `console.warn`s the code and reason on every failure, and `VoiceNotePlayer`'s play button shows the same category, translated to a short phrase by `Format.mediaFailureReason`, in its tooltip once a fetch is known to have failed.

Telling a cache failure apart from a connector failure needed no cache-package sentinel (the `app` package's depguard rules do not allow importing `cache`, and adding one there felt like the wrong direction for an infrastructure package to grow): `FetchMedia`'s fill closure captures the connector's own error in a local variable before returning it to `cache.Cache.Fetch`; if `Fetch` still failed but that local is `nil`, the closure was never even called, so whatever failed did so in the cache itself (an invalid name, a full disk), reported as `cache` regardless of the underlying OS error's text.

Separately, closing the loop needed a connector that could actually fail a voice note's download: the fake connector's `FetchMedia` wrote the same procedurally painted JPEG for every message, regardless of media kind, so a voice note "downloaded" successfully but the file QtMultimedia was handed was never audio at all — a bug a fake-controller unit test, which only ever hands the player a path it trusts, cannot see. `FetchMedia` has no access to the message's own media kind (its signature is `(ctx, conv, messageRemoteID, path)`, matching every other connector), so it tells a voice note apart from a photo by `path`'s own extension instead — `app.mediaFileName` is the one place that names it, and only a voice note's path ends in `.ogg`. The first version of this check matched on the final path verbatim and still failed every time: `cache.Cache.fill` always calls a connector's `FetchMedia` with a temporary path suffixed `.part`, renaming it into place only once the write succeeds, so the extension check has to trim that suffix first or every voice note silently gets the photo placeholder under the right file name. `backend/internal/connector/fake/voice.go` carries a fixed, committed third-of-a-second silent Opus-in-Ogg clip (there is no Opus encoder in this module's own dependencies to generate one at runtime the way `placeholderPhoto` paints its JPEG); `tests/qml/VoicePlayback/shell.qml` drives the real Panel and the real test helper through Ctrl+K, Escape and Enter on this fixture, the one test in the suite that exercises the RPC round trip, `app.Commands.FetchMedia`, the fake connector's own download and the path landing back on the message all at once, which is exactly the seam the original bug lived on.

## WhatsApp's `MarkRead` is read back from persisted message keys, and also sends WhatsApp's own chat-read mutation

Reconnecting was marking every previously-read WhatsApp conversation unread again, even though the phone still showed it read: `MarkRead` only ever acted on an in-memory `unread` map, fed by live incoming messages and a heuristic (`noteUnreadTail`) that guessed, at history-sync time, which of a conversation's freshly-synced messages were its unread ones. A fresh process starts with that map empty, so a resync straight after a restart or a re-pair had nothing to tell WhatsApp about, and the connector's own stored unread count was then overwritten by WhatsApp's own unchanged server-side figure. `MarkRead` (now in `markread.go`) instead reads a conversation's newest `conv.Unread` incoming messages straight back out of `message_keys` (`keys.go`), which gained an additive `timestamp` column (Unix milliseconds, matching `domain.Message.Created`; `ensureMessageKeysTable` migrates an account's existing database to add it, since `CREATE TABLE IF NOT EXISTS` does not) so they can be ordered by recency. This is the same assumption `noteUnreadTail` made — WhatsApp's own unread count names how many of a conversation's newest messages are unread, never which ones by id — just read back at `MarkRead` time instead of guessed at sync time and stashed in memory, so it works identically whether the unread messages arrived live, during this run's own history sync, or an earlier run entirely. One trade-off was accepted deliberately: `MarkRead` no longer deduplicates, so calling it twice for a conversation that is still unread resends the same receipts; WhatsApp tolerates a resent read receipt (the same thing happens on any ordinary reconnect), and this was judged far safer than ever again losing read state to a restart.

`MarkRead` also now sends `appstate.BuildMarkChatAsRead`, the app-state mutation WhatsApp's own clients send when a chat is opened, naming the chat's newest message (again read back from `message_keys`) as the point everything is read up to. The per-message read receipts already being sent only ever update the *sender's* client; they do nothing to WhatsApp's own server-side record of this account's unread count, which is what the phone and any other linked device actually resync from — without this mutation, a resync kept bringing an already-read chat back as unread no matter how many receipts had gone out. Sending it is best effort, logged and ignored on failure (`logMarkChatReadFailed`), the same as Telegram's own read reporting: the receipts already sent still stand, and a later resync corrects any miss. The reverse direction — a chat marked read by this same mutation from the phone or another linked device (`events.MarkChatAsRead`) — is handled the way the existing self-read receipt lane already was: `Sink.Unread` to 0; a chat marked *unread* this way is left alone, since nothing here tracks how many messages that would put back and WhatsApp's own separately-synced unread count corrects it regardless.

## WhatsApp's "0" system account is a real, if read-only in practice, conversation titled "WhatsApp"

WhatsApp's own "0" system account (`0@s.whatsapp.net`), which sends real security notices and service announcements, used to be treated by `isSystemJID` the same as the status broadcast, old-style broadcast lists and newsletters: dropped outright, in both history sync and a live message, so its notices never appeared at all. Unlike those three, it is addressed to this account specifically and carries content worth reading, so `isSystemJID` no longer recognises it; `titleFallback`'s fixed case for it (`"WhatsApp"`, ahead of the ordinary phone-number fallback) is what it resolves to once a message's own push name, this connector's name cache and any saved contact (all checked first, same priority order as any other direct chat) come back empty, which they always will since nobody has "0" saved as a contact. A history-synced entry for it with no real message content is still dropped the same way any other never-before-seen conversation with nothing worth showing is (see `hasRealContent`), so an account that has never received one of these notices sees no empty "WhatsApp" conversation appear on its own.

## A 403 is a stale WhatsApp media link too, and a media retry's re-upload is accepted even when its plaintext digest no longer matches

A real account's voice notes kept failing after the fix above: ten downloads logged `class=http` (the generic bucket, carrying no status) and never got a retry at all, and two more got a retry, which whatsmeow reported as succeeding, immediately followed by a decrypt failure. `downloadFailureClass` now logs the numeric status alongside its class whenever whatsmeow's own `DownloadHTTPError` carries one (`downloadFailureStatus` in `diagnostics.go`), which was enough to show the ten were all `403`s: whatsmeow's own `DownloadMediaWithPath` already treats `ErrMediaDownloadFailedWith403` exactly like `...With404`/`...With410` (it gives up on that host rather than trying the next one), so `expiredDownloadErrs` now includes it too, and a 403 retries through the primary phone the same way a 404 or 410 already did.

The decrypt failure after a successful retry is a second, separate problem: WhatsApp's primary phone can genuinely re-encode a file when it re-uploads it for a retry (voice notes especially), so the re-upload's plaintext legitimately no longer matches the `FileSHA256` the original message declared, even though nothing about it is actually wrong. whatsmeow's own `downloadAndDecrypt` already sets its `data` return value from a successful decrypt *before* running that specific plaintext check, so a failure there (`ErrInvalidMediaSHA256`) still comes back with the decrypted bytes attached to the error — the media-key HMAC, checked immediately before, already authenticated the ciphertext against this message's own key by that point. mautrix-whatsapp's own `reuploadWhatsAppAttachment` relies on exactly this and logs, rather than fails, the same mismatch ("WhatsApp seems to ignore them too"). `recoverStaleDigest` (`fetch.go`) does the same here: `downloadOrRetry` and `retryDownload` both check it before falling through to `classifyDownloadErr`, and `logStaleDigestAccepted` (`diagnostics.go`) reports how often this happens. This does not, and cannot, cover the other two decrypt errors (`ErrInvalidMediaEncSHA256`, the ciphertext hash, and `ErrInvalidMediaHMAC`): both are checked *before* whatsmeow ever decrypts anything, so there is no authenticated data to fall back to, and whatsmeow's own public API has no way to skip either check and still get a decrypted result back.

## MarkRead's phone-visible failure was the app layer always reporting zero unread, not the connector

A real account's "mark read in OmaMessenger does not mark read on the phone" report turned out to have nothing wrong in the WhatsApp connector at all: `app.Commands.MarkRead` fetched the conversation to hand the dispatcher *after* `store.MarkRead` had already cleared its unread count to zero, so every single call — not just some — told WhatsApp's connector a conversation with zero unread messages, which `unreadMessageKeys` correctly treats as nothing to do. It now fetches the conversation first and clears the count after, so the dispatcher sees the real count. `app.Ingest`'s separate debounced path (a message arriving while the user is actively looking at its conversation) had the same shape of bug for a different reason: `Ingest.save` returns the conversation it fetched *before* `AddMessage` bumps its unread count, and `Incoming` immediately clears that count locally again before the debounced `MarkRead` to the service ever fires, so the conversation `scheduleMarkRead` was handed was always stale. `Ingest` now accumulates the real count itself (`pendingUnread`, added to on every call that schedules a flush, reset once it fires) rather than trusting a conversation value that the same code path already overwrites.

`whatsapp.MarkRead` itself gained one diagnostic line per call, `whatsapp: mark read (receipts=%d, senders=%d, chat_patch=sent|failed|skipped, has_timestamp=%v)` (`logMarkRead`, `markread.go`), including the now-common case of `receipts=0, senders=0` for a call with nothing pending — on its own, in a real account's log, this line would have pointed straight at the app-layer bug above without needing a connector-side investigation at all. `chat_patch` reuses the outcome `sendChatReadState` already computed (now returned as a `chatPatchResult` instead of only logged on failure); `has_timestamp` flags a `message_keys` row saved before the timestamp column existed (default `0`), which an account only clears by receiving a fresh message in that conversation, not by restarting or re-pairing — the existing `timestamp DESC, rowid DESC` fallback already picks a sensible row either way, so this is visibility, not a correctness gap.

A third possible cause was investigated and ruled out: WhatsApp's read receipt only carries a `participant` (sender) JID for a group chat at all (`whatsmeow.Client.MarkRead` never attaches one for a direct chat), and the sender JID this connector stores per message (`senderKeyID` in `keys.go`) already keeps whichever form — phone JID or LID — whatsmeow itself reported the message's sender in, with no canonicalization that could have changed it. No evidence pointed at a real addressing mismatch here, so no change was made; group read receipts are the one path this was not able to verify against a real multi-device group.

## Telegram's update-manager state is saved to its own file per account, not a store table; WhatsApp already catches up on its own

Both services were checked against the same problem: a long gap between helper runs must not silently lose whatever happened on the service while it was not running. They turned out to need opposite treatment.

Telegram's gap recovery (`gotd/td`'s `updates.Manager`, wired in `connector.go`) only ever worked within one run: `updates.Config.Storage`, `AccessHasher` and `UserAccessHasher` default to in-memory stores, so a restart always began with none of the three and `Manager.loadState` treated that as "forget", fetching only the server's current pts and silently discarding everything from the gap. `backend/internal/connector/telegram/updatestate.go` adds `updateStorage`, implementing all three interfaces (`GetState`/`SetState`/`SetPts`/`SetQts`/`SetDate`/`SetSeq`/`SetDateSeq`/`GetChannelPts`/`SetChannelPts`/`ForEachChannels`, and both access-hash getters and setters) over one JSON file per account, `<accountID>.updates.json` in the same `telegram/` directory `credentials.go`'s `sessionPath` and `credentialsPath` already use, written whole on every change and read back whole on `Run`, exactly the pattern `gotd/td`'s own `session.FileStorage` already uses for the session itself. A table in the shared SQLite store was the other option the brief raised; a file was chosen because this state belongs entirely to `gotd`'s own manager (nothing else in the helper reads it), it changes on nearly every incoming update, so giving it a migration and a place in the store's schema would add ongoing coordination cost for a value no other package needs, and the account directory already has exactly this shape of file for exactly this reason. `Forget` deletes it alongside the session and credentials.

With state restored, `Manager.Run`'s own startup (`internalState.Run` calls `getDifference` before entering its event loop) calls `updates.getDifference` against the saved pts/qts/date on every `Run`, and gotd dispatches whatever it gets back — new messages, and anything else (edits, deletes, read-inbox) folded into `OtherUpdates` — through the same `tg.UpdateDispatcher` handlers (`handleUpdates` in `live.go`) a live update reaches, so nothing connector-specific had to change to make the gap apply through the existing pipeline. `TestConnector_AppliesTheWholeGapOnceAfterARestart` drives this directly against `updates.Manager` and a fake `API`, bypassing `Connector.Run` (which needs a real MTProto dial `gotd.NewClient` cannot fake), the same way `scenario_test.go`'s driver already bypasses `Run` for its own reasons; connectortest's shared `Restart` scenario was not reused here because it bypasses `Run` by calling the connector's handlers directly rather than exercising the manager/storage pair this change is actually about. `updates.getDifference` answering `UpdatesDifferenceTooLong` (the gap is too large to list) is handled entirely inside gotd itself: it saves the pts Telegram hands back and immediately asks again from there (`TestConnector_FallsBackGracefullyWhenTheDifferenceIsTooLong` confirms this persists and does not loop or error); `OnTooLong`/`OnChannelTooLong` are wired to one stderr line each, naming only that a resync happened, so a real report of missing messages can be told apart from a connector bug without logging anything private.

WhatsApp needed no equivalent change. `go.mau.fi/whatsmeow`'s own design delivers a session's queued end-to-end messages, and resyncs app state (pin, archive, contacts), as ordinary live events the moment a reconnect succeeds — there is no separate "offline batch" event type to miss, and `Connector.Run` already registers `handleEvents` before calling `dev.connect` (the comment already on that line: "WhatsApp sends history and missed messages as soon as a session connects, and right after pairing, before connectOrPair returns, so the handlers listen first or those events are lost for good"). Every event kind whatsmeow can emit for a backlog delivery — a message, an edit or a revoke (both arrive as `*events.Message`, see `isEdit`/`isRevoke`), a reaction, a receipt (both lanes, see `events.Receipt`'s entry above), `DeleteForMe`, pin/archive/mark-read — already goes through the same `handleEvents` switch regardless of whether it is live or backlog, so no code path is "offline-aware" by design; `TestRun_HandlesEventsThatArriveWhileConnecting` already proved this for history sync specifically, and `TestRun_AppliesTheWholeOfflineGapDeliveredAtConnect` (`events_test.go`) extends the same proof to a message, its edit, its revoke, a reaction and a self-read receipt delivered in one burst through `dev.duringConnect` before `Run`'s `connectOrPair` returns, confirming the claim rather than finding anything to fix.

## Reminders are local and fire from the helper, not the UI

Snoozing a conversation is local to this computer, the same as hiding: nothing about when a reminder is due or that one exists at all is meaningful to WhatsApp or Telegram, and the service already has no concept of it, so there is no connector call to make and no `Organizer`-style sync to keep in step.

The due check runs as its own goroutine in the helper (`app.reminders`, started by `Commands.RunReminders` from `main.go`), not as a QML `Timer` in `ui/Service.qml`, for the same reason notifications are shown from the helper rather than the UI: the window is destroyed and recreated by Omarchy on every hide and show, and the plugin's own service (which does survive a hide) still only exists while `omarchy-shell` itself is running. A reminder due while the window is closed, or while Omarchy is between reloads, would either never fire or need its own separate persistence and re-arm logic duplicated in QML. The helper already keeps running for as long as there is a reason to (an open connector, a pending request), already owns the database that stores `reminder_at`, and already has the one `Notifier` that raises a desktop notification — so one more timer there, re-armed from the same data it already owns, is strictly less to keep in sync than teaching the UI to watch for due reminders itself.

The scheduler re-queries `store.PendingReminders` for the next due time rather than keeping its own copy of what is pending: `SetReminder` wakes it through a buffered channel (`reminders.changed`) whenever a reminder is set or cleared, so a new, sooner reminder is never left waiting behind whatever timer was already armed, and a restart finds every still-pending reminder exactly where the database already has it, due or not, with no separate recovery step. A reminder is deliberately never cleared automatically once it fires: it stays "due" (and sorted to the top of the list, marked "Reminder") until the user unsnoozes it or acts on the chat, which is also why the scheduler remembers (in memory, per run) which due time it already notified for a conversation, so firing is a one-time event per due time rather than repeating every time its own loop wakes again and finds the same overdue row.

## @-mentions: UTF-16 offsets throughout, a member's remote id as its mention id, and sending stays out of scope for stickers

`domain.Mention`'s `Offset` and `Length` are UTF-16 code units, not bytes or runes. Telegram's own message entities already use UTF-16 units, so the Telegram connector passes them straight through in both directions with no conversion at all. A JavaScript string's own indices (`.length`, `.slice`, `.indexOf`) are UTF-16 units too, so the composer's picker (`ui/lib/Mentions.js`) and the bubble's mention highlighting (`Format.messageHtml`'s `mentions` argument) need none either. Only the WhatsApp connector, whose wire format has no position information of its own (a mention is a literal "@<digits>" substring plus a separate list of the JIDs it names), ever converts between UTF-16 and the UTF-8 byte offsets a Go string indexes by; `domain.ByteOffsetsForUTF16` and `domain.UTF16Len` are the one shared place that conversion happens, so it is written and tested once rather than once per connector.

A `domain.Member.ID` is a connector's own remote id for that person, in the exact same form a conversation's `RemoteID` already takes (Telegram: `"user:<id>:<accessHash>"`; WhatsApp: the bare JID string `remoteID` already produces for a sender). Reusing that shape rather than inventing a new one meant `Connector.Members` and the outgoing mention entities Telegram builds, and the JID WhatsApp parses back out of a mention, could reuse `inputPeer`/`jidFromRemoteID` unchanged.

The composer never trusts a mention's offset once it has been inserted: `ui/lib/Mentions.js`'s `resolveMentions` re-finds each inserted member's "@name" token in the final, trimmed text by searching forward from the previous match, rather than carrying the picker's own insertion-time offset through to `Send`. Typing before or after an inserted mention, or `String.trim()` itself, would otherwise desync a cached offset from where the token actually ended up; re-finding it is cheap and always correct, at the cost of silently dropping a mention whose exact "@name" text the user has since edited away, which is the same trade-off `resolveMentions`' doc comment calls out.

WhatsApp mentions inside a photo, video or document caption (`ContextInfo.MentionedJID` on those message kinds, not just `ExtendedTextMessage`) are not built on send: `outgoingMessage` (`reply.go`) is the only place `outgoingMentions` is wired in, and `uploadAttachment` (`upload.go`) was left untouched. The composer always sends plain or replied text when it carries mentions; attaching a file while an "@mention" is also typed sends the mention as literal text, unresolved, the same as it behaved before this feature existed, rather than growing every attachment-building function's argument count for a caption-mention combination the brief did not ask for.

Sending a sticker is out of scope: receiving one normalizes to the new `"sticker"` media kind on both services, static or animated, but nothing offers to send one back. A sticker is not a file the user already has on disk the way a photo attachment is; sending one means browsing the service's own sticker packs, which neither connector exposes and the composer's attach button has no UI for. If this is ever built, it is a new attachment kind and a pack browser, not an extension of the existing file picker.

## Stickers render through the existing media pipeline, never through a Lottie or video decoder

A sticker's full image is fetched and cached exactly like a photo's (`domain.Media.FileName` set, downloaded through the existing `MediaFetcher`/cache path), on the premise that a plain, non-animated `Image` element only ever decodes a format's first frame rather than animating it, which is what "render the first frame, never animate" asks for without any special-casing on the UI side. That premise holds for WhatsApp, whose stickers are always WebP, animated or not, so `FileName` is set unconditionally there. It does not hold for Telegram's two other sticker encodings: a Lottie animation (`application/x-tgsticker`) is JSON describing vector keyframes, not an image a `QImage` reader can decode at all, and a video sticker (`video/webm`) is a video stream, not a still frame one. Telegram's connector leaves `FileName` empty for both, so the UI never asks to download or decode something it cannot show, falling back to the sticker's own thumbnail (`Thumb`) or its associated emoji (`Media.Emoji`, read from `DocumentAttributeSticker.Alt` on Telegram, `StickerMessage.Emojis` on WhatsApp) instead. `ui/components/StickerView.qml` encodes exactly this: it only ever sets an `Image`'s source, never an `AnimatedImage`'s.

A sticker's thumbnail is not necessarily a JPEG the way every other media kind's is: WhatsApp's `StickerMessage.PngThumbnail` is a PNG. Rather than teach `domain.Media.Thumb` a format field, `StickerView.qml` is the one place that knows to build its `data:` URI with `image/png` instead of the `image/jpeg` every other preview-showing component (`PhotoView`, `PhotoViewer`, `LinkPreview`) hard-codes, since it is the only component a sticker's thumbnail ever reaches.

## WhatsApp vote decryption relies on whatsmeow's own secret store; this connector only persists the poll shell and the tally

Decrypting a WhatsApp poll vote (`whatsmeow.Client.DecryptPollVote`) needs the poll creation message's own secret (`MessageContextInfo.MessageSecret`), keyed by the chat, the poll's sender and its message id. whatsmeow's own `Client` already saves that secret itself, in its per-device session database, the moment a message carrying one is first processed (`storeMessageSecret`, called from the library's own message handling before an `events.Message` ever reaches this connector) — so this connector never writes that secret anywhere itself, and `Vote` and `handlePollVote` (`vote.go`) call `DecryptPollVote`/`BuildPollVote` straight through the `device` interface, trusting whatsmeow to already have it.

What whatsmeow's decrypt gives back is only the SHA-256 hash of each selected option's text (`PollVoteMessage.SelectedOptions`), with no option text, no running tally and no per-voter history of its own: a vote protocol, not a poll model. `pollstore.go` is what turns that into the poll the UI shows, in the same per-account database the media reference and message-key stores already use (`storage.go`): `poll_meta` and `poll_options` save a poll's question, multiple-choice flag and each option's text (keyed by the hex of the same hash a vote carries, see `pollOptionID`) once, when its creation message first arrives (`savePoll`), and `poll_votes` keeps every voter's current selection, replaced wholesale on each new vote from that voter rather than merged, the way a `PollUpdateMessage` always carries a voter's complete choice rather than a diff. `pollTally` recomputes the full poll — each option's vote count and whether the signed-in account itself chose it — from these three tables on every read, rather than keeping a running count that could drift from what was actually saved.

## Telegram quiz handling is "do nothing extra"

A Telegram quiz is a `Poll` with `Quiz: true`; its options already carry `Correct` through the same `PollAnswerVoters` tally every ordinary poll's results use, and Telegram itself only fills that field in once the signed-in account has voted or the poll has closed — before then, every option's `Correct` reads `false` from the service's own response, not because this code hides it. `pollFrom` (`telegram/poll.go`) reads `Quiz` and each option's `Correct` the same way it reads everything else in a `PollAnswerVoters`, with no quiz-specific branch anywhere in this connector or the UI: the poll bubble just happens to show a correct answer once Telegram starts reporting one. WhatsApp has no quiz concept at all, so `domain.Poll.Quiz` and `PollOption.Correct` stay at their zero values for every WhatsApp poll.

## Creating a poll is out of scope

Both connectors only receive polls and cast votes in them; neither offers to create one. `whatsmeow.BuildPollCreation` and Telegram's `messages.sendMedia` with an `InputMediaPoll` exist and would make this possible, but building a poll's own compose UI (the question field, a variable list of options, a multiple-choice toggle) is a new composer surface the brief for this feature never asked for, the same way sending a sticker was left out when receiving one was built (see above). If this is ever built, it is its own composer mode, not an extension of `messages.send`'s existing `attachment` field, which already means a file on disk.

## `keys.conf` overrides: Keymap.js keeps its defaults, a sibling file does the merge, and `QS_DISABLE_FILE_WATCHER` turns out not to matter here

`ui/lib/Keymap.js` stays the single definition of default bindings; `ui/lib/KeyBindings.js` is a second, equally pure file that parses `keys.conf`, merges its overrides into a copy of `Keymap.BINDINGS`, and resolves conflicts. `Keymap.js`'s own `match`, `bindingsFor`, `commands`, `keyFor` and `composeHint` each gained one optional trailing parameter (`list`, defaulting to `BINDINGS`) rather than being rewritten: every existing call site that omits it keeps behaving exactly as before, and a caller that has loaded `keys.conf` passes its merged list instead. `Highlight.hints`, the per-message key-hint row's own formatter, used to spell out `'r reply'`/`'e react'`/… as literal strings rather than reading `Keymap` at all; it now takes the same optional bindings list and reads each key through `Keymap.keyFor`, so an override reaches that row too, without changing what it prints when no override exists. `ui/Service.qml` is the one place that actually loads the file (see below) and holds the result as `effectiveBindings`; `ui/Panel.qml`, `ui/components/KeyHints.qml`, `ui/components/MessageDelegate.qml`, `ui/components/Composer.qml`, `ui/components/ListColumn.qml`, `ui/components/PhotoViewer.qml` and `ui/controllers/WindowController.qml` each gained a `bindings` property (or read `service.effectiveBindings` directly, where they already held `service`) threaded the same way `nowMs` already is, since the brief named these exact surfaces — the command palette, the footer hints and the key-hint rows — as the ones that must reflect the effective keys.

A key spec's two "obvious" conflict definitions turn out to disagree, and only one of them is real: comparing every binding reachable from a context against every other one (a context's own bindings plus every global one, the same candidate set `Keymap.match` itself resolves against) flags dozens of pairs that already exist in the shipped defaults, such as `dialog.up` (Ctrl+K, context `dialog`) against `palette.conversations` (Ctrl+K, global). None of those are bugs: `match` always tries a context's own bindings before its global ones, so a context-specific binding deterministically shadows a global one on the same key, which is a real, intended feature (`compose.newline`'s own comment spells out relying on exactly this for `Ctrl+J`), not an ambiguity. The only pairing that is genuinely ambiguous is two bindings that both list the *same* context string, specific or both `global`, since nothing then decides which of the two wins. `KeyBindings.findConflicts` groups bindings by each literal context string they carry (including `"global"` as one such group) and only checks within a group, which is why overriding a global action onto a key a context-specific default already uses (tested in `tests/unit/keybindings.test.cjs`) is left alone rather than reverted: it only ever answers to that key outside the context that already claims it, exactly as a newly-written global binding using that key would.

The brief asked to verify whether `QS_DISABLE_FILE_WATCHER=1` (set in `omarchy-launch-shell`, see omarchy.md) stops a `FileView`'s own `watchChanges` from working, since the plugin cannot editorialize a guess here if wrong. It does not: Omarchy's own shell (`/usr/share/omarchy/shell/Commons/Color.qml`'s `userShellFile`, `/usr/share/omarchy/shell/plugins/bar/Bar.qml`'s file-watching for the active theme and the bar-hidden toggle) already relies on `FileView { watchChanges: true }` to pick up a user's own config edit live, in the exact same process that env var is set for in production. `QS_DISABLE_FILE_WATCHER` only turns off Quickshell reloading its own loaded QML on a *source* change (see omarchy.md's note that a plugin copy still needs `omarchy-restart-shell`); a `FileView`'s own watch is a different, unrelated mechanism and keeps working. `ui/Service.qml`'s `keysFile` follows the exact shape of Omarchy's own `userShellFile`: `watchChanges: true`, `onFileChanged: reload()` (since `text()` is stale inside that signal itself), and the real work done from `onLoaded`/`onLoadFailed` once the reload reports back.

`FileView.setText()` turns out to create every missing parent directory as well as the file itself (verified empirically against a path several directories deep that did not exist, offscreen, before writing this code), so `Service.openKeyConfigFile` (the palette's **Open key bindings file**) needs no separate `mkdir`-style step: it calls `setText` with `KeyBindings.template(Keymap.BINDINGS)` only when `onLoadFailed` has already reported `FileNotFound`, never otherwise, so a file the user has actually edited is never overwritten, then opens it with `Qt.openUrlExternally`, the same xdg-open path every other externally-opened file in this UI already uses.

Both `make test-qml` and `make demo` now also set `XDG_CONFIG_HOME` to a path inside each test's own isolated root, the same way they already isolate `XDG_DATA_HOME`: before this, any test that merely constructed a `Service` (nearly all of them) would have had its `keysFile` resolve to the real developer machine's own `~/.config/omamessenger/keys.conf`, reading it if present and, had any test ever run **Open key bindings file**, writing to it. `tests/qml/KeyBindings/` ships a fixture at `config/omamessenger/keys.conf`, copied into that isolated `XDG_CONFIG_HOME` by the existing `cp -R` step before Quickshell even starts, so the startup load (not just the live-reload path, separately exercised by overwriting the file mid-test with a second `FileView`) is deterministic rather than racing a file write against the engine's own boot.

QML's JS engine rejects two syntax forms Node happily parses: object spread (`{...x}`, an "Unexpected token" syntax error from `qmllint`, worked around with `Object.assign({}, x, {...})` instead) and `Array.prototype.flatMap` (not a syntax error, but a runtime `TypeError` the moment it is called, since the method itself does not exist on this engine's arrays, worked around with an explicit loop building the result with `.concat`). Array spread (`[...iterable]`) and `Set`/`Map` are unaffected and already used elsewhere in `ui/lib`. Neither gap shows up in `make test-js` (plain Node has both), only in `make test-qml`, which is exactly the two-layer trap javascript.md's own header warns about.

## Ctrl+K and Ctrl+G become one unified palette; its "Messages" section is one row per conversation, not per message

Beeper's own command palette merges jumping to a chat with searching messages, so Ctrl+K and Ctrl+G now both open `WindowController`'s existing "conversations" palette mode rather than two separate affordances: Ctrl+G used to call `ListController.run("search.focus")`, which focused the conversation list's own inline search field (still there, still reachable by mouse or Tab, just no longer bound to a global key); `Actions.OWNERS['search.focus']` now names `window`, and `WindowController.run` treats it as an alias for `openPalette("conversations")`. The "Conversations" section keeps behaving exactly as Ctrl+K always did: an instant, local fuzzy filter of whatever `ListController.all` already holds (`Palette.search`/`Palette.conversationOrder`), with no round trip. A "Messages" section is new: typing restarts `WindowController`'s own `messageSearchTimer` (250 ms), which then calls `conversations.list({query})` — the exact RPC `ListController`'s inline search already used, so no new method was added — and keeps the answer in `_messageSearchResults`, filtered through `Palette.messageRows` to rows with `matchMessageId` set at all (a title-only match belongs in "Conversations" instead). `Rpc.guard` drops a reply for a query the palette has since moved past, the same pattern `ListController._search` already used.

This reuse shapes what "Messages" actually shows: `store.Conversations`' search already picks out only the single newest message that matched per conversation (`conversationsByTitleOrMessage`'s `hits` CTE, one row per `conversation_id`), so the palette's "Messages" section is one row per matching *conversation*, each showing that conversation's newest matching message, never a second or third hit from the same chat. A real per-message result list would need a new query shape (and likely a new RPC, since `conversations.list`'s one-row-per-conversation shape is relied on by the conversation list itself); reusing the existing search RPC, as asked, was judged worth that narrowing for a first version. `domain.Conversation` gained `MatchMessageID` and `MatchSender` (both `omitempty`, additive) precisely so a "Messages" row carries enough to open and highlight the exact message, not just the conversation.

Combined keyboard navigation (`WindowController.movePalette`/`acceptPalette`) treats the two sections as one list for Up/Down: index positions `0..paletteResults.length-1` are "Conversations", everything after is "Messages", computed from `paletteResults.length + paletteMessageResults.length` rather than a merged array, so `paletteResults`' own shape (plain `domain.Conversation` objects, read by `_openConversation`) never has to carry a message row's different shape. `CommandPalette.qml` renders the split with `ListView`'s own `section.property`/`section.delegate` rather than a hand-rolled header item, gated behind a new `sectioned` property so "commands"/"links"/"keyBindings" mode, whose rows carry no `section` field, never shows one.

## `ConversationController.openMessage`: a pending highlight applied once the conversation's own page loads, best effort if the message is older than that

Enter on a "Messages" row must open its conversation and land the highlight on the exact matched message, not just whatever `open()` already does (start on the newest loaded message). `ConversationController.open` always clears `highlightedId` to `""` immediately and lets `MessageTimeline`'s `initialLoaded` signal set it to the newest message once the first page arrives (`onInitialLoaded: root.resetHighlight()`); a caller cannot simply set `highlightedId` right after calling `open()`, since that assignment would always lose the race to the timeline's own, later-arriving reset. `openMessage(conversation, messageId)` instead records `messageId` in `_pendingHighlightId` *before* calling the same `_setActive` `open()` uses, and `MessageTimeline.onInitialLoaded` now runs `_applyInitialHighlight`, which checks that field first: when the message turns out to be in the page that just loaded (`timeline.find(id)`), it wins over the newest-message default; otherwise `resetHighlight()` runs exactly as before. A message older than the conversation's first page (the same limitation `scrollToReply`, used for jumping to a quoted message, already has) opens the chat without a visible highlight rather than erroring or forcing a deeper fetch, since both call sites accept that trade-off already.

## Incognito read receipts: gated once in the app layer, not per connector; Service.qml's own value is the setting's real fallback, not the manifest default

`app.Settings` gained a plain `ReadReceipts bool` (default `true`), read by both paths that ever call a connector's `MarkRead`: `Commands.MarkRead` (a direct `conversations.markRead` call) and `Ingest.flushMarkRead` (the debounced read receipt a burst of incoming messages while focused schedules). Both already clear the local unread count unconditionally before this check, so incognito mode only ever skips the one line that would otherwise call `c.dispatcher.MarkRead`/`in.dispatcher.MarkRead`; nothing in `connector.Connector`, `connector.Manager` or either service's own `MarkRead` implementation changed. This is why the brief's "connectors don't each need it" holds: Telegram's `MessagesReadHistory`/`ChannelsReadHistory` and WhatsApp's read receipts and chat-read app-state patch are simply never reached, from one gate, rather than three.

The harder design question was not the Go side but keeping the setting coherent across its two UIs: the plugin's own "Read receipts" setting (forwarded through `settings.apply`, the same mechanism `notificationDetail` already uses) and the command palette's "Toggle read receipts". Omarchy only forwards a bar widget the settings the user has actually changed there, so `BarWidget.qml`'s `_forwardSettings` can call `Service.applySettings({})` — carrying no `readReceipts` key at all — at any time an unrelated setting changes, or the plugin reloads. If `ui/lib/Settings.js`'s `withDefaults` always fell back to the manifest's own default (`true`) for a missing `readReceipts`, every such re-forward would silently undo a palette toggle. `withDefaults` instead takes an optional second argument, the fallback to use when the given settings carry no explicit `readReceipts`, and `Service.qml` always passes its own current `readReceipts` property there, in both `applySettings` and `toggleReadReceipts`; an explicit value from Omarchy's own settings still wins over that fallback, since that is a real user change. `Service._lastSettings` remembers the raw object `applySettings` was last given (not the merged result) purely so `toggleReadReceipts` can resend every other setting unchanged alongside the one it flips, without needing its own copy of `notifications`/`notificationDetail`.

The footer's "Read receipts off" indicator (`ui/components/ReadReceiptsIndicator.qml`) pairs a glyph with a label rather than relying on an icon alone, the same rule the list's own mute glyph already follows, and shows only `Service.readReceipts === false`; nothing server-side exposes whether a particular `MarkRead` call was actually skipped, so this is reporting the setting's own state, not auditing the helper's behaviour; the Go tests that read receipts are honoured, both ways, are what verify the behaviour itself.

## Outgoing attachments retire on delivery, with retention and a size limit standing in for the cases that would otherwise never clean up

The outgoing media area kept every attachment forever, since nothing ever removed one once its message no longer needed it for a retry. A message confirmed sent, delivered or read will never be retried, so `Ingest.OutgoingStatus` now retires its attachment right there, through a new `retireOutgoingAttachment` (`backend/internal/app/outgoing.go`, mirrored by `outgoing_test.go` rather than folded into `ingest.go`/`ingest_test.go`, which were already near the file-length gate). A sent photo's bubble shows that outgoing copy directly (see "Sending photos and files" above), so before deleting it, `retireOutgoingAttachment` adopts it into the downloaded-media cache under the same name `FetchMedia`'s own download path would use (`cache.Cache.Adopt`, new alongside the existing `Fetch`), so a later `FetchMedia` call for that message finds it already cached rather than downloading it back from the service it was just sent to. Either step failing is only logged: at worst a photo is re-downloaded once, or its outgoing copy outlives its message a little longer than it needed to, neither worth failing the status update over.

A message still pending or failed keeps its copy, since `Retry` needs it, but nothing before this bounded how long or how large that could grow for an attachment nobody ever retried. `cache.Outgoing` gained the same shape of limit `cache.Cache` already enforces for downloaded media, parameterised the same way (`NewOutgoing(dir, retention, sizeLimit)`, with the actual numbers - seven days, 256 MiB - as constants in `main.go` next to `mediaCacheLimit`, not baked into the package): a background `Sweep`, run once at startup and hourly after (`RunSweeper`, a ticker loop tested with `synctest`), drops copies older than the retention window first, then, if the area still holds more than its size limit, the least recently used of what remains. A file a `Reserve`/release pair marks as having a send in progress right now is never touched by `Sweep`, regardless of age or size, so a sweep landing mid-upload cannot pull a file out from under the connector reading it; `Commands.dispatch` reserves for exactly the span of its call to the connector's `Send`, released whether it succeeds or fails. A `Retry` for a message whose copy `Sweep` already evicted fails fast with a plain, safe message ("the attachment is no longer available; attach it again") from a new existence check (`checkAttachmentAvailable`), rather than failing deep inside the dispatch with nothing useful to say.

Both areas' `Stats` methods share the same shape (bytes held, limit), so `Doctor`'s existing `CacheStats` capability check, already used for the downloaded media cache, covers the outgoing area for free: a second `Facts.OutgoingSize` and "Outgoing attachments" check sit beside the existing "Media cache" one, filled by `cacheSizeState`'s twin rather than a shared, awkwardly-generic helper, since `any` would be the only way to share one function across two differently-typed fields.

## Failed sends heal themselves: automatic retry, re-copying from the original file, and the sweep no longer evicts

A failed message's local outgoing copy is the only copy there will ever be - it never reached the service - so losing it loses the message. This supersedes the second and third paragraphs of "Outgoing attachments retire on delivery" above: the retention window and size-limit eviction they described are gone, and `Retry`'s "swept" error now means something narrower.

**Automatic retry.** A new `retrier` (`backend/internal/app/retry.go`, mirroring `reminder.go`'s own goroutine) retries every failed outgoing message on its own: at once once its account reconnects (`Ingest.AccountStatus` wakes it on a transition to `domain.AccountConnected`), and otherwise on a backoff - 30s, 2m, 10m, 1h, then hourly - for up to 24h since the message first failed, after which it stops and waits for the user's own retry. `Commands.retryAttempt` is the one place that actually dispatches a retry, whether woken by the scheduler or asked for by `messages.retry` (`Commands.Retry`), which first clears the message's retry state so a retry the user asks for always starts the backoff over, exactly the "resets the backoff" `messages.retry` already promised. Three new columns on `messages` (`retry_at`, `retry_attempts`, `retry_since`) persist the schedule so a restart re-arms from the store, the same as reminders already did; `store.PendingRetries` reads them back soonest-first. `domain.Message.RetryAt` crosses the protocol (`omitempty`) as the quiet "retrying…" signal the UI can show next to "Not sent"; `RetryAttempts` and `RetrySince` do not, the same as `Media.Path` never did, since they are the scheduler's own bookkeeping.

Not every refusal is worth retrying. `connector.ErrSendPermanent` and `connector.SendRetryAfter` (`backend/internal/connector/retry.go`) let a connector's `Send` tell `rescheduleOrStop` apart a refusal retrying will never fix from one that might, and, when the service itself states a wait (Telegram's flood wait), how long. Telegram's `classifySendErr` wraps `tgerr.AsFloodWait` and a short list of permanent RPC errors (`PEER_ID_INVALID`, `USER_IS_BLOCKED`, …); WhatsApp's wraps `whatsmeow.ErrBroadcastListUnsupported` and a malformed remote id, the only two send-time refusals it reports on its own that retrying could never fix. Nothing else about either connector changes: a refusal that is not recognised defaults to worth retrying, the safe assumption when a service's own error surface is not fully mapped.

**Re-copying from the original file.** `prepareAttachment` now also remembers the file the user attached from - `domain.Media.OriginalPath` and `OriginalModTime` - but only when it is a real file on disk, not one already inside the outgoing area such as a clipboard paste (`attachedFromDisk`, which compares directories rather than widening `OutgoingMedia`'s interface for one check). Both fields persist in two new `messages` columns rather than inside the `media` JSON blob, since `Media.Path` and now these two share its `json:"-"` tag for the same reason - they would leak into the protocol otherwise - and the blob is round-tripped through one `json.Marshal`/`Unmarshal` that `json:"-"` already exempts from persistence too. `restoreAttachment`, shared by `Retry` and `retryAttempt`, checks the outgoing copy first and only reads `OriginalPath` - never any other file - when it is gone, re-copying through the same `storeAttachment` a fresh attach uses, after a size-and-modtime check (`recopyFromOriginal`) confirms it still looks like the file that was attached. Neither copy being available, or the original having changed, reports the same safe `errAttachmentUnavailable` the old "swept" error already used, just reached a different way.

**The sweep stops evicting.** `cache.Outgoing.Sweep` no longer applies a retention window or a size limit to anything: its only job now is dropping an orphan - a file whose id matches no message `store.MessageExists` can find at all, such as a clipboard paste never sent or a message the user deleted - and even that waits out a short grace period (`NewOutgoing`'s `grace` parameter, repurposed from the old retention meaning; one hour in `main.go`) so a file just stored has time to become a real message's copy first. `Reserve` still guards a file mid-send, now mostly belt-and-suspenders since an orphan by definition belongs to no message a send could be using. The 256 MiB size limit (`outgoingSizeLimit`, unchanged) is reported through `Doctor`, via `doctor.Facts`' `OutgoingLimitMiB` and `FailedAttachments` (`store.FailedAttachmentCount`), so the "Outgoing attachments" check's detail reads "over 256 MiB — N failed message(s) waiting" - the one place this whole change lets a count into a doctor detail, which the package doc comment now says is fine where it helps. A later security review found that nothing actually stopped the area growing past that limit in the meantime: `Outgoing.Store` now caps each copy at whatever room is left under the limit (`remaining`/`enforceRoom`) and refuses - `errOutgoingFull` - rather than writing an attachment that would push the area over, since a clipboard paste is content another program handed this helper, not bounded by anything upstream the way a sent photo's own size might otherwise be assumed to be.

## A WhatsApp chat's remote id is chosen once and persisted, not recomputed from whatsmeow's LID mapping every time

This supersedes the parts of "WhatsApp's self-chat always canonicalizes to its phone JID, never its LID" and "Deleting messages: `connector.Deleter`, removal not a tombstone, and WhatsApp's LID mismatch fixed at `chatID`" above that described an ordinary (non-self-chat) chat's id as "the mapped phone form when whatsmeow already knows it, the bare id otherwise": that rule still describes the self-chat correctly (its phone JID is reliably known once paired, so it never needs a stored choice), but for any other chat it was a live-computed guess, not a stable id, and a real account's chat could still split in two.

**The bug.** `chatID` used to call `dev.pnForLID` fresh on every single call and trust whatever it answered at that moment. WhatsApp addresses the same 1:1 chat by phone JID (PN) or by hidden id (LID) depending on which of its own internal paths delivered a given report - history sync, a live message, a receipt, a revoke - and whatsmeow only learns the mapping between a contact's two forms at some point after it starts seeing them, not before. A chat reported by LID before that mapping exists got the bare LID id; the exact same chat reported again later, by LID or by PN, once the mapping had arrived, now resolved differently (to the PN id), creating a second, empty-looking conversation and orphaning everything already stored under the first. The reverse order - PN first, LID later - had the same problem once a LID report arrived expecting the PN id but finding nothing recorded against the bare LID either.

**The fix.** `chatID` (`backend/internal/connector/whatsapp/normalize.go`) now takes the connector's own media store (its sidecar database, alongside message keys and poll state - see "WhatsApp's media references live in their own database" above) and persists, in a new `chat_aliases` table (`chatalias.go`), which remote id a chat was first reported under. On every call it gathers the JID's own remote id and, when whatsmeow's LID store already maps it (`device.altJID`, replacing the one-directional `pnForLID` with whatsmeow's own bidirectional `Store.GetAltJID`), that other form's remote id too, looks both up in `chat_aliases`, and returns whichever canonical id either one already resolves to - or, the first time neither does, records the form this call arrived under as that canonical id, under both aliases if both are already known. Every later call, by either form, after a restart or not, resolves back to the exact same id: a chat never splits, and never needs a re-pair to merge back together, because nothing ever needed merging in the first place. The self-chat keeps its own, simpler rule unchanged (`dev.isSelfChat`/`dev.selfChatID()`, checked first, before any alias lookup): its phone JID is always known once paired, so it has never needed a stored choice.

A connector built with no media store at all (some unit tests) falls back to the old, single-call guess - the mapped phone form when already known, the bare id otherwise - since there is nowhere to persist a choice; this is explicitly not stable across such a connector's own lifetime; every other call path always has a media store.

**Existing accounts need no re-pair.** This is forward-looking, same as the self-chat fix before it: an account that already has a chat split in two from the old bug keeps that split (merging two already-separate conversations correctly would need its own UI and store support, and risks guessing wrong - the same reasoning the self-chat fix gave for not migrating its own stray LID conversation). Going forward, the first report of any chat - under whichever form arrives first - fixes its id for good.

**Per-person ids get a lighter version of the same idea, deliberately not the stored one.** The same mismatch - the same real person reported once by LID, once by their mapped phone JID - also double-counted a reactor in a message's reaction tally, a poll's voter list, and a group's per-participant read tracking, since each of those kept its own sender key by calling `remoteID` on whichever form a given event happened to carry. `personID` (`normalize.go`) is the fix: prefer the mapped phone form when whatsmeow already knows it, the bare id otherwise, with no table of its own to persist a choice, because none is needed here - whatsmeow's own LID-to-phone mapping, once learned, never becomes unknown again, so every call from then on agrees without anything to remember. `live.go`'s `reactorKey` (reaction chips and poll voter ids, via `vote.go`'s `handlePollVote`) and `receipts.go`'s `receipt` (the participant key `advanceSent` tracks a group's slowest member by) both call it now.

`keys.go`'s `senderKeyID` - message_keys.sender_id - deliberately keeps using the bare, as-received form, not `personID`: that value also has to build the exact `Participant` WhatsApp expects when reacting to, replying to or deleting someone else's message in a group (`targetKey`), and whatsmeow's own `BuildMessageKey` builds that field from the sender address exactly as a message's own `MessageSource.Sender` carried it, never a resolved alternative - a group's wire protocol addresses each participant by whichever form that specific group uses, and substituting the other form there risks addressing the wrong thing, or nothing at all, rather than fixing a display-only tally. The same reasoning covers `retrySender` (`retry.go`) and `markReadFrom`'s per-sender grouping (`markread.go`), both of which read `sender_id` back for the same kind of outgoing address, not a display count.

**Deleting a failed message.** `DeleteMessages` previously required a remote id for every message, which a failed send never has - it never reached the service - so there was no way to delete one at all. It now accepts a failed outgoing message with no remote id (`neverReachedService`), skips the connector call for it entirely (nothing to tell a service that was never told), and removes its outgoing copy the same way a confirmed delivery already does (`Commands.removeOutgoingAttachment`, `outgoing.go`). Matching switched from `store.DeleteMessages`'s remote-id lookup to a new `store.DeleteMessagesByID`, since the local ids were already resolved and validated by this point; the old remote-id path stays for `Ingest.Deleted`, which only ever hears a service's own ids.

## `MessageTimeline.loadOlder` drops a stale reply the same way `loadInitial` already did

`loadInitial` already guarded against its `messages.list` reply landing after the conversation it was for had closed or been switched away from, but `loadOlder` (scrolling up for an older page) did not: scrolling up in one conversation, then switching to another before the older page answered, spliced that stale page's messages into whichever conversation was open when the reply arrived, and overwrote its `hasMore`/`historyUnavailable` with the wrong conversation's values. `loadOlder` now takes the same `guard` function `loadInitial` does, checked right before the reply is applied; `ConversationController.loadOlder` passes `() => id === root.activeId`, capturing the open conversation's id when the call starts, exactly as `_setActive`'s own guard for `loadInitial` already does.

## A stale `media.paste` reply is dropped, not kept for the conversation it started in

`ComposerController.pasteImage` asks the helper for the clipboard's image asynchronously; switching to another conversation before the reply lands used to attach the pasted image to whichever conversation was open when the reply arrived, not the one the user was actually pasting into - a privacy leak, since a photo meant for one chat could land in another. The fix captures the open conversation's id when the paste starts and compares it against the open conversation again once the reply arrives, the same guard `MessageTimeline.loadInitial` already uses for a stale `messages.list` page; a mismatch drops the reply outright, on both the success path (the image) and the failure path (the plain-paste fallback), rather than picking one of two more complex alternatives: keying the pending attachment per conversation so the original chat gets it back on return, or re-showing it there some other way. Neither seemed worth the extra state for an action - pasting a clipboard image - that is trivial to redo by switching back and pressing Ctrl+V again, and silently attaching it somewhere once the user has moved on would still be surprising even if that somewhere was technically "correct".

## WhatsApp: drop only protocol messages known to be housekeeping

`isContentless` drops a `ProtocolMessage` only when its type is on an explicit list of housekeeping kinds (key shares, ephemeral settings, app-state sync and the like). Any other type, including ones WhatsApp adds later, is stored with the generic placeholder and logged, so an unrecognised message shows up as something rather than silently leaving its chat empty.

## WhatsApp: a chat first seen through our own message is still created, never named after us

Ingest drops a message for a conversation it was never told about, so the first message this run sees for a chat creates it whichever direction it went. An outgoing message's push and business names are this account's own, so they are never used to title the chat; it gets the contact name or fallback instead.

## WhatsApp: a direct chat's name cache is keyed by its canonical chat id, not whichever address form a report happened to use

Some business or non-contact accounts message almost entirely through their hidden id (LID), with no row in whatsmeow's own contact store for either form. `resolveDirectTitle` used to cache a resolved name, and read `titleFallback`'s input JID, from the bare address form a given report arrived under (`remoteID(jid)`) rather than the chat's stable `chatID`; a report that happened to arrive by LID, even for a chat already known by its mapped phone JID, both missed a name already cached under the phone form and formatted its own fallback as the neutral "Unknown contact" instead of "+number", since `titleFallback` never tried mapping the LID first. Since `store.EnsureConversation` refreshes a conversation's title on every report, whichever form reported last won, so a real name learned under one form could be clobbered by a weaker fallback computed under the other. `resolveDirectTitle` now resolves and caches by `chatID`'s canonical id, and reads its own fallback from the JID's mapped phone form when `device.altJID` already knows one (`phoneFormOf`, also now shared with `personID`); history sync additionally feeds a synced message's own push name (`WebMessageInfo.PushName`) into the same resolution, which it previously never did. An existing chat already mistitled "Unknown contact" fixes itself on the next live message or history sync that carries a name, with no re-pair needed, since nothing about a chat's stored remote id changes - only the title resolved for it.

## A history sync's media reference must be saved from the unwrapped message, not the wrapper WhatsApp stored it in

A real account's log showed `media: fetch failed (service=whatsapp, kind=video, reason=not-found)` for a video the conversation list already showed a thumbnail for: the message arrived through history sync, in a chat with disappearing messages on, so WhatsApp's own `WebMessageInfo` stored it wrapped in `waE2E.EphemeralMessage`. `normalize.go`'s `unwrap` exists exactly to peel that kind of wrapper, and `history.go`'s `syncMessage` already called it, through `historyMessage`, to read the message's own text and media for display - but `syncMessage` then passed its own, still-wrapped `content` to `saveMediaRef` and `savePoll`, not the unwrapped copy `historyMessage` used internally. `mediaAndRef` (`normalize_media.go`) has no case for `EphemeralMessage` itself, so `downloadRef` quietly reported nothing to save, and a later `media.fetch` found no reference at all. `syncMessage` now unwraps `content` once and passes that to both calls, the same copy `historyMessage` would have produced; a live message needs no equivalent fix, since whatsmeow's own event dispatch (`events.Message.UnwrapRaw`) already unwraps it before a connector ever sees it (see `unwrap`'s own doc comment).

Separately, WhatsApp's video notes ("round" videos, `waE2E.Message.PtvMessage`) were never recognised at all: `mediaAndRef`, `contextInfo`, `mediaCaption`, `mediaPlaceholder` and `recognizedContentFields` (`diagnostics.go`) every had a case for `VideoMessage` but none for `PtvMessage`, even though it is the exact same `*waE2E.VideoMessage` type under a different field name. A video note therefore fell to the generic `[Message]` placeholder and saved no download reference either, the same missing-reference symptom as the wrapped case above. Each of those switches now treats `PtvMessage` exactly like `VideoMessage`, since nothing about downloading or showing one differs.

The UI's own "Something went wrong in the helper, try again" message for a failed `media.fetch` already had the machinery to do better - `server/errors.go` already sends the safe reason category in the error's `data.reason`, and `ui/lib/Format.js`'s `mediaFailureReason` already turns it into a phrase used elsewhere for a message's inline "Unavailable" tooltip - but `MediaController.qml`'s `downloadMedia`, when the user actually asked to open the media (`report` true), always fell back to `Rpc.errorText(error)`, the fixed sentence for the error's JSON-RPC code, ignoring that reason entirely. `Format.mediaUnavailableMessage(kind, reason)` now names the kind too, for the three reasons that mean the file is truly gone (`not-found`, `expired`, `decrypt`): "This video is no longer available.", for instance, instead of the generic sentence. A reason worth retrying (`download`, `cache`, `timeout`) still gets the generic text, since claiming the media is gone for good would be wrong there.

## A worn-out media key, not just an expired CDN link, gets a phone retry too

A real account's log showed `whatsapp: media download failed (class=decrypt)` turning into `media: fetch failed (kind=photo, reason=decrypt)` for photos, with no retry ever attempted: `downloadOrRetry` (`fetch.go`) only sent a retry receipt when `isExpiredDownload` matched one of WhatsApp's stale-link statuses (403, 404, 410), and returned a worn-out hash or HMAC straight through `classifyDownloadErr` otherwise. `SendMediaRetryReceipt`'s own doc comment only names 404 and 410 as the case it is "mostly relevant" for, and this connector's own earlier reasoning (see "A 403 is a stale WhatsApp media link too…" above) already noted that `ErrInvalidMediaEncSHA256` and `ErrInvalidMediaHMAC` are checked *before* whatsmeow decrypts anything, so there is no authenticated data a local fallback could ever accept the way `recoverStaleDigest` does for a stale plaintext hash.

What a local fallback cannot do, a fresh answer from the primary phone still can: WhatsApp's own primary device has been observed re-encrypting a file on a retry's re-upload, so the reference this connector saved when the message first arrived can fail even an honest download attempt, while a fresh retry answer's path decrypts cleanly. `downloadOrRetry` now sends a retry receipt for a decrypt failure exactly as it already does for an expired link, rather than giving up at once. `retryDownload` (`retry.go`) takes the original failure as `cause`, so the one case this cannot help - no `message_keys` row saved for the message, so there is no sender to build a retry request from at all - still reports the same category that failure would have had without any retry attempted (`retryUnavailableErr`): a stale link with nothing to retry is still `domain.ErrMediaExpired`, but a decrypt failure stays `domain.ErrMediaDecryptFailed` rather than being misreported as the phone having said the media was gone, which it was never asked about.

## A chat migrated to LID addressing needs its "mark chat as read" patch sent by LID, not its phone JID

A real account's log showed `whatsapp: mark read (receipts=N, senders=1, chat_patch=failed, has_timestamp=true)` on every single `MarkRead` call for one chat, with its per-message read receipts (`markReadFrom`, sent by `dev.markRead`) going through fine. The two take different JIDs down to whatsmeow: a receipt is sent for the `chat` and `sender` `MarkRead` itself resolves fresh from the message, while the app-state "mark chat as read" patch names the chat `chatID` resolved for it, which keeps "whichever remote id it was first reported under for the rest of its life" (see `chatID`'s own doc comment) - a chat's phone JID or its LID, whichever a report first happened to carry. Once an account's identity for a chat has migrated to LID addressing, a plain read receipt to its phone JID still reaches WhatsApp's servers, but the app-state patch, keyed by `[appstate.IndexMarkChatAsRead, target.String()]`, is rejected by the server when `target` is still that chat's now-superseded phone JID, exactly the asymmetry the log line showed.

`sendChatReadState` (`markread.go`) now resolves `chat` through a new `lidFormOf` (`normalize.go`, the mirror of the existing `phoneFormOf`) before building the patch, addressing both the mutation's index and its `MessageKey.RemoteJID` by the chat's LID once whatsmeow's own LID store has learned one, and leaving it unchanged otherwise, so an account that has not migrated sees no change in behaviour. The per-message read receipts `markReadFrom` sends are deliberately left alone: they are not the ones the real account's log showed failing, and whatsmeow's own guidance for a message's `Participant`/sender address (see `keys.go`'s `senderKeyID`) is to use the address exactly as the message carried it, not a resolved alternative.

This was diagnosed, not just worked around: `dev.sendAppState`'s error was previously discarded down to a bare `chat_patch=failed`, which could not tell this cause apart from an account that has simply never finished its post-pairing app-state key sync (`appstate.ErrKeyNotFound`), the server actually rejecting a patch for some other reason (`whatsmeow.ErrAppStateUpdate`), or a timeout. `chatPatchFailureClass` now sorts the error into one of `key`, `rejected`, `timeout` or `other`, logged alongside the existing fields as `chat_patch_error`, so a future report of "still shows unread on the phone" can be checked against which of these it actually was rather than guessing again.

## An overlay with an editable field is destroyed on close, not just hidden

A marketplace maintainer flagged that `Overlays.qml` kept the command palette and account setup instantiated the whole time the window is open, each with a native `TextField` only `visible: false` once closed: on supported Qt versions, an editable `TextInput`-based field reads a foreign Wayland client's clipboard text on every change even while hidden, with no size limit or deadline, so a hidden field left alive is a way to stall or exhaust the shared shell with a streaming clipboard offer before any paste ever happens. The fix wraps each overlay with an editable field (the command palette, account setup, the new-chat dialog) in a `Loader` whose `active` is the same flag that used to drive its `visible` binding, so the field is constructed only while its overlay is open and destroyed, not merely hidden, the moment it closes. Durable state (which step a sign-in is on, the palette's query, the dialog's search text) already lived in the matching controller rather than the view, per `qml.md`'s "never only in a delegate", so closing and reopening still resumes exactly where things were; each view's own `Component.onCompleted` now does the opening focus work its `onOpenChanged`/`onVisibleChanged` handler used to, since a view built fresh by a `Loader` is already open the moment it exists and never sees that property actually change. A hidden overlay with no editable field (the reaction picker, the health check report, the close and delete questions, account removal) does not need this: the report was specifically about a `TextInput`-based field reading the clipboard, not about an overlay existing off-screen in general.

## Spell check: one bundled English dictionary, loaded lazily, gospell over cgo-based spellers

The composer's spell check needed a Hunspell-compatible checker that stays `CGO_ENABLED=0` (the helper is a static, cross-compiled binary) and a dictionary that ships inside it, since nothing downloads on plugin load (see "Release binaries, installed automatically on first open" above) and the helper has no network access beyond the messaging services.

- **Engine: `github.com/client9/gospell`.** It is pure Go, MIT-licensed, and reads Hunspell `.aff`/`.dic` files directly from `io.Reader`s, so the bundled dictionaries never touch disk at runtime. The alternatives either wrap a C spell checker (hunspell itself, requiring cgo) or ship their own smaller word list with weaker affix handling.
- **English only, one dictionary at a time.** Bundling every language Hunspell supports would multiply both the binary size and the `THIRD_PARTY_NOTICES` surface for a feature nobody asked for beyond English; British and American are the two spellings OmaMessenger's users actually write in. `spell.chooseLocale` picks between them from the `spellLanguage` setting or, on "auto", the `LC_MESSAGES`/`LANG` locale environment, so most people never have to choose.
- **SCOWL size 60, by way of en-wl/wordlist's Hunspell release.** SCOWL's size-60 cut is the same one most Linux distributions ship as their default `en_GB`/`en_US` Hunspell dictionaries: large enough for ordinary writing, small enough that the gzip-compressed `.aff`/`.dic` pair embeds at about 180 KB each (`backend/internal/spell/dictdata/*.gz`, decompressed at load time). Three licenses apply to that data - SCOWL itself (Kevin Atkinson), the Hunspell affix file (derived from Geoff Kuenning's Ispell), and WordNet, one of SCOWL's own sources - reproduced verbatim in `backend/internal/spell/dictdata/NOTICE.txt` and folded into `scripts/third-party-notices.tmpl`, alongside whatever `go-licenses` finds for `gospell` itself (MIT, found automatically).
- **Memory: lazy load, one dictionary at a time, released when off.** A loaded dictionary costs tens of megabytes (gospell indexes the word list for suggestions on top of the raw data), which is wasted entirely for someone who never touches the composer or who turns spell check off. `spell.Checker` loads nothing until the first `Check`, `Suggest` or `AddWord` call, keeps only whichever locale is currently in use, and drops it the moment `SetEnabled(false)` runs; switching `SetLanguage` away from the loaded locale drops it too; a word added through `AddWord` is merged into the live dictionary at once and appended to a personal word list under `$XDG_DATA_HOME/omamessenger/spelling/<locale>.txt`, read back in on the next load.
- **Skip rules live in Go, not `ui/lib`.** `spell.candidates` (`tokenize.go`) decides what counts as a checkable word - skipping a URL, an `@mention`, an email address, a run containing a digit, and a backtick code span - entirely on the backend, so there is exactly one implementation of the rule rather than a UI copy that could drift from it; the UTF-16 offsets it reports use the same convention `domain.Mention` already does, so the composer needs no unit conversion either.

## Spell check: suggestions and the picker are a round trip; "Ignore" and underline drawing are not

`ComposerController` owns the `spell.check`/`spell.suggest`/`spell.addWord` round trip and the `spellMisspellings`/`spellSuggestions` state Composer.qml renders from, debounced the same way `WindowController.messageSearchTimer` debounces the palette's message search. `Composer.qml` itself stays a pure view - it takes `misspellings` and `suggestions` as properties and reports intent through `spellSuggestionsRequested`/`spellWordAdded` signals, never calling the helper directly (see `qml.md`) - except for two decisions that are purely local and never need a round trip at all: which flagged word the caret or a click is inside of (`ui/lib/SpellCheck.js`, pure), and "Ignore", which only ever filters the composer's own `_ignoredWords` for this session and is deliberately never told to the helper or saved anywhere. The underline overlay recomputes from `TextArea.positionToRectangle`, deferred with `Qt.callLater` since the text layout is not settled in the same tick a text, caret or misspellings change arrives in, and draws two rectangles instead of one for a range that wraps across a line break.

## The helper-error banner is a transient notice, not sticky state

Panel used to show a bare `||` chain of six controllers' `lastError` with no way to dismiss it and nothing that ever cleared it, so one failed request left a red line at the top of the window permanently. `WindowController.errorBannerText` now merges the same six sources through `ErrorBanner.pick` (`ui/lib/ErrorBanner.js`), and `dismissErrorBanner()` clears all of them at once; it is called by a six-second timer (restarted on every new error, its interval a property so tests can shrink it), by the banner's own click target, by `Navigation.escapeAction`'s new top-priority `"dismiss-error"` step, and by two `Connections` blocks that treat the open conversation changing (`conversationController.activeId`) and the helper's own status changing (`service.status`) as fresh starts. Each of the six sources also clears itself on the next successful reply, rather than only on the next failure overwriting it. The status-change clear exists because `RpcClient.cancelPending`'s own housekeeping failure ("The helper restarted.", code 0) landed in `ListController.lastError` during the installFailed flow in `tests/qml/Install`, and with Escape now dismissing a visible error before anything else, that stale, already-irrelevant notice ate the Escape press meant to open the close question; clearing on any status change drops it before it can do that, and generalizes to every other status transition for the same reason the conversation-change clear does. Escape dismissing the banner first, alone, is deliberate: a user escaping out of whatever they were doing should not also lose that context just because an unrelated request happened to fail first.

## Incognito audit: nothing to add, so nothing was added

A request for a full "incognito mode" asked whether turning read receipts off (see "Incognito read receipts" above) also needed to stop typing indicators, online/presence updates and voice-note "played" receipts, each a distinct signal WhatsApp and Telegram support sending. Auditing both connectors (`whatsapp/device.go`'s `device` interface, `telegram/connector.go`'s `MarkRead`) found that none of the three are ever sent by either one in the first place: there is no code path that reports this account composing a reply, no call to either service's presence/online API, and no call to WhatsApp's played-receipt type or Telegram's `messages.readMessageContents`. `Settings.ReadReceipts` already gates the one signal that does exist (`Dispatcher.MarkRead`) from a single place in the app layer, reached by both connectors through `connector.Manager`.

Given that, two things were deliberately not done. First, no new connector capability was added to send typing, presence or played signals just so `ReadReceipts` could then gate it: the issue asked for those signals to be hidden, not for them to be built. Second, the "Read receipts" label was not renamed to "Incognito": the condition for renaming it was that the setting cover everything a true incognito mode would need to, which the audit found it already does, but the setting's key (`readReceipts`, in the protocol and in `manifest.json`) stays as it is regardless, and a label rename across the UI, its tests and the docs was judged not worth the churn for a change with no behavioural effect. What the audit did produce: `TestMarkRead_SendsNoOtherSignal` in both `backend/internal/connector/whatsapp` and `backend/internal/connector/telegram`, asserting the complete, exact set of calls `MarkRead` makes, so a future change that adds one of these signals outside the existing gate fails a test rather than shipping silently; and the full writeup in `docs/privacy.md`'s "Reading and replying without the sender being told", including what this mode structurally cannot hide (being connected at all can surface "online" or "last seen" through WhatsApp's or Telegram's own protocol; sending a reply is itself activity the other side sees).

## Message formatting spans: Telegram's own entities, WhatsApp's markers left for later

Telegram reports a message's bold, italic, links and the rest as a separate list of `MessageEntity` spans over the text, with UTF-16 offsets - structured data a connector can read with no ambiguity, the same shape `domain.Mention` already used for `@name` tokens. `domain.Span` (`backend/internal/domain/formatting.go`) generalizes that to `{kind, start, end, url}`, persisted and carried through the protocol as `Message.Formatting`, the same JSON-in-a-column pattern mentions already use (see `store/formatting.go`, `store/mentions.go`).

WhatsApp sends no such structured data: `*bold*`, `_italic_`, `~strike~` and `` ```mono``` `` are literally part of the message text its clients render, with no offsets or entity list at all - the connector would have to parse those markers back out of plain text itself, deciding where a pair of asterisks is really meant as emphasis versus someone's literal "*" in prose (a price, a footnote marker, an emoticon), a judgment call Telegram's own structured entities never require. That parsing was judged not cheap enough to fold into this change, so WhatsApp messages keep showing those markers as plain, literal characters for now; `docs/api.md` says so next to `formatting`'s own description.

## `MediaController.downloadMedia` queues every caller for an in-flight fetch, rather than letting a second one silently drop

`tests/qml/VoicePlayback`, the one test that drives a real voice note end to end, failed intermittently in CI with the play button stuck on "▶" forever, even though the note had genuinely downloaded (its path was already known). Lengthening the fake connector's placeholder clip from a third of a second to three seconds (see `backend/internal/connector/fake/voice.go`'s own doc comment) did not fix it, because that was never the race: `VoiceNotePlayer.Component.onCompleted` fires `wanted()` - a silent prefetch, `ConversationController.fetchMedia` with `done: () => {}` - the moment the bubble becomes visible, and the test's own Enter keypress reaches `openMedia` right after, often before that prefetch's `media.fetch` round trip has answered. `MediaController.downloadMedia`'s de-duplication guard (`if (root._fetching[id]) return;`) was a bare flag: a second caller for the same id while one was already in flight returned immediately, discarding its own `done` callback entirely rather than ever running it. The prefetch's `done` was always the inert no-op, so the open that arrived during its window never started playback, and nothing short of a second, later click (outside the race) ever would. Reproducing this needed no voice note or real player at all: `tests/qml/MediaController`'s own scripted service shows the same drop with a plain video, calling `fetchMedia` then `openMedia` for an undownloaded id before answering the one `media.fetch` either triggered.

`_fetching[id]` now holds every waiter still owed an answer (`{report, done}`), not just a flag; the one request's callback runs every waiter's `done` on success, or tells every waiter that asked to be told (`report: true`) the same failure once, rather than overwriting one caller's sentence with another's. This is a general fix at the one place every media path shares, not a voice-specific patch: a photo's own thumbnail prefetch racing its own open would have hit exactly the same drop. The three-second clip stays; it still guards the real, separate risk it was added for (a very short clip finishing between two of the test's own 100 ms polls), and shrinking it back now that the actual bug is fixed would only reintroduce that risk for no benefit.

`make test-qml`'s failure output changed alongside this: a failing test used to print only its log's own `FAIL`/`ERROR` lines, which showed `VoicePlayback`'s own assertion but nothing from Qt or QtMultimedia underneath it. It now prints the whole log (still with `qt.qpa` noise filtered), since a future flake under the real player may need exactly the surrounding lines this one did not.

## Editing your own sent messages: store first, service second, mentions carried as-is

`Commands.EditMessage` (`backend/internal/app/edit.go`) updates the stored message before telling the connector, then reverts that same update if the connector refuses, rather than waiting for the service to confirm first: the UI should show an edit as soon as it is asked for, the same instant `Send` already shows a new message as pending before the service has answered. The revert reuses `store.EditMessage`, the same call `Ingest.Edited` applies for the service's own echo, so a slow echo of an edit that already landed is a no-op, not a second change - both paths key off the same remote id. One known rough edge from reusing that call for a revert: `store.EditMessage` always marks a message `edited`, so a reverted failed edit leaves that flag set even though no edit actually took effect; narrower than this change was worth fixing, since `EditMessage` already existed for a different purpose (recording a confirmed change) and a dedicated revert path would only exist for this one rare case.

Only an outgoing, text-only message that already has a remote id can be edited (`editable`, same file) - a connector only ever needs to reapply the message's own already-known `Mentions` field, not a freshly chosen set the UI would have to resolve all over again: editing changes words, not who is mentioned, so `messages.edit`'s own params are deliberately just `{conversationId, messageId, text}`, with no `mentions` field to keep in sync with the composer's own token tracking.

The WhatsApp and Telegram connectors (`connector/whatsapp/edit.go`, `connector/telegram/edit.go`) both implement the new optional `connector.MessageEditor` capability, following `Deleter`'s own shape: a `ErrNoEditor`/`ErrEditUnsupported` pair the `app` layer maps to a safe, invalid-input message, never a raw connector error. WhatsApp additionally checks `whatsmeow.EditWindow` and the saved message key's `fromMe` flag itself, the same two checks `DeleteMessages`' own revoke path already makes for the same reason: only this account's own, not-too-old message can be changed, and WhatsApp's server would reject anything else anyway, but a clear `ErrEditUnsupported` here is more useful than its raw error.

The UI reaches editing two ways - `E` on a highlighted message, or `Up` in an empty composer (`compose.editLast`) - both funnelled through `ComposerController.startEdit`, which loads the message's text into the existing draft rather than a separate field, the same way a reply never duplicates its own text storage. Which message counts as "editable" and whether `Up` should mean edit at all is `ui/lib/Edit.js`'s decision, proven in `tests/unit/edit.test.cjs`; the controller only wires that decision into reactive state, proven in `tests/qml/ComposerController`.

`backend/internal/app/helpers_test.go` was already close to the 400-line gate `file-length-limit` enforces; adding `fakeEditor` alongside the other connector-capability fakes would have pushed it over on its own. Rather than trim unrelated code to make room, those fakes (`fakeRefresher`, `fakeOrganizer`, `fakeMemberLister`, `fakeReactor`, `fakeVoter`, `fakeDeleter`, `fakeEditor`) moved to a new `connector_fakes_test.go`, the same reasoning that split `outgoing.go` from `ingest.go` above: a shared test-helpers file is still one file in spirit, split by what it holds once it outgrows the gate, not a dumping ground for whatever last needed room.

## Multiple accounts of the same service already worked; what was actually missing was telling them apart

Investigating issue #12 found nothing to fix: every layer is already keyed by account id, never by service - `connector.Manager.byAccount`, the store's `accounts`/`conversations`/`contacts` tables (`UNIQUE(account_id, remote_id)`, not `remote_id` alone), and each connector's own session and media files (`whatsapp/device.go`'s `sessionPath(dir, accountID)`, `telegram/credentials.go`'s equivalents). Two Telegram accounts (`tg-personal`, `tg-work`) already ship in the fake fixture (`backend/internal/connector/fake/scripts.go`) for exactly this reason, and the rail (`ui/lib/Rail.js`) already splits a service into one entry per account once it has more than one. `docs/decisions.md` had no entry for this because nothing was ever decided to make it work; it was a consequence of keying everything by account id from the start. What issue #12 was actually missing is proof: `backend/internal/store/conversations_test.go`'s `TestEnsureConversation_KeepsTwoAccountsOfTheSameServiceIndependent`, `backend/accounts_test.go`'s `TestAccountRegistry_AddsTwoAccountsOfTheSameServiceIndependently` and `backend/internal/app/scenario_test.go`'s four `TestTwoAccounts_*` tests now cover it end to end, through the real fake connectors, so a future change that breaks this isolation fails a test rather than shipping silently.

The one real gap was that two accounts of the same service look identical once signed in: both just say "WhatsApp". `Account.Alias` (`backend/internal/domain/domain.go`), set through the additive `accounts.setAlias` method, is deliberately a separate field from `Account.Name` rather than letting the user edit `Name` directly: `Name` is what the provider gave the account (so far always the service's own display name), and losing that original value - for support, for debugging, for "what did this say before I touched it" - seemed worse than the one extra field. Every place that shows an account's name - `Rail.displayName`, `accountLabel`, `accountDescription`, `accountNames`, `accountEntries`, and the conversation header's new `Rail.accountSuffix` - falls back to `Name` through the one shared helper rather than each repeating `alias || name`, so a future caller cannot forget the fallback. `accountSuffix` only names an account once its service has more than one, matching `multiAccountServices`' own threshold and keeping a single-account service's header exactly as quiet as it was before.

## Blocking a contact and reporting spam

`connector.Blocker` and `connector.SpamReporter` (`connector/connector.go`) are two separate optional capabilities rather than one, because a service can offer one without the other: Telegram's `contacts.block`/`contacts.unblock` and `messages.reportSpam` map directly onto both, but whatsmeow's WhatsApp client exposes only `UpdateBlocklist` - there is no spam report of its own to call. `connector/whatsapp/block.go` implements `Blocker` alone; `connector/telegram/block.go` implements both. `connector.Manager.SetBlocked` fails with `ErrNoBlocker` when the underlying connector has none, the same shape as `Deleter`/`Editor`, since reporting a block the service never made would mislead the user; `Manager.ReportSpam` instead no-ops when there is no `SpamReporter`, the same shape as `Organizer`'s optional methods, since `app.Commands.ReportSpam` always blocks and hides locally regardless of whether the service had anything of its own to report.

`app.Commands.BlockContact` asks the connector first and only writes the conversation's `blocked` column once that call has succeeded, rather than the local-first, best-effort shape `SetPinned`/`SetArchived` use: a block is the one point of this feature, so a local flag with nothing actually blocked on the service would be actively misleading, unlike a pin or archive that is still useful purely locally if the service call fails.

`ReportSpam` hides the conversation (`store.SetHidden`) rather than archiving it. Archived is one of the two fields a service's own dialog sync can overwrite through `Ingest.Organized` (see `connector/whatsapp/organize.go`'s own doc comment on why that sync is the single source of truth); nothing here ever reports this archive to the service for that sync to agree with, so a later full resync could silently un-archive a chat the user asked to get rid of. `hidden`, like a reminder, is never touched by anything but the user's own request, so it cannot be reverted out from under them the same way.

Both `BlockContact` and `ReportSpam` refuse a group with `ErrInvalidInput`: a group has no single contact to block, and the official apps offer neither action there either. Leaving or reporting a group is out of scope for this change.

## Untrusted images are sanitized in the helper, never trusted as received

A marketplace review found that a sticker's embedded PNG thumbnail reached `StickerView.qml`'s `Image` unchanged: Qt's own PNG reader still inflates a `zTXt`/`iTXt`/`iCCP` chunk's zlib stream to draw nothing from, so a compressed-metadata bomb runs on the strength of a chunk the UI never reads, and a declared width or height in the tens of thousands makes Qt allocate the matching bitmap before anything checks whether the file is even that big. Every path that can put a sender's bytes in front of a QML `Image` or `AnimatedImage` has the same two risks: a message's embedded preview (WhatsApp's JPEG/PNG thumbnail, Telegram's own compact "stripped" encoding), a downloaded photo, a downloaded sticker (always WebP, animated or not), and a document that turns out to be a real GIF file rather than a video merely marked to play like one (see "A video's actual bytes decide whether it animates as a GIF, never its filename or attributes" below, which replaced the filename-based check this paragraph originally described). A full video is not one of these: QtMultimedia decodes it, not Qt's own image plugins, a different decoder with a different risk profile - see "A video's own container and stream headers are validated before anything plays in-window" below for how that risk is now closed too.

`backend/internal/imagesafe` is the one place that risk is closed, on the helper side rather than in QML, because the helper is where the untrusted bytes first exist as a parsed structure at all - the UI only ever sees a file path or a base64 string, already too late to tell a stripped chunk from a kept one. `Sanitize(data, profile)` checks the format by its own magic bytes, never a sender's claimed mimetype, and rejects anything that is not PNG, JPEG, GIF or WebP outright: an unrecognized format is shown as a file, never forwarded as if it were an image. For the three formats with a real chunk or segment structure (PNG, JPEG, GIF), it rewrites the byte stream keeping only what rendering needs - PNG's `IHDR`/`PLTE`/`IDAT`/`IEND`/`tRNS`/`gAMA`/`cHRM`/`sRGB`/`pHYs` and APNG's `acTL`/`fcTL`/`fdAT`, dropping `zTXt`/`iTXt`/`tEXt`/`iCCP`/`eXIf` and everything else; JPEG's start-of-frame, table and scan markers plus plain `APP0`/JFIF, dropping every other `APPn` (EXIF, an ICC profile, Photoshop data, Adobe's colour-transform marker) and `COM`; GIF's Graphics Control extension and the Netscape looping Application extension, dropping Comment and Plain Text extensions and any other Application extension, which is exactly where a GIF can smuggle an arbitrary packet (an embedded XMP block, for one). WebP has no chunk CRCs to validate structurally the same way, so its RIFF container is walked and rebuilt the same way, dropping `ICCP`/`EXIF`/`XMP` and clearing the matching flag bits in an extended file's `VP8X` chunk so it no longer promises a chunk that is no longer there. Every chunk or segment that is kept is copied byte for byte; nothing here resizes or re-encodes a single pixel, so a legitimate image decodes to the exact same picture afterward.

Before any of that, and cheaply, `Sanitize` reads the declared width and height straight off the format's own header - PNG's `IHDR`, JPEG's first start-of-frame segment, GIF's logical screen descriptor and each frame's own image descriptor, WebP's `VP8X` chunk or, lacking one, its `VP8`/`VP8L` bitstream header - and rejects anything over the caller's `Profile`. Two profiles cover every case: `Thumbnail` (1024 px per side, 1024×1024 pixels, 2 MiB of input) for a message's embedded preview and a downloaded sticker, both always drawn small; `FullImage` (8192 px per side, 40 megapixels, 32 MiB of input) for a downloaded photo and a document that turns out to be a real GIF, both generous enough for anything a phone camera or a genuine animation produces but far short of the gigabyte-scale bitmap a crafted header can otherwise demand. An animated GIF or WebP additionally caps its frame count (1024) so a file built from many tiny frames cannot make the walk itself, rather than any one frame's decode, the expensive part. After rebuilding PNG, JPEG or GIF, `Sanitize` runs a cheap `image.DecodeConfig` over the result and confirms it reports the same dimensions already found: a confirmation that the rewritten stream is still well-formed, not a full pixel decode, since nothing here needs to re-verify compressed data its own chunk or segment framing (CRC-checked for PNG, length-checked for JPEG and GIF) already accounted for. WebP has no such confirmation decode available at all - Go's standard library has no WebP decoder - so its correctness rests entirely on the RIFF and bitstream headers being read correctly, which is covered by hand-built fixtures and a fuzz target instead.

Every connector path that writes a photo, sticker or real-GIF document to disk goes through `connector.SaveImageMedia`, never a raw `os.WriteFile`: WhatsApp's `fetch.go` and Telegram's `fetch.go` each decide the right `imagesafe.Profile` from the media kind they already know (`whatsapp/normalize_media.go`'s `imageProfile`, `telegram/media.go`'s `imageProfile`/`documentImageProfile`) and call the shared saver; everything else - a video, a voice note, an ordinary document - goes through the unchanged `connector.SaveMedia` instead, since none of it is ever loaded as an image and sanitizing it would cost without protecting anything. Telegram's non-image download still streams straight to disk rather than buffering first, the one function `backend/internal/connector/media_test.go`'s static guard test allows a raw file write in at all: a large video buffered fully in memory just to call a generic writer would cost real memory for a kind that was never at risk. `whatsapp/normalize_media.go`'s `thumb` and `telegram/media.go`'s `strippedThumb` run the same `Sanitize` call over a message's embedded preview before it is ever base64-encoded into `domain.Media.Thumb`, returning "" - the same as if the sender had sent none - rather than the raw bytes, when the check fails.

QML keeps a second, independent layer: every `Image` or `AnimatedImage` that can show received content (`PhotoView`, `PhotoViewer`, `StickerView`, `LinkPreview`'s thumbnail, `InlineVideo`'s thumbnail and real-GIF player, `FullVideoPlayer`'s real-GIF player) sets a bounded `sourceSize`, tied to the component's own box rather than the file's declared size, so Qt never allocates a bitmap larger than what is actually drawn even for a file that somehow reached it unsanitized. `tests/unit/bounded-image-source.test.cjs` guards this statically, the same way `no-bare-color.test.cjs` guards the `Color` singleton. One component is deliberately left alone: `AccountSetup`'s QR code shows a value this UI generated itself, never a sender's or another program's bytes. `Composer`'s own outgoing-attachment preview used to share that exemption, on the reasoning that it only ever showed a file the user picked; a later review pointed out that one of those files is a clipboard paste, content another program put there, so it is checked and bounded (`Style.space(32)`) like any other image instead.

Why the helper and not QML alone: Qt's `Image` has no hook to inspect or rewrite a file's chunks before decoding it, only `sourceSize` to bound the result after decoding has already started, so the compressed-metadata class of bomb - the one this review actually found - can only be stopped before the bytes ever reach Qt at all. The two layers are deliberately redundant rather than either one alone: `imagesafe` is the real fix, proven byte-for-byte against crafted PNG, JPEG, GIF and WebP fixtures and fuzzed for parser crashes; `sourceSize` is cheap insurance against anything that turns out to need sanitizing that is not loaded through this package's one audited path yet, such as a future media kind.

## A declared media size is checked before downloading, not only after it is already in memory

A follow-up review found the cap `imagesafe.Sanitize` applies to a downloaded photo, sticker or GIF ran too late to matter for memory: Telegram's `downloadImage` (`connector/telegram/fetch.go`) buffered a download fully into a `bytes.Buffer` before `connector.SaveImageMedia` ever checked its length, and WhatsApp's `FetchMedia` (`connector/whatsapp/fetch.go`) handed whatsmeow's `DownloadMediaWithPath` - which also returns a whole file in one piece - no size check at all. Both now check the sender's own declared size against the matching `imagesafe.Profile`'s `MaxInputLen` first, refusing (`errMediaTooLarge`, a permanent failure neither connector retries) before asking the service for anything at all when the declared size already exceeds it.

Telegram's own downloader exposes no `io.Reader` to wrap in an `io.LimitReader`, only a `Stream(ctx, io.Writer)`; `boundedBuffer` is the writer-side equivalent, failing once more than `MaxInputLen` bytes have actually arrived, so a sender who understated the declared size cannot still make this connector hold an unbounded amount in memory. WhatsApp's whatsmeow client has no streaming download at all to bound the same way - `DownloadMediaWithPath` already returns the whole decrypted file before this connector sees any of it - so the backstop there stays `imagesafe.Sanitize`'s own existing length check on whatever whatsmeow handed back; the declared-size check at least avoids that cost for the common case of a sender's size being honest. Both connectors also now bound the download itself with `context.WithTimeout` (`fetchTimeout`, two minutes, already how WhatsApp's connector behaved; Telegram's is new), so a stalled transfer cannot leave `FetchMedia` waiting forever either.

## A pasted or outgoing image is capped and sanitized the same way a downloaded one is

The same review that found the declared-size gap above found two more paths trusting a size too late. `clipboard.Wayland.Read` buffered `wl-paste`'s entire stdout before anything checked it; `MaxPasteLen` (32 MiB, the same cap as `imagesafe.FullImage`) is now enforced by a bounded `io.Writer` on `cmd.Stdout` itself, for the same reason `boundedBuffer` exists above. `app.PasteImage` now also runs a pasted image through `connector.SanitizeOutgoingImage` (new, wrapping `imagesafe.Sanitize` with the full-image profile) before handing it to `cache.Outgoing.Store`: a paste is bytes from whichever other program last owned the clipboard, never trusted further than a sender's own attachment. `connector/whatsapp/upload.go`'s `jpegThumbnail`, which builds an outgoing photo's own preview, now calls `image.DecodeConfig` and checks the declared dimensions against `imagesafe.FullImage`'s own caps before ever calling `image.Decode`, the full decode that would otherwise allocate a bitmap that size.

`cache.Outgoing.Store` now enforces the outgoing media area's own size limit rather than only reporting it (see "Failed sends heal themselves" above), and `Composer`'s own outgoing-attachment preview is no longer exempt from the bounded-`sourceSize` check (see "Untrusted images are sanitized" above): both were previously treated as this machine's own content, overlooking that a clipboard paste is not. Bounding `sourceSize` here was correct to do but was wrongly treated as having closed the gap by itself: Qt's PNG, GIF and BMP decoders still decode a file at the size its own header declares before `sourceSize` ever gets to scale the result down, so a crafted file reaches the same unbounded allocation `sourceSize` was meant to prevent. A later review found this still open for a file picked from disk rather than pasted, which this paragraph did not cover at all; see "A composer's attachment preview only shows a file the helper has already sanitized, never guessed from its extension" below for the fix that actually closes it, for both.

## Every download is size-capped and deadline-bound, not only a photo or sticker

A further review found the discipline "A declared media size is checked before downloading" (above) gave a photo, sticker or real GIF file still left every other download - a video, a plain file, a voice note - completely unbounded, and found the one path that mattered most: a video the sending service marks to autoplay like a silent "GIF" (WhatsApp's `gifPlayback`, Telegram's `DocumentAttributeAnimated`) is fetched by the UI the instant its bubble is shown, with no click from the user at all. That flag is entirely sender-controlled, so a hostile sender could already make every reader of a conversation download something large before anyone asked for anything.

`media.fetch` now takes an optional `auto` param (`backend/internal/server/methods.go`'s `mediaFetchParams`), additive and defaulting to `false` so an older UI is unaffected; the UI sets it only for `InlineVideo`'s own animated-autoplay fetch (`MediaController.fetchMedia`, via `Media.isAnimated`), never for a deliberate click. `connector.MaxBytes(auto)` (`backend/internal/connector/limits.go`) picks the hard cap that applies: `AutoFetchMaxBytes` (16 MiB) for that one automatic case, generous for the short, silent clips a service actually marks this way (most are well under a MiB) while bounding what a sender can make happen with no click at all; `MaxUserFetchBytes` (2 GiB) for everything else, generous for any ordinary attachment - both services already cap a single upload well under that - while still bounding memory and disk against a hostile or corrupted reference. `connector.ByteCap(declared, max)` narrows further to the sender's own declared size plus a 1 MiB tolerance, so a declared count that is accurate but rounded is never refused for undershooting by a few bytes, while a stream that keeps growing past that is still refused well before the hard cap. A photo, sticker or real GIF file is unaffected by any of this: it already goes through `imagesafe`'s own, stricter profile regardless of `auto`.

Both connectors now apply the same three checks to a video, file or voice note that a photo already got: refuse a declared size over the limit before asking the service for anything, cap the bytes actually received at `ByteCap` (via the new `connector.BoundedWriter`, wrapping Telegram's existing chunked `Stream` call, and a new `boundedFile` wrapping WhatsApp's destination file the same way), and bound the attempt with a deadline. The deadline is `connector.IdleContext`: an idle timeout (30 s) for a user-requested download large enough to stream to disk, preferred over a single flat one so a slow but steadily arriving large file is not cut off just because it takes longer than a small one would, plus an absolute ceiling (10 minutes) regardless; an automatic fetch keeps the flat `fetchTimeout` (2 minutes) it already had, since `AutoFetchMaxBytes` keeps those quick either way. An idle-triggered cancellation reports `context.Canceled`, not `context.DeadlineExceeded` - Go's own context package reserves that for a deadline actually elapsing on its own timer - which is why `app.fetchFailureReason` already treated both the same way, as a timeout, before this change; a new `too-large` reason (wrapping the shared `connector.ErrMediaTooLarge`) now reports the size-cap case on its own, rather than falling into the generic `download` reason.

WhatsApp's `DownloadMediaWithPath` returns a video or file's whole decrypted contents in one piece, which is exactly the whole-in-memory download the review asked to stop using above a size threshold. Checking whatsmeow (`go.mau.fi/whatsmeow`) found it does offer a streaming alternative: `DownloadMediaWithPathToFile`, which copies ciphertext to a destination `File` (an `io.Reader`/`Writer`/`Seeker`/`ReaderAt`/`WriterAt`/`Truncate`/`Stat` surface `*os.File` already satisfies) as it arrives and decrypts it in place there, never holding more than one chunk in memory regardless of file size. `fetch_stream.go`'s `streamOnce` uses it for every kind but a photo, sticker or real GIF file (which stay on the existing in-memory path, already small and bounded by `imagesafe`), wrapping the destination in `boundedFile` so a declared size that undersold what the server actually sends is still caught; `download_file.go` holds the thin real adapter. The primary-phone retry an expired CDN link already triggered (`retry.go`) got a parallel streamed counterpart, `retryStreamedDownload`, sharing the same `refreshRef` the in-memory retry already used.

The media cache's own directory limit (`mediaCacheLimit`, 1 GiB, `main.go`) is a separate, older bound on total disk use across every cached file, not a per-file one; `MaxUserFetchBytes` alone could let a single file exceed it. `cache.Cache.Fetch` now rejects a just-fetched file whose own size alone already exceeds the cache's limit (`ErrTooLargeForCache`), removing it rather than keeping it: `prune`'s own rule of never dropping the file it was just asked to keep means such a file could otherwise never be brought back under the limit no matter how much else was evicted. Keeping it only until nothing has it open was the other option the review named, but this cache keeps no reference count of open files at all, and refusing outright is simpler and no less safe; the accepted tradeoff is that a legitimate file near the 2 GiB user cap, well over the 1 GiB cache target, is refused rather than cached - if that turns out to matter in practice, raising `mediaCacheLimit` is the fix, not reference counting. `app.fetchFailureReason` reports this the same `too-large` way as the connector-level cap, so the UI shows one consistent reason regardless of which layer actually refused it.

## Desktop notifications are capped: a bounded number in flight, and a bounded title and body

A review found `notify.Desktop.Notify` opened a new goroutine and a new session-bus connection for every notifying message, each living up to `notifyTimeout` (5 minutes) if nothing ever closed the notification, with no limit on how many could be open at once - a burst of incoming messages (reconnecting after being offline, say) could open an unbounded number of both. The title and body it passed to `Bus.Show` were also unbounded: a sender fully controls a message's own text, which becomes the body.

Reusing one bus connection across every notification was the other option the review named, but `Desktop` is used as a value type across the package (`var _ app.Notifier = notify.Desktop{}`, test literals), and durably sharing a connection would need it to hold state that outlives any one call - the simpler fix, and the one the review offered as an alternative, was a concurrency cap. `Desktop.acquire`/`release` (`backend/internal/notify/notify.go`) add a semaphore, `MaxConcurrentNotifications` (8) deep, created lazily on first use since `Desktop` is still often constructed as a bare struct literal; `Notify` acquires a slot synchronously, before spawning anything, and simply drops the notification if none is free, rather than queuing it - a notification is a transient hint, never something worth making a later one wait behind. Lazy, mutable, per-instance state means `Notify` needed a pointer receiver to persist it across calls (a value-receiver copy would otherwise create a fresh, always-empty semaphore every time); `Desktop` is now always used as `*Desktop`, in `main.go` and throughout its own tests.

`truncateRunes(s, max)` cuts `title` and `body` to `maxTitleRunes` (200) and `maxBodyRunes` (2000) - generous for any real conversation name or message preview, since Omarchy's own daemon already wraps long text on screen - converting to `[]rune` first so the cut always falls on a rune boundary rather than splitting a multi-byte character into invalid UTF-8. This runs in `Notify`, before `escapeBody`, so a long message is cut down first and the three markup characters are then escaped in whatever remains, never the other way around.

## A notification body is escaped before it reaches the notification server

Omarchy's own notification daemon advertises the freedesktop "body-markup" capability, hyperlinks included, and renders a shown notification's body as `StyledText`. `notify.Desktop.run` passed a message's own text straight through to `Bus.Show` as that body, so text that happened to contain `<a href=...>` or `<b>` would be rendered as markup rather than shown as the words it actually was. `escapeBody` (`backend/internal/notify/notify.go`) replaces `&`, `<` and `>` with their entity forms - the only three characters the body-markup subset of the spec treats as significant - once, in `run`, so every caller of `Notify` (an arriving message, a snoozed reminder) is covered without each one remembering to escape its own text. The title (summary) is left unescaped: the notification spec requires a server show it as plain text, with no markup interpreted at all, so escaping it would only turn a literal `&` into a visible `&amp;` for no safety benefit.

## A video's actual bytes decide whether it animates as a GIF, never its filename or attributes

A review found a Telegram document could carry both `DocumentAttributeVideo` and `DocumentAttributeAnimated` together with a sender-chosen name ending ".gif". `documentMedia` (`backend/internal/connector/telegram/media.go`) checked `d.video` before `isGIFImage` in its dispatch, so such a document reached the UI as `MediaVideo` with `Animated: true` and that filename - exactly the shape `domain.Media.IsGIFFile` and `ui/lib/Media.js`'s `isGifFile` used to decide a video should decode through `AnimatedImage` rather than QtMultimedia - while `documentImageProfile`'s own `case d.video` skipped `imagesafe` entirely, since Telegram's "send as animation" ordinarily really is a silent mp4. A sender who set both attributes but sent an actual GIF, or anything else, as the bytes got them written to disk unsanitized and then decoded by Qt's image plugins as if they had passed the same check every other image on this UI goes through.

The fix moves the decision from declared metadata to the file's own bytes, checked once downloaded, in one place both connectors share: `connector.SanitizeIfGIF` (`backend/internal/connector/media.go`) reads a file's first bytes and, only when they are a genuine GIF header ("GIF8"), reads the whole thing, sanitizes it through `imagesafe.FullImage` in place, and reports true; anything else - including a file already too large to be a plausible GIF under that profile, refused rather than read in full, so a "video" padded past the cap purely to force a large read is never a free resource hit - is left exactly as it was and reported false. `app.Commands.DecodeAsForMedia` (`backend/internal/app/media.go`) calls this for a message's own `MediaVideo` once `FetchMedia` has already put it on disk, and `server.mediaFetch` folds its verdict into `media.fetch`'s result as the new, additive `decodeAs` field (`"gif"` or omitted) - never a new field on `domain.Media` itself, since that type is filled in before anything is downloaded and has no bytes yet to check.

`domain.Media.IsGIFFile` and `ui/lib/Media.js`'s `isGifFile` are gone outright, not merely downgraded to a hint: nothing in the UI should ever again pick a decoder from a filename or an "animated" flag, both fully sender-controlled. `InlineVideo.qml`, `FullVideoPlayer.qml` and the photo viewer's own path now read a `decodeAs` property, threaded from `MessageTimeline`'s `mediaDecodeAs` role (set from `media.fetch`'s result the same way `mediaPath` already is) rather than computed from the message's static media object. A connector's own `isGIFImage` (by mime type or name) and `gifFileName` stay, but only as classification hints that choose `domain.Media.Kind`/`FileName` for labelling and routing to the video view in the first place; neither one, nor the `Animated` flag, is consulted again once a file is on disk - only `SanitizeIfGIF`'s own check of its bytes is. `mediaFileName` (`backend/internal/app/media.go`) now names every `MediaVideo` message's cache entry "`<id>.mp4`" unconditionally, dropping the ".gif" extension it used to choose from the same untrusted metadata: Qt's image plugins sniff a file's actual format from its content, not its extension, so this costs nothing and removes one more place a sender's claim was trusted.

## Every URL this UI opens is checked against one allow-list, in the helper and again in the UI

A review found WhatsApp's link preview took its URL straight from `GetMatchedText()` (`backend/internal/connector/whatsapp/normalize_media.go`), the sender's own message text matched by WhatsApp's own link detection, not a server-resolved value - unlike a formatting span's link, already checked against `linkSchemes` (`backend/internal/connector/telegram/formatting.go`), nothing filtered a link preview's scheme before it reached the UI, which opened it unfiltered through `Qt.openUrlExternally` in four different places (`MessageBubbleContent.qml`, `Highlight.js`'s `o` key, `MessengerLayout.qml`, `WindowController.qml`).

The scheme allow-list itself moved to `domain.AllowedLinkURL` (`backend/internal/domain/formatting.go`), since both connectors need it and `domain` is the one package every connector already imports with nothing internal of its own (see di.md): Telegram's `linkSpanAt` now calls it instead of keeping its own copy, and both connectors' `linkPreview` drop a disallowed URL (set it to `""`) rather than report it at all - the preview itself still shows its title and description, just with nothing to open. Dropping it, rather than refusing the whole preview, matches how a link span with a disallowed scheme is already handled: the surrounding content is still worth showing.

The UI keeps a second, independent check, the same reasoning as the imagesafe write-up above: `ui/lib/Links.js`'s `isAllowed` reuses `Format.spanURL`'s own allow-list (one list, kept in step with `domain.AllowedLinkURL` by hand, the same way `imagesafe`'s profiles and the helper's declared-size checks already are two independently maintained but matching things) rather than inventing a second one. Every place that might open a URL from a message, a link preview or a service's own text now reports a `linkOpenRequested` signal - bubbled from `MessageBubbleContent` through `MessageDelegate` and `ConversationView` the same way `mediaOpen` already is, or from `AccountSetup` directly - rather than calling `Qt.openUrlExternally` itself; every one of those signals, plus the palette's own "links" mode and the `o` key's single-link case, ends at `WindowController.openExternalLink`, the one property that actually calls `Qt.openUrlExternally`, and only after `Links.isAllowed` passes. `tests/unit/openurl-coverage.test.cjs` enforces this the same way `no-bare-color.test.cjs` enforces the `Color` singleton rule: every `Qt.openUrlExternally` call outside an explicit allowlist of files fails the build. That allowlist - `Service.qml`, and the controllers' own `openExternally` properties for a downloaded photo, video or file - is deliberately not pushed through the same check: each of those is always a `"file://"` path for a file this helper or the user already put on disk, not a URL a sender or service handed the UI as text, so `Links.isAllowed`'s scheme check (which would reject `file:` outright) does not apply to them at all. That is not quite the same as saying the path itself is never sender-influenced, which an earlier version of this entry claimed: before the fix described in "Received media is cached and opened by what it actually is, never a sender's claimed name" below, a file, voice note or sticker's cache path carried the sender's own claimed file name verbatim. It no longer does, but the UI still never builds one of these URLs by raw string concatenation - see "A local `file://` URL is always percent-encoded, in case any of its characters would otherwise break it" below - since a local path, whoever chose its name, can still hold characters (`#`, `?`, `%`, a space, non-ASCII text) that a naive `"file://" + path` would mangle.

## A sign-in hint is always a fixed, connector-written string, never a raw service error

A review found `whatsapp/pairing.go`'s `pairByPhone` building its failure hint as `"That did not work: " + err.Error() + ...`, where `err` is whatever `whatsmeow.PairPhone` returned - an IQError straight from WhatsApp's servers, or any other wrapped error whatsmeow produces. `AccountSetup.qml`'s step hint renders as `Text.StyledText` with `onLinkActivated` wired up, so a server (or anything on the path to it) that controlled that text could turn it into a clickable link to whatever it liked.

The fix is the same shape `app.fetchFailureReason`/`MediaFetchError` already use for a failed media download (see above): never put the error itself in front of the user, only a fixed, safe sentence, with the error reduced to a bare diagnostic line (`log.Print("whatsapp: pair by phone failed")`, no error text at all, since the error could otherwise echo the phone number just typed) for whoever reads the helper's own stderr. `pairByPhoneFailedHint` is that one fixed sentence; nothing here needed a richer set of categories, since there is exactly one way this particular call can fail that the user needs told apart from success.

Auditing every other `Hint` and `PasswordHint` both connectors report found nothing else to fix: Telegram's `codeHint` maps a fixed set of enum values (how the code was sent) to fixed sentences, its own failure hints ("That code did not work...", "This account has two-step verification...") are written out directly, and its one genuinely service-supplied string - the two-step verification hint the account's own owner set, read by `passwordHint` - already renders as `Text.PlainText`, where markup injection is not possible regardless of content; it was already correctly commented as untrusted text. `AccountSetup.qml`'s stale comment claiming the step hint was safe because "every branch is a fixed string we wrote ourselves" was wrong about `root.hint` specifically (the one branch that used to carry the WhatsApp bug); it now says what is actually true - every branch, including `root.hint`, is fixed - and notes that `onLinkActivated` reporting `linkOpenRequested` rather than opening anything itself (see the URL-filtering entry above) is a second, independent reason a future hint that turned out not to be fixed still could not reach an arbitrary scheme.

## A local file:// URL is always percent-encoded, in case any of its characters would otherwise break it

A review found `MediaController.qml`, `ConversationController.qml`, `ConversationController.openExternally`'s own default, `Service.qml`'s key-config opener, `PhotoViewerController.openExternally` and several views' own `Image`/`MediaPlayer` sources (`PhotoView.qml`, `PhotoViewer.qml`, `StickerView.qml`, `VoiceNoteRuntime.qml`, `Composer.qml`'s attachment preview) all building a local `"file://" + path` URL by plain string concatenation. Qt parses whatever reaches a URL property or `Qt.openUrlExternally` as a URL, not a plain string: a path holding `#` is read as starting a fragment, `?` a query string, `%` the start of a (likely invalid) escape, a space or non-ASCII text can simply be misread, any of which can truncate the URL, point it at the wrong thing, or fail outright, never only "the user picked an unusual file name."

The fix is one function, `Links.fileURL` (`ui/lib/Links.js`), used at every one of those call sites: it splits path on `/` and runs each segment through `encodeURIComponent` before rejoining them with `/` and prefixing `"file://"`, so the path's own separators are never themselves encoded while everything else that could confuse a URL parser is. `tests/unit/openurl-coverage.test.cjs` gained a second check alongside its existing one for a direct `Qt.openUrlExternally` call: no QML file may build a `"file://"` URL by hand-concatenation outside `Links.fileURL`'s own implementation, with the one documented exception of `InlineVideo.qml`, `VideoRuntime.qml` and `FullVideoPlayer.qml`, left alone because a separate, concurrent change was already in progress on the video fetch path those files are part of; they still need the same fix once that lands.

This stands regardless of what names the path: the entry above ("Received media is cached and opened by what it actually is...") means a downloaded file's own cache name no longer carries a sender's claimed file name at all, but the outgoing media area still names a user's own sent attachment from the file they themselves chose (see `cache.Outgoing.Path`), and this plugin's own `keys.conf` path is built from wherever `$XDG_CONFIG_HOME` happens to resolve to - neither is attacker-controlled, but both, like any local path, can still legitimately hold a character that would otherwise break a raw `"file://"` concatenation. An earlier version of this file's "Every URL this UI opens is checked against one allow-list" entry claimed these paths were simply "never sender- or service-controlled," which was true in intent but imprecise about why they still need `Links.fileURL` rather than being exempt from any URL-building care at all; it has been corrected to say so.

## Whether a received file is risky to open is the helper's call, not the UI's

A review asked for a received file to be classified against a published list of active or executable content - a web page, an SVG that can carry a script, a shell or Python script, an executable, a shortcut, and so on - and confirmed with the user before `xdg-open` ever sees it, rather than opening it the way a photo or PDF already does. Two places could decide this: a pure `ui/lib` function working from the file's extension and whatever MIME type the helper happened to report, or the helper itself, which has the file's own verified bytes in hand at the moment it names it. Splitting the decision across both risks the two drifting the way `domain.AllowedLinkURL` and `Links.isAllowed`'s own scheme list are explicitly two independently maintained things that happen to match (see the URL-allow-list entry above) - acceptable there because both sides already needed their own copy for other reasons; here neither side does, so one became the single source of truth instead.

The helper won: `app.MediaRisk` (`backend/internal/app/mediarisk.go`) sniffs the already-cached file at the path `media.fetch` or `media.save` just resolved - the same `sniffContentType` the caching fix above uses, so this costs nothing extra to compute from bytes already read - and checks the result against `riskyExtensions` and `riskyContentTypes`, two tables of the published catalogue above (plus `"bin"`, the caching fix's own fallback for anything unrecognised, since unmatched content is never confirmed safe either). `media.fetch`'s result gained one additive field, `risky` (omitted, i.e. `false`, for everyday media), rather than a new method: this is called on every successful fetch regardless of kind, cheaply, instead of only for a kind the allow-list might flag, so a future kind needs no extra wiring to be covered. It is computed fresh from `path`'s own bytes every single time, not cached alongside the fetch result and not read from the message's own media kind or claimed file name, so a cache hit - which runs none of the naming logic again - still gets the same answer a fresh download would.

The UI side has no classifier of its own: `MediaController.qml` stores `risky` on the message row exactly like `decodeAs` (see the GIF-decoding entry above) through `MessageTimeline.setMediaRisky`, and `_openIfAllowed` checks it before ever calling `openExternally`, opening `riskyConfirmOpen`'s question instead. `OpenRiskyConfirm.qml` offers the same y/n idiom `BlockConfirm.qml` and `ArchiveAllConfirm.qml` already use, except Enter and the visually highlighted default both choose "Save to Downloads," not "Open anyway" or "Cancel": every other y/n question in this UI defaults to the harmless choice, but here the "do nothing destructive" default and the "do nothing at all" default (Cancel) are different, and Enter chooses the one that still lets the user look at the file, safely, rather than the one that does the least. "Open anyway" (`y`) is a second, separate, deliberate answer. Confirming or saving reuses the path and cooldown bookkeeping `_openIfAllowed` already resolved, so answering the question is still the same click that asked it, not a fresh one.

## The desktop entry never rewrites the shared mimeinfo.cache

A review found `scripts/desktop-entry.sh`'s `install_desktop_entry` running `update-desktop-database` on `~/.local/share/applications` after writing this plugin's own `.desktop` file. That directory is on the allowed-writes list (see scripts.md), but `update-desktop-database` rewrites the whole shared `mimeinfo.cache` there, every other installed app's entry included, not just this one's. The entry declares no `MimeType` key at all - OmaMessenger is launched from Omarchy's apps menu, never used to open a file by its type - so there was nothing for that cache to index from this entry in the first place; the call was dropped rather than kept for a case that does not exist.

## Util.execDetached takes one command string, not an argv array

A review claimed `MediaController.qml` and `ConversationController.qml` passed an array to Omarchy's `Util.execDetached`, which "expects a single command string," so Copy silently did nothing - contradicting a real test where the user reported Copy working. Reading Omarchy's own `Commons/Util.qml` settled it: `execDetached(command)` is defined as `Quickshell.execDetached(["bash", "-lc", command])`, and every real call site in Omarchy's own shell (`AppLibrary.qml`, `Bar.qml`, `Menu.qml`) passes `command` as a plain string, never a list. Both of this plugin's calls instead wrote `Util.execDetached(["sh", "-c", "<command string>"])` - the whole array became the single `command` argument, so the actual call became `Quickshell.execDetached(["bash", "-lc", ["sh", "-c", "<command string>"]])`, with the nested array coerced to one comma-joined, unexecutable word.

Running a minimal offscreen Quickshell probe (`quickshell -p` against a throwaway root importing `qs.Commons`, cleaned up immediately after) confirmed this directly: `Util.execDetached(["sh", "-c", "touch /tmp/marker"])` never created the marker file, while `Util.execDetached("touch /tmp/marker")` did, every time. The claim was correct; the user's own successful-looking test most likely saw `MediaController`'s unconditional "Copied to clipboard" notice (set regardless of whether the detached process ever ran, since `execDetached` is fire-and-forget with no result to check) rather than an actual, verified paste.

The fix drops the extra `["sh", "-c", ...]` wrapper entirely - `Util.execDetached` already runs its argument under `bash -lc`, so wrapping it in a second shell invocation was never needed even once the argument shape was fixed - keeping `Util.shellQuote` on every interpolated value exactly as before. `tests/unit/shellexec-coverage.test.cjs` now matches `Util.execDetached(` directly (rather than the old, array-specific pattern) and additionally rejects the broken argv-array shape outright, so neither mistake can return unnoticed.

## A video's own container and stream headers are validated before anything plays in-window

A security review found that a received video - including one a sending service marks to autoplay like a silent, looping "GIF" (WhatsApp's `gifPlayback`, Telegram's `DocumentAttributeAnimated`) - reached QtMultimedia inside the shell process with nothing checking its declared codec, frame size, duration or track count first, and that a "GIF"-marked video autoplayed and auto-decoded the moment its bubble was shown, with no click at all; each visible bubble also got its own decoder, so a chat full of them could be decoding many videos at once. All three are now closed: the helper validates a video's own bytes before anything in the shell may decode it, nothing plays or even downloads without a click, and exactly one video decodes at a time across the whole window.

`backend/internal/videosafe` (new) reads an MP4/MOV (ISO base media file format) or WebM/Matroska (EBML) file's container and stream headers in pure Go, never shelling out to `ffprobe` and never reading a file's actual sample data. A hand-written reader was chosen over a dependency: this package needs only a handful of fields (a track's handler, its sample entry's codec fourcc or CodecID, its declared width, height and sample count, and the movie's own duration), and writing that by hand, bounded and fuzzed, is simpler to audit and license than pulling in a general-purpose demuxer and clearing it through `go-licenses` for something this narrow. Every read goes through a single `cursor` type wrapping an `io.ReaderAt` (an `*os.File` in production; a fake in `readfailure_internal_test.go` for the one defensive branch - a read that fails after its own box or element header was already found - no well-formed file can actually reach), with absolute offsets rather than sequential reads, so a crafted header can never make this package itself read or allocate more than a few hundred bytes regardless of how large the file on disk is. A box or EBML element's own declared size is always checked against the small, already-bounded remainder of its container (`size > limit-off`, never `off+size > limit`): comparing against the limit instead of the sum is what keeps a maliciously huge 64-bit size (EBML allows up to 2^56-1) from wrapping the sum negative and slipping through, the exact case `TestValidate_WebMHugeElementSize` and `FuzzValidateWebM`'s own seed corpus both exercise directly. A shared box/element-count budget (`maxBoxBudget`, 10,000) across one whole `Validate` call bounds the work a long chain of tiny, otherwise well-formed boxes can demand.

`Validate(path)` reports `playable` true only once every limit in `limits.go` passes: an allowed video codec (`avc1`/`avc3`/`vp09`/`av01` in MP4/MOV; `V_VP8`/`V_VP9`/`V_AV1` in WebM/Matroska), width and height each at most 1920, a duration at most 10 minutes (the longest of the movie's own header and every track's own, so a track that disagrees with the movie-level value can never sneak a longer video past the cap), at most 3 video tracks, a declared sample count at most 10,000,000 (read as a single field from `stsz`/`stz2`, never allocated, since the point is catching an absurd declared count, not iterating one), and, if the file carries audio, an allowed audio codec (`mp4a`/`Opus` in MP4/MOV; `A_AAC`/`A_OPUS`/`A_VORBIS` in WebM/Matroska). An audio track in any other codec refuses the whole file rather than muting it: this package only answers whether a file is safe to decode, never rewrites its bytes the way `imagesafe` does, so there is no way to strip or mute a track without re-muxing the file, out of scope here. A file that is neither container at all, or fails any of these, is reported simply `false` with no error, the same way `imagesafe.Sanitize` reports a bad image: this is attacker-controlled data, not a program fault. `Validate` returns an error only when the file itself cannot be opened or statted. `isobmff_test.go` and `matroska_test.go` cover both the happy path and every rejection reason with hand-built fixtures (`helpers_test.go`), including a truncated box, a track missing a required child box, and a declared size over the limit; `FuzzValidateMP4` and `FuzzValidateWebM` seed the corpus with an oversize dimension, a wrong codec, a truncated box, a huge EBML size and a non-video file, and `go test -race`'s normal run already covers the defensive readAt-failure branches through `readfailure_internal_test.go`'s fake reader.

`connector.VideoPlayable(path)` (`backend/internal/connector/media.go`) wraps `Validate` for the connector layer; `app.Commands.VideoPlayableForMedia` (`backend/internal/app/media.go`) calls it for a message's own `MediaVideo` once `FetchMedia` has put it on disk, the same shape `DecodeAsForMedia` already has for the GIF check, and `server.mediaFetch` folds the verdict into `media.fetch`'s result as the new, additive `playable` field (see docs/api.md), alongside the existing `decodeAs`. The two checks run independently and in that order: a video `SanitizeIfGIF` already confirmed is a genuine GIF image is never run through `VideoPlayable` for a meaningful answer either way (its rewritten bytes are no longer a valid video container at all, so `Validate` would report `false` on it regardless) - the UI's own `Media.canPlayInline(decodeAs, playable)` treats `decodeAs === "gif"` as always safe to play, through the image engine, and never consults `playable` for that case.

Removing the auto-fetch and auto-decode a "GIF"-marked video used to get on its own (`InlineVideo.qml`'s old `Component.onCompleted`/`onVisibleChanged`/`onPathChanged` triggers, firing a `wanted()` signal with no click at all) meant unifying its click handling with an ordinary video's: both now go through the same bottom `MouseArea` and the same `toggled()` signal, so a first click on either asks `MediaController.toggleVideo` to fetch the file, and only once `media.fetch` answers does `_selectOrOpenVideo` decide whether to select it for in-window playback (`Media.canPlayInline` true) or fall back to opening it in the user's own video player (false) - exactly the fallback a click already took on a machine with no QtMultimedia at all. A "GIF"-marked video that turns out to be an ordinary MP4 (every one WhatsApp or Telegram actually sends this way) now shows its thumbnail and a play mark like any other video, rather than decoding for free. A real GIF *image* file is the one case the review allowed to keep auto-playing without asking again: once a click has downloaded it and `decodeAs` comes back `"gif"`, `AnimatedImage` plays it immediately, with no second click to start it, exactly as before - only the initial fetch now needs the one click every other video needs, since there is no way to know a sender-flagged "animated" video will actually turn out to be a real GIF image before downloading it, and auto-fetching just in case would reopen the exact hole this change closes. `playMark` and the bottom click area, previously excluded for every animated video, now show for one that has not yet been confirmed a real GIF, and hide once it is one and already animating.

A single decoding slot, `VideoController.playingId`, already existed for ordinary videos sharing one bubble's worth of attention at a time; a "GIF"-marked video used to sit outside it entirely, decoding independently of everything else merely by being visible. It now shares the same slot: selecting it (through the same `toggle` a click already calls) deselects whatever else was playing, and `InlineVideo._decoding` requires `root.playing` for every kind alike, dropping its old `root._animated ||` exception. The slot's reach was also widened to cover the in-app viewer, which previously ran its own `FullVideoPlayer` with no coordination with any bubble's own selection at all: `VideoController.select`/`deselect` (new, alongside the existing `toggle`) let `PhotoViewerController.show`/`close` claim the slot for whichever video it opens, idempotently (selecting an already-selected video is a no-op, never a toggle-off), and give it back on close only if nothing else has claimed it since. `windowActive`, which already stopped a bubble's own decoder the moment the window lost focus, now reaches the viewer's `FullVideoPlayer` too (`Overlays.windowActive`, threaded from `MessengerLayout`'s existing `conversationController.windowActive`), so leaving the window unloads a full-size video exactly as it already unloads an inline one.
## Received media is cached and opened by what it actually is, never a sender's claimed name

A review found `app.mediaFileName` naming a file, voice note or sticker's cache entry `<id>-<sender's own file name>`: a sender fully controls that name and its extension, so a disguised attachment - an executable claiming to be `invoice.pdf.exe`, a script with no extension at all that a desktop's own file-type detection would still treat as text - kept whatever extension the sender picked straight through to the file this UI eventually hands to `xdg-open`. A photo and a video were already safe, named `<id>.jpg`/`<id>.mp4` unconditionally (see the GIF-decoding entry above); nothing else was.

The fix: `fetchIntoCache` (`backend/internal/app/media.go`) still uses `cache.Fetch` with `fixedMediaName`'s own extension for a photo or video, but names every other kind `<id>` plus an extension chosen from `extensionFor`'s fixed allow-list (`backend/internal/app/mediasniff.go`), keyed by the MIME type `sniffContentType` reads from the downloaded bytes themselves, sniffed with `http.DetectContentType` (plus one added case: a `<svg` tag inside what it calls generic XML, the one common active-content format it does not name on its own). A type the allow-list does not recognise gets `.bin`, never assumed safe for being unmatched. The sender's own claimed file name survives only as what `media.save` names the copy it leaves in the user's own downloads directory (see `downloadName` in `backend/internal/app/mediasave.go`), never as anything this helper caches or opens on the sender's say.

The snag: the final name can only be chosen once the file's bytes exist, but `cache.Fetch`'s own name has to be known before the fill that downloads them even starts. `cache.FetchNamed` (`backend/internal/cache/fetchnamed.go`) is `Fetch`'s counterpart for this: it locks and locates an existing cached file by `id` alone (a name match requires the next character, if any, to be `.`, so `id` "m1" can never match a different message's "m12.jpg"), and, once there is none yet, fills a file private to that `id`'s own download before asking `nameFor` - `fetchIntoCache`'s own sniff-and-choose closure - what to rename it to. A second `FetchNamed` call for the same `id` never re-fills or re-asks `nameFor`: whatever name the first call chose is what every later one finds.

An already-cached file from before this fix (`<id>-<sender's name>`) is never matched by `FetchNamed`'s own id-prefix-then-`.` rule, so it is simply never found again: the next time that message's media is asked for, it is downloaded and named afresh under the new scheme, and the stale copy is left for the cache's own least-recently-used pruning to clear out eventually, the same as any other file nothing has touched in a while. No migration step was needed for this reason alone.

One more wrinkle, specific to `make build-fake`'s own test connector: `fake.Connector.FetchMedia` has always told a voice note's download apart from a photo's by `path`'s own extension, the one signal it has without the message's media kind in its signature (matching every real connector's own) - and relied on `app.mediaFileName` always giving a voice note's path a fixed `.ogg` ending for this. Under the new scheme, the path `FetchNamed` hands `fill` while downloading is just `<id>.part`, with no extension to read at all. `voiceHintedFill` (`backend/internal/app/media.go`) wraps the connector call for exactly this one kind: the download briefly happens under `<id>.part.ogg` instead, moved back to the plain `<id>.part` `FetchNamed` is waiting for once it finishes, cleaned up if the download itself fails. Every real connector ignores `path`'s extension and writes whatever the service actually sent regardless, so this changes nothing for them, and it never influences the file's own final cache name either, which is still decided only by sniffing the downloaded bytes.

## Automatic fetch stays capped for every media kind, and every open goes through one gate

A further security review found the two disciplines above - "Every download is size-capped and deadline-bound" and "Whether a received file is risky to open is the helper's call" - had each grown one gap of their own, plus a third, separate one in how a saved file was named. This section states the rule each gap exposed, since by now it spans several files on both sides of the protocol; the sections above still explain how each discipline first came to be.

**A declared size of zero is never a free pass, for any kind.** `whatsapp.fetchImage` (`connector/whatsapp/fetch.go`) checked a photo, sticker or GIF document's declared `FileLength` against `imagesafe.Profile.MaxInputLen`, same as "A declared media size is checked before downloading" above describes, but skipped that check entirely when `FileLength` was left at its zero default - exactly what a sender who wants the check skipped would do - and then still called whatsmeow's in-memory `DownloadMediaWithPath`, with nothing capping the read itself. It now streams to a temporary file through `DownloadMediaWithPathToFile`, the same way `fetch_stream.go` already streams a video or file, wrapped in the same `boundedFile`; the declared-size check is now only ever the cheap, early exit, never the only gate standing between a reply and an unbounded read (see `fetch_image_stream.go`'s `streamImageOnce` and `retry.go`'s `retryStreamedImageDownload`, its primary-phone-retry counterpart).

**An automatic fetch is never trusted with more than `AutoFetchMaxBytes`, image or not.** Both connectors' image path ignored `auto` altogether, trusting `imagesafe.FullImage`'s own 32 MiB input cap even for a fetch nobody clicked - double `AutoFetchMaxBytes` itself, the limit "Every download is size-capped and deadline-bound" (above) describes applying to everything else. `connector.ImageFetchCap(profile, auto)` (`connector/limits.go`) is the one function both connectors now call: `profile.MaxInputLen`, narrowed to `AutoFetchMaxBytes` whenever `auto` is set and that cap is the smaller of the two. A deliberate fetch - a click, the viewer opening, or a tap-to-load retry - still gets the profile's own, larger cap.

**An automatic fetch is not only the one case it used to be.** `media.fetch`'s `auto` param had drifted to describing only `InlineVideo`'s animated-autoplay fetch, and a prior change had actually removed every caller of it - a video never auto-fetches at all any more, only a click does - leaving `auto` accepted but sent by nothing. That same change's QML side, though, still fetched a photo's full image, a sticker's full image and a voice note's full file the moment each one's row became visible, with no click at all, and that fetch kept sending `auto: false`: exactly the "fetched with no click, without the small automatic cap" class this whole section is about, just moved from video to every other kind that still auto-fetches. `MediaController.fetchMedia` - the one function `PhotoView`, `StickerView` and `VoiceNotePlayer`'s own `wanted()` signals all reach, through `MessageBubbleContent`, `MessageDelegate`, `MessengerLayout` and `ConversationController.fetchMedia` - now always passes `auto: true`. Every other entry point (`openMedia`, `toggleVideo`, `openExternal`, `copyMedia`, `saveMedia`, the photo viewer's own `show`) keeps passing `auto: false`: each one is reached only by a click, Enter, a keyboard shortcut, or the viewer opening, never by a row merely scrolling into view. `tests/unit/auto-fetch-coverage.test.cjs` pins both shapes: `fetchMedia` must pass `auto: true` to `downloadMedia`, and the three `wanted()` handlers must all reach `mediaWanted()`, never some other signal that could quietly skip `fetchMedia` altogether.

**A legitimately large automatic item fails visibly, not silently.** Once `fetchMedia` actually enforces the small cap, a photo genuinely larger than 16 MiB needs a way back, rather than sitting on its blurred preview (or, for a sticker, its emoji fallback) forever with nothing to click. `MediaController.retryMedia` is the deliberate counterpart `fetchMedia` always lacked: the same `downloadMedia` call, with `auto: false`. `PhotoView` and `StickerView` read the fetch's own `failedReason` (`VoiceNotePlayer` already did, for its "Unavailable" tooltip) and, only when it is `"too-large"` and there is still no path, show a "Tap to load" affordance instead of the usual "unavailable" state, wired to `retryMedia` (`PhotoView` reuses its existing `opened()` signal, since showing the viewer already fetches deliberately; `StickerView` and `VoiceNotePlayer` each needed their own click target). `Format.js`'s `MEDIA_FAILURE_REASONS` gained the matching phrase, since `"too-large"` had no entry at all before this - it was never something an automatic fetch was previously allowed to fail at.

**The in-app viewer's own external-open is not a second gate.** `PhotoViewerController.openExternally` called `Qt.openUrlExternally` itself, skipping both the per-message cooldown and the risky-open confirmation `MediaController._openIfAllowed` already enforces for every other external open (see "Whether a received file is risky to open is the helper's call" above) - a second, ungated door to the same action. It now closes the viewer and calls `conversation.openMediaExternal(id)` instead, the same path a bubble's own "open externally" action already uses, so a risky file opened from the viewer still asks first, and a repeat click within the cooldown is still ignored. `tests/unit/openurl-coverage.test.cjs`'s allow-list dropped `PhotoViewerController.qml` accordingly: `WindowController.openExternalLink` (checked URLs) and `MediaController`'s and `ConversationController`'s own default `openExternally` property (the terminal action behind the gate) are the only remaining direct callers, plus `Service.qml`'s unrelated local open of the user's own `keys.conf`.

**A video opening the viewer is not the same as a video decoding in it.** The viewer opens for any video kind once `videoController.available` or the file is a confirmed GIF image, before `media.fetch`'s own `playable` verdict can be known for an undownloaded file - deliberately: refusing to open the viewer at all would mean never discovering whether a video is playable in the first place, since nothing fetches it otherwise. What actually gates QtMultimedia decoding is `FullVideoPlayer`'s own `Loader.active: root.available && root.playable && …`, unaffected by whether the viewer around it is open: a video that turns out unplayable shows "This video can't be played here" with the external-open button, never a decoder.

**Copying media to the clipboard no longer shells out from QML at all.** `MediaController.copyMedia` and `ConversationController`'s own default `copyToClipboard` built a `wl-copy --type <mime> < <path>` string for `Util.execDetached`, with the MIME type picked from the message's own kind (`Media.mimeFor`) rather than sniffed - the one path in "Util.execDetached takes one command string, not an argv array" (above) that still built a shell command string from message-adjacent data, even though every value in it did go through `Util.shellQuote` correctly. The additive `media.copy {messageId}` method (`server/mediacopy.go`, `app.Commands.CopyMedia`) fetches the message's media if need be, the same way `media.save` does, sniffs its MIME type fresh from the downloaded bytes (never trusted from the message), and writes it to the clipboard through `clipboard.Wayland.Write` (new, alongside the existing `Read`) - `exec.CommandContext("wl-copy", "--type", mimeType)` with the file as `cmd.Stdin`, a fixed argv with no shell string at all, bounded by its own `writeTimeout` (10 s, longer than `Read`'s `commandTimeout` since a copied video can be considerably larger than anything this helper ever pastes in). `MediaController.qml` now just calls `media.copy` and shows the same confirmation; `ConversationController`'s own `copyToClipboard` property, and `MediaController`'s matching default, are both gone along with it. `tests/unit/shellexec-coverage.test.cjs` now also fails if any QML file shells out to `wl-copy` directly, closing the class rather than only the one instance of it.

**A saved file's own extension is never the sender's claim either.** `media.save`'s `downloadName` used the sender's claimed file name verbatim when there was one - unsanitized, and with whatever extension the sender picked, display-only rather than used to decide how the file is cached or opened, but still exactly the kind of sender-controlled text "Received media is cached and opened by what it actually is" (above) already distrusts for everything else about a saved file. A control character, or a right-to-left override or isolate character (Unicode category Cf, which covers `U+202A`-`U+202E` and `U+2066`-`U+2069`) could make a saved name's real extension read differently than it is in a file manager that renders them, the same class of trick "Whether a received file is risky to open is the helper's call" (above) already protects the open path from. `downloadName` now keeps only the sender's name as a stem: its own claimed extension dropped, every Cc or Cf character stripped, runs of whitespace collapsed, the result capped at 100 runes, and `extensionFor`'s sniffed-content-type extension always appended instead - the same allow-list "Received media is cached and opened by what it actually is" already uses for the cache's own name. A stem that sanitizes to nothing (all control or bidi characters, or no claimed name at all) falls back to the fixed stem `"file"`, so a save is never named just its extension or nothing at all.

## An outgoing photo attachment is sanitized before anything decodes it, the same as a downloaded one

A review found `app.photoThumb` calling `image.Decode` directly on an attachment the user picked from disk, with no `imagesafe` check and no `image.DecodeConfig` dimension cap first: "Untrusted images are sanitized in the helper, never trusted as received" (above) covers a downloaded, pasted or sanitized-outgoing-from-clipboard image, but an attachment read straight off the user's own disk had no equivalent gate at all, so a crafted header could still make this helper allocate an unbounded bitmap just to build a tiny outgoing thumbnail.

`connector.SanitizeOutgoingImageFile(path)` (new) is `SanitizeOutgoingImage`'s own file-based sibling: it checks path's declared size against `imagesafe.FullImage.MaxInputLen` before reading anything into memory, the same discipline "A declared media size is checked before downloading" already applies to a download, then reads, sanitizes and overwrites the file in place with the result. `app.describeAttachment` runs every photo attachment through it, via `sanitizeAttachedPhoto`, before `imageDimensions` or `photoThumb` ever decodes the stored copy: an attachment that fails - too large, or not really a valid PNG, JPEG, GIF or WebP - is refused outright with a safe, fixed sentence, and `prepareAttachment` removes the unsanitized copy `storeAttachment` already wrote to the outgoing media area rather than leaving it behind. This is a real behaviour change for a format `imagesafe` does not recognise (BMP, say): such a file used to attach successfully with no thumbnail; it is now refused entirely, the same trade `imagesafe` already makes everywhere else, since there is no way to sanitize a format this package cannot parse.

Auditing every other `image.Decode`, `image.DecodeConfig`, `png.Decode`, `jpeg.Decode` and `gif.Decode*` call in `backend/` found one more already-guarded case worth confirming rather than fixing: `connector/whatsapp/upload.go`'s `jpegThumbnail`, building an outgoing WhatsApp photo's own preview, already calls `image.DecodeConfig` and checks the result against `imagesafe.FullImage`'s own caps before its one `image.Decode` call (see "A pasted or outgoing image is capped and sanitized the same way a downloaded one is", above) - and since `describeAttachment` now sanitizes the stored file before any connector ever reads it for upload, that path is doubly covered. `.golangci.yml` gained a `forbidigo` rule banning all five functions outright, with an exact exclusion list naming `imagesafe` itself (the one package allowed to decode at all) and the two files - `attachment.go` and `upload.go` - whose own doc comments explain why their one remaining call is already guarded, so a new, unguarded call anywhere else fails the build immediately instead of waiting for the next review to find it by hand.


## A voice note's own bytes decide whether it plays in-window, the same discipline video already has

A review found `VoiceNoteRuntime.qml` loading a downloaded voice note straight into `MediaPlayer` with nothing checking its codec or stream shape first - videosafe's own discipline existed for video, but no audio counterpart did - and found `ui/lib/Media.js`'s `kindFor` picking the voice player for an unrecognized-kind message purely from its claimed file name's extension (`isAudioFileName`, matching `.mp3`, `.ogg`, `.wav` and others): a disguised attachment could make the UI choose that decoder from a name alone, exactly the class of bug "A video's actual bytes decide whether it animates as a GIF" (above) already closed for video.

`backend/internal/audiosafe` (new) is videosafe's sibling for audio: `Validate(path)` reads only the handful of container or frame headers each format needs, through the same bounded, absolute-offset reads videosafe's own `cursor` uses (reimplemented here rather than shared, since videosafe's cursor, span and box-reading helpers are all unexported and the two packages judge different things), and reports playable true only for one of three simple shapes: a single-bitstream Ogg file whose first page's payload opens with Opus's own `OpusHead` magic (RFC 7845) and whose highest granule position, divided by Opus's fixed 48kHz granule rate, implies a duration within `maxDuration`; an MP4/M4A file with exactly one audio track in an allowed codec (AAC or Opus) and no video track at all; or a constant-bitrate MPEG-1 Layer III (MP3) stream, confirmed by finding several consecutive frame headers each exactly where the previous one's own declared bitrate and sample rate predict the next one starts. A second, distinct Ogg bitstream serial number, a video track in an MP4 container, or an MP3 stream in any other shape (MPEG-2/2.5, Layer I/II, free or variable bitrate) is refused outright: this package never walks a variable-length frame chain or a multiplexed stream, which is what "simple to validate" means here, and refusing anything it cannot validate simply is safer than guessing. The duration cap is 30 minutes, generous for a voice note or a shared song. `FuzzValidateOgg`, `FuzzValidateMP4Audio` and `FuzzValidateMP3` seed each walker's own corpus the way videosafe's fuzz targets do.

`connector.AudioPlayable(path)` wraps `Validate` for the connector layer, the same shape `connector.VideoPlayable` already has; `app.Commands.AudioPlayableForMedia` calls it for a message's own `MediaVoice` once `FetchMedia` has put it on disk, mirroring `VideoPlayableForMedia` exactly, and `server.mediaFetch` folds whichever of the two verdicts applies into `media.fetch`'s existing, additive `playable` field (see `docs/api.md`) - one shared field, since a message is never both kinds at once, rather than a second one. `ui/lib/Media.js`'s `AUDIO_EXTENSIONS` and `isAudioFileName` are gone outright: `kindFor` no longer re-guesses "voice" from a file name at all, so a voice note received before the helper's "voice" media kind existed (see "A voice note's media is written once..." above), permanently stuck with kind `"file"`, now renders as a plain file row rather than a player - a real behaviour change, accepted because there is no safe way to tell a disguised executable from a real audio file by name alone, the same trade-off "Received media is cached and opened by what it actually is" already made for the cache's own naming. `VoiceNotePlayer.qml` gained a `playable` property, threaded from `MessageTimeline`'s existing `mediaPlayable` role the same way `InlineVideo.qml` already reads it; `MediaController._selectOrOpenVoice` (replacing the unconditional `_toggleVoice` call `openMedia` used to make) starts the in-window player only when `voiceController.available && timeline.mediaPlayable(id)`, and falls through to the same gated external-open path a video or file already gets otherwise. The button stays clickable either way - a downloaded but unplayable note still opens, just not in place - with its tooltip naming the difference ("Open in your own application") rather than disabling the control, which is reserved for a fetch that is known to have failed outright.

`tests/unit/mediaplayer-gating.test.cjs` is the audit the UI side of this fix needed: `tests/unit/bounded-image-source.test.cjs` already guards every `Image`/`AnimatedImage` showing received content, but a `MediaPlayer`'s own gate is architectural rather than a single property to check for - video gates its `Loader.active` on `playable` directly, while a voice note's shared, always-loaded runtime is gated one layer up, at the one call site that may ever hand it a real path. The new test asserts no `MediaPlayer` exists outside the two reviewed runtime files, and that every known way a real path reaches one of them - `InlineVideo`'s and `FullVideoPlayer`'s own `_runtime.item.source = root.path` assignment, and `MediaController`'s call to `voiceController.toggle(` - appears only in an exact, exhaustive list of files, each of which must also read the helper's own `playable` verdict somewhere in its own text; a new entry point, or one of these losing its gate, fails loudly rather than silently.

## The search field and the composer's text input are destroyed, not merely hidden, exactly when they are irrelevant

A review found `ListColumn`'s search field, and `Composer`'s own text input, hidden but never destroyed in a narrow window showing the other column, or (for the composer) with no conversation open at all: `visible: false` on a parent does not cascade into destroying a child's own QML object, so a hidden `TextField`/`TextArea` stays alive and keeps reading Wayland clipboard changes with no size or time limit on supported Qt versions, the exact risk `tests/unit/textinput-lifetime.test.cjs` already closed for the command palette, account setup and the new-chat dialog (see "An overlay with an editable field is destroyed on close, not just hidden", above) - just not yet for these two, which that fix's own `ALLOWLIST` excused as "always visible", true of the surrounding component but not of the field inside it.

Both fields now sit behind their own `Loader`, inline (`sourceComponent: Ui.TextField { ... }`/`sourceComponent: ScrollView { ... }`, the same pattern `Overlays.qml` already uses for its own gated panels, rather than a separately named `Component { id: ... }`, which a later audit found the static checker below cannot see through), gated by a boolean that is false exactly when the field would otherwise sit there unused: `ListColumn`'s own `root.visible` (true only while the list column is the one shown) for the search field, and a new `Composer.active` property, set by `ConversationView` to `root.visible && root.conversation !== null` (shown, and something to compose into), for the composer's input. Each field's owning component stays instantiated unconditionally by its caller exactly as before - nothing about `ListColumn` or `Composer` as a whole changes - only the one field inside each is now loaded and destroyed on its own.

Neither field's own text lives in the field any more: `ListColumn`'s search text already flowed one-way from `ListController.query` (`text: root.query` plus `onTextChanged: root.queryEdited(text)`), unaffected, since destroying and recreating a mirror of a value the controller already owns loses nothing. The composer's text needed the same move: `Composer.text` changed from `property alias text: area.text` to a real `property string text: ""`, pushed into a freshly loaded input on `Loader.onLoaded` and on every later external change (`onTextChanged: if (root.input && root.input.text !== root.text) root.input.text = root.text`), and read back out of the input's own `onTextChanged` the same way, each guarded against the other so neither loops - the exact idiom `ConversationView`'s own `onDraftChanged` already uses one layer up, for the same reason ("a binding from draft to the composer would break the first time the composer clears itself after sending"). `Composer.input` (the live field itself, or `null` while inactive; a plain `property var`, the same reasoning `VoiceNoteController`'s own `_engine` documents) replaces the old `property alias input: area` so every caller - `MessengerLayout`'s newline, paste-fallback and focus-mirroring `Connections`, and the handful of internal functions the field's own signals call - can be written to check for `null` rather than assume the field is always there. `focusInput()` grants a pending focus request once the input actually loads (`_focusPending`) rather than assuming `Loader.item` is ready the instant `active` turns true, which nothing in this codebase actually guarantees.

`tests/unit/textinput-lifetime.test.cjs`'s `ALLOWLIST` lost both entries: a component whose one field gates itself this way needs no caller-side Loader at all, so the test gained `fieldSelfGated`, which checks every `TextField`/`TextArea`/`TextInput` declaration in a file is itself inside a gated `Loader` in that same file, and skips the existing cross-file "is this component only ever instantiated behind a Loader" check for any file where that is true. `tests/qml/OverlayLifecycle`'s own baseline dropped `composerInput` (no conversation is open in that test, so it no longer exists) and a new `tests/qml/FieldLifetime` drives a narrow window through opening and closing a conversation, checking at each step that exactly the right field exists, that typing into each still reaches its controller (`ListController.query`, `ComposerController.draft`) exactly as before, and that the search field's text survives being hidden and shown again - proof the controller, not the field, was always what actually held it.

## Incoming message text and a rendered pipe table are both capped, not left to the sender's word

A review found no bound at all on a received message's own text length - `domain.MaxTextLength` caps what the composer may send, but nothing capped what a sender could claim arrived - and found `ui/lib/Markdown.js` turning a pipe table of any size into a real HTML `<table>` with no row or column cap, so a message built from many columns or many rows could make the UI lay out an unbounded amount of rich text in one bubble.

`domain.MaxIncomingTextLength` (64 KiB) is the helper-side cap: generous enough that no real message is ever affected, far looser than `MaxTextLength` since it exists only to bound a sender-controlled field, not to match what a real client would ever send. `domain.TruncateIncomingText` cuts on a valid UTF-8 boundary and appends a fixed `"[message truncated]"` notice within that same cap, rather than refusing the message outright the way sending over-length text is refused: a sender is not asking permission the way the local user is when sending, so shortening it is friendlier than dropping it. `Ingest.save` (both `Incoming` and `History` route through it) and `Ingest.Edited` both run every message's text through it before it ever reaches the store, so nothing downstream - the UI, a notification, a conversation list's preview - ever sees an untruncated one.

`ui/lib/Markdown.js` gained `MAX_TABLE_ROWS` (50) and `MAX_TABLE_COLUMNS` (20): `tryParseTable` now reports a table over either cap as not a table at all, the same as any other text with a stray `|` in it, rather than rendering a silently truncated table that disagrees with how many rows or columns the sender's own message actually had. `ui/lib/Format.js` gained `MAX_RICH_TEXT_INPUT_LENGTH` (65536 UTF-16 code units, a generous match for `MaxIncomingTextLength` kept independently since this file has no way to import a Go constant - the same two-independently-maintained-but-matching pair `Links.js`'s own allow-list and `domain.AllowedLinkURL` already are): `messageHtml` cuts its own input to this cap before any escaping, linkifying or table parsing runs over it, so the HTML it builds is always bounded by a predictable multiple of the cap - never a raw cut through the middle of a tag, which slicing the finished HTML itself could otherwise produce.

Auditing every `Text`, `TextEdit` or `TextArea` in `ui/` set to `StyledText` or `RichText` (`tests/unit/richtext-bounds.test.cjs`, a new allow-list test in the same style as `no-bare-color.test.cjs`) found three: `MessageBubbleContent.qml`'s own message body, now bounded by `messageHtml`'s own cap; `AccountSetup.qml`'s sign-in hint, already fixed, short, connector-written sentences, never raw service or sender text (see "A sign-in hint is always a fixed, connector-written string" above); and `ConversationRow.qml`'s conversation-list preview, whose preview line and search match are cut to `Format.MAX_PREVIEW_LENGTH` (200 characters) before escaping, since a row only ever shows one elided line.

## Input from other local processes: only D-Bus signals needed a sender check, and the helper never trusted one

A review found `notify.Desktop`'s D-Bus wiring trusting a notification signal from any sender on the session bus, and reading it with no length or type checks: `dialSessionBus`'s `AddMatchSignal` matched on interface alone, `dbusBus.Wait` never compared a signal's own `Sender` to anything, and `matchActionInvoked` indexed `sig.Body[1]` with no check that the body had a second element at all - a one-element `ActionInvoked` signal, which any local process can send on the session bus with no privilege at all, panicked and would have taken the whole helper down with it, and a well-formed but spoofed `ActionInvoked(id, "default")` could fake a click on a notification nobody actually clicked.

`dbusBus.Show` now resolves `org.freedesktop.Notifications`'s own unique bus name through `org.freedesktop.DBus.GetNameOwner` before calling `Notify` (not at dial time: nothing owns the name yet on a freshly connected bus with no daemon running, and `Show`'s own call is the point this helper is about to start trusting that name's answers anyway), narrows the signal match to that sender with `dbus.WithMatchSender`, and records it on the bus. `Wait` then refuses any signal whose `Sender` is not that exact value as its first, authoritative check, before it reads anything else out of the signal's body: the match rule narrows what the session bus ever delivers, but `Wait`'s own check is what actually matters, since a match rule is advisory for an already-connected subscriber and this package never assumes otherwise. `matchActionInvoked` now checks `len(sig.Body) < 2` and uses a comma-ok type assertion on `sig.Body[1]` before ever indexing it, the same discipline `signalIsFor` already gave `sig.Body[0]`; a malformed or wrongly-typed body is simply never matched, rather than defaulting to an empty action. `Notify`'s own goroutine recovers from a panic either way, logging only the recovered value's own type (`%T`), through a new `notify.Logger` interface wired from `main.go`'s existing logger - defence in depth behind the fix above, for a bug reached from this path or any other no one has found yet, since one malformed signal must never be able to take every other notification, let alone the helper itself, down with it (see errors.md: recover at the protocol boundary).

Auditing every other point the helper reads input from another local process, for the same pair of problems - no check on where it came from, and parsing with no length or type checks - found nothing else to fix:

- **D-Bus elsewhere:** `notify.go` is the only file in `backend/` that imports `github.com/godbus/dbus/v5` at all. `ServiceReachable`'s own `NameHasOwner` call reads a single `bool` back through `Store`, nothing to index or type-assert, and it never shows a notification or acts on the answer beyond a yes/no for the doctor report.
- **Clipboard reads:** `clipboard.Wayland.Read` shells out to `wl-paste`, whose output - from whichever other application last put something on the clipboard, trusted no further than a sender's own message - is already bounded by `MaxPasteLen` (32 MiB) through `boundedWriter`, and bounded in time by `commandTimeout`; `app.PasteImage` then runs it through `connector.SanitizeOutgoingImage`, the same decode-and-re-encode gate a downloaded photo gets (see "A pasted or outgoing image is capped and sanitized the same way a downloaded one is", above), before it ever reaches the outgoing media area. There is no sender identity to check here at all - any local process can write to a Wayland compositor's clipboard by design - so bounding size and distrusting content fully, which this path already did, is the correct discipline rather than a gap.
- **Files written by other apps in shared dirs:** nothing under `backend/` reads a file from a directory another application writes into. Session and database files live under `$XDG_DATA_HOME/omamessenger`, created and read only by this helper; an outgoing attachment's path comes from a file the local user picked through their own file manager, which is the user's own trusted action, not another process's unsolicited input, and is itself sanitized before anything decodes it (see "An outgoing photo attachment is sanitized before anything decodes it", above).
- **Environment variables:** `os.Getenv`/`os.LookupEnv` read a handful of values (`OMA_FAKE_DEMO`, locale variables for `spell.chooseLocale`, `HOME`/`XDG_*`), each a plain string compared or passed straight to a library that already validates it; none is indexed, decoded or type-asserted as structured data.
- **Goroutines started on data from outside the process:** every long-running goroutine `main.go` starts directly (`RunReminders`, `RunRetries`, `Ingest.Run`, the outgoing sweeper) terminates on `ctx.Done()` and runs code with no untrusted parsing of its own. `notify.Desktop.Notify`'s own per-notification goroutine is the one this review's own fix now recovers explicitly. `connector.Manager.launch`'s goroutine (one per connector account, via `supervise`) calls `c.Run(ctx, sink)`, which calls straight into `Ingest`'s `Sink` methods as a connector parses whatever the service just sent. `supervise` runs it through `runRecovered`, so a panic there becomes the fixed error "connector failed unexpectedly": the account shows as errored and the supervisor's usual restart-with-backoff takes over, instead of one malformed update crashing the helper and every other account with it. The error names nothing from the panic, since that could carry message content. Any other error a connector's run returns is shown the same way, as the fixed "Connection failed, retrying" (`connector.ConnectionFailedDetail`): a connector wraps its library's and the service's own errors, which can carry file paths, account ids or the service's own text, so none of that is stored or shown as the account's status.

## Sender-controlled counts: formatting spans, mentions, reactions, poll options and link preview text are capped once, at ingest

A review found `domain.TruncateIncomingText` capping a message's own `Text` at ingest, but nothing capping `Formatting`, `Mentions`, `Reactions` or a poll's own options, and `Ingest.Edited` not even sharing the `Text` cap with `Ingest.Incoming`/`History` - each ran its own, slightly different inline logic. A sender fully controls every one of these: Telegram's `spansFromEntities` converts every formatting entity a message carries with no cap of its own, and a poll's `optionsFromAnswers`/`pollCreationMedia` build one `domain.PollOption` per answer the service reports, however many that is. `ui/lib/Format.js`'s `styledHtml` is `O(ranges × boundaries)` - for every cut between two range boundaries, it re-filtered the full range list to find which ones were active over it - so an unbounded span or mention list would have made a single message's own rich-text render do unbounded work on the UI thread.

`domain.SanitizeIncoming(m Message) Message` (new, `backend/internal/domain/limits.go`) is the one function both `Ingest.save` (used by `Incoming` and `History` alike) and `Ingest.Edited` now call, so neither path can drift from the other's caps the way they already had: it truncates `Text` first, then caps `Formatting` and `Mentions` against the truncated text's own new length - dropping any span or mention left dangling past where the text now ends, the same way an edit that shortens a message already could leave one stranded - then caps `Reactions`, and bounds a poll's option count and text or a link preview's title, site name and description through `CapMedia`. Every cap is generous for anything a real client sends (Telegram's own apps cap a poll at 10 options, for instance) while still bounding what a hostile sender's own metadata can make a connector pass through unchanged:

| Collection | Cap | Where enforced |
| --- | --- | --- |
| Formatting spans per message | `domain.MaxFormattingSpans` = 256 | `domain.SanitizeIncoming`, at ingest |
| Mentions per message | `domain.MaxMentions` = 64 | `domain.SanitizeIncoming`, at ingest |
| Reaction chips per message | `domain.MaxReactions` = 64 | `domain.SanitizeIncoming`, at ingest |
| Poll options per message | `domain.MaxPollOptions` = 64 | `domain.SanitizeIncoming` → `CapMedia`, at ingest |
| Poll question / option text | `domain.MaxPollQuestionLength` / `MaxPollOptionTextLength` = 300 UTF-16 units | `domain.SanitizeIncoming` → `CapMedia`, at ingest |
| Link preview title / site name | `domain.MaxLinkPreviewFieldLength` = 300 UTF-16 units | `domain.SanitizeIncoming` → `CapMedia`, at ingest |
| Link preview description | `domain.MaxLinkPreviewDescriptionLength` = 2000 UTF-16 units | `domain.SanitizeIncoming` → `CapMedia`, at ingest |
| Group members per conversation | `domain.MaxGroupMembers` = 5000 | `app.Commands.Members`, on every fetch |
| Contacts per search | `domain.MaxContactResults` = 1000 | `store.Contacts`' own `LIMIT`, on every search |
| Reply quote text | `domain.ExcerptLength` = 80 characters | `domain.Excerpt`, already applied wherever a quote's text is filled in (pre-existing; confirmed, not changed) |

`ui/lib/Format.js` gained its own `MAX_FORMATTING_SPANS` (256) and `MAX_MENTIONS` (64), matching the Go caps independently (the same two-independently-maintained-but-matching pair `MAX_RICH_TEXT_INPUT_LENGTH`'s own comment describes, since this file has no way to import a Go constant): `messageHtml` caps both before choosing which rendering path to take, as defence in depth behind the helper's own ingest cap for a connector bug or an older helper still handing it an oversized list. `styledHtml` itself was also rewritten as a single sweep over the sorted boundary points - adding each range to a running "active" list exactly once, at its own start, and dropping it exactly once, at its own end - rather than re-filtering every range for every boundary in between, so a message built from many overlapping spans no longer does quadratic work even within the capped range.

## A reaction's own tally bypassed every ingest cap, through the connector's own cache

The caps above covered a reaction tally once it reached `Ingest`, but not the two places a live reaction actually enters the helper. WhatsApp's `Connector.reactTo` (called from `handleReaction` in `live.go` and `React` in `react.go`) folded a sender's `ReactionMessage.Text` - any string, any length, naming any message id - straight into `c.reactions`, a `map[string]map[string]string` keyed by `"<conversation remote id>/<message remote id>"`, with nothing ever evicting an entry: a sender naming an endless stream of message ids, real or entirely fabricated, grew it forever, and the recomputed tally this builds went to `Ingest.Reacted` uncapped. `Ingest.Reacted` itself then called `store.SetReactions` with that tally exactly as given, never through `domain.SanitizeIncoming` or `CapReactions`, so neither the chip count nor one chip's own emoji text had any limit by the time it reached the store and the UI. `ui/components/ReactionChips.qml`'s chip `Text` had no `elide` and sized itself from `implicitWidth`, so an oversized emoji string would have stretched the chip itself rather than being cut off.

Fixed in three places:

- `domain.CapReactions` (`backend/internal/domain/limits.go`) now drops a reaction whose own emoji text exceeds `domain.MaxReactionEmojiLength` (32 UTF-16 units; dropped outright, never truncated, since cutting an emoji mid-cluster renders as mojibake) before capping the tally at `MaxReactions`, so both ends of a reaction chip are bounded by the one function. `Ingest.Reacted` (`backend/internal/app/ingest.go`) now runs every tally it is handed through `domain.CapReactions` before calling `store.SetReactions`, the same cap `SanitizeIncoming` already gives a reaction arriving as part of a message. `store.SetReactions` already only updates a message already known to the store (confirmed, not changed; see `TestSetReactions_IgnoresAMessageThatIsNotStored`), so a reaction naming a fabricated message id was already dropped at that layer - the fix closes the gap further up, where the connector's own cache was growing regardless of whether the store would ever keep the result.
- WhatsApp's `reactTo` (moved into `backend/internal/connector/whatsapp/react.go`, alongside `React`) now treats an oversized emoji the same as an empty one (cleared), bounds `c.reactions` to `maxReactionTargets` (2000) distinct messages with FIFO eviction of the oldest once full, bounds one message's own reactor count to `maxReactorsPerMessage` (`domain.MaxGroupMembers`, refusing a new reactor past it rather than displacing an existing vote), and forgets a message's entry outright once its tally empties, so reacting then clearing repeatedly cannot pad the cache. Telegram's own `reactions()` (`normalize.go`) has no equivalent cache to bound: it rebuilds the tally from the server's own `tg.MessageReactions` on every update rather than accumulating one locally, so `Ingest.Reacted`'s own cap is the only one it needs.
- `ui/components/ReactionChips.qml`'s chip `Text` now sets `elide: Text.ElideRight` and bounds its own width to `maxChipTextWidth` (`Style.space(160)`), so an oversized emoji string elides instead of stretching the chip.

## Opening a link whose own visible text does not match its target asks first

The allow-list fix above ("Every URL this UI opens is checked against one allow-list") stops a disallowed scheme, but says nothing about a scheme-allowed link whose own visible text lies about where it goes. A review found Telegram's `MessageEntityTextURL` - a formatting span rendering as `<a href="…">` over a sender-chosen piece of text that can read as anything at all, including a different URL entirely (`backend/internal/connector/telegram/formatting.go`, `ui/lib/Format.js`'s `styledSegment`) - opened the same way any other link does, after only the scheme check: `WindowController.openExternalLink` never knew, and had no way to ask, whether what the person actually read before clicking was the real destination.

`ui/lib/Links.js` gained `needsConfirmation(displayText, url)`, a pure decision with its own node tests: true when `url` is a `mailto:` link carrying a query string (`?subject=`, `?body=`, `?attach=`, …, which can silently prefill a recipient, subject, body or attachment), or when `displayText` does not name the same destination as `url` once a scheme difference (`http` vs `https`), a leading `"www."` or a trailing slash is allowed for (`sameTarget`/`normalizeTarget`) - generous enough that an ordinary client's own auto-linking quirks never trigger it, while a link whose text claims a different site, or reads as plain prose, always does. `displayTextFor(text, spans, url)` recovers what the person actually saw for a clicked href: the matching `"link"` span's own text slice, or `url` itself when no span matches, which is always true for a plain autolinked URL (its own visible text is built from the same string as its href, so the two are identical by construction and this function's answer is moot for that case).

Every `linkOpenRequested(url, displayText)` signal - `MessageBubbleContent` (its `TextEdit`'s own link, and its `LinkPreview`), `AccountSetup`'s hint - now carries both, threaded unchanged through `MessageDelegate`, `ConversationView`, `MessengerLayout` and `Overlays` the same way it already carried `url` alone, to the one place that decides: `WindowController.openLink(url, displayText)`. A link preview's own `onOpened` and an account-setup hint's link pass `url` for both (a link preview's card never claims its own text is the URL; a hint is always a fixed, connector-written string per "A sign-in hint is always a fixed, connector-written string" above), and the palette's "links" mode and the `o` key's single-link case do the same, since `Highlight.links` only ever finds a bare autolinked URL in a message's raw text, never a formatting span's own link - the one case this fix is about can only be reached by clicking the rendered rich text itself.

`openLink` calls `Links.needsConfirmation` once, centrally, rather than at each call site: a mismatch opens `LinkOpenConfirm` (new, `ui/components/LinkOpenConfirm.qml`, the same `ChoiceDialog` idiom `OpenRiskyConfirm` and `BlockConfirm` already use, wired into `Overlays.qml` the same way), showing the link's real target in full. Cancel is the Enter-reachable default, never Open, so a stray Enter can never follow a link nobody meant to read as safe; "Copy link" puts the real target on the clipboard instead, through a hidden, `readOnly` `TextEdit` kept in `WindowController` for exactly this (`_clipboardProxy` - `readOnly` so it is never itself a live editable field for `tests/qml/OverlayLifecycle` to flag, the fix that test itself guards against). A plain link whose text already is its own href, or one from a link preview, still opens straight away as before - the dialog exists only for the case a sender's own formatting can actually produce.

**A later review found this fix itself still had a gap.** `displayTextFor(text, spans, url)` recovered a clicked link's own visible text by matching the click's href - the anchor's own URL, which is all Qt's `onLinkActivated` ever hands back - against each span's URL in turn, returning the first one that matched. Two spans that carry the very same URL with different visible text write that identical href on both their anchors, so a click on either reports the same string to `onLinkActivated`, and a lookup keyed on that string alone has no way to tell which one was actually touched. A sender could give an honest-looking span (its own text is the URL itself, so clicking it alone would never need confirming) and a disguise span the same URL and unrelated text; a click on the disguise then matched the honest span first and reported its text instead, skipping the question entirely. `displayTextFor` also fell back to returning `url` itself when no span matched at all, which `sameTarget` always reads as a match - fail-open for exactly the case a lookup should have been least sure about.

The fix stops resolving a click by its URL at all. Every anchor `Format.messageHtml`/`styledHtml` writes - a formatting span's link, a table cell's or any other auto-linked bare URL - now gets its own private href, `oma-link:<index>` (`Format.linkHref`/`Format.linkIndexFromHref`), naming that anchor's own position rather than its destination, so two anchors sharing one URL now write two different hrefs and are never confused again. `Format.messageLinkAnchors(text, mentions, spans)` runs the exact same render as `messageHtml` and returns the ordered `{url, displayText}` list those indices point into - the one place a URL is read back for a click, always by position, never guessed from a string a sender controls. `Links.js`'s `resolveClickedLink(href, text, mentions, spans)` (replacing `displayTextFor`) looks an href's index up in that list and returns the one anchor it actually names. An href it cannot resolve - this file's own gone stale, or anything else - never falls back to assuming a match: it resolves to nothing at all when its scheme is not on `isAllowed`'s list (refused outright), or to the raw href as both its own `url` and an empty `displayText` otherwise, which `sameTarget` can never call the same destination, so it always asks rather than ever opening unquestioned. `MessageBubbleContent`'s `onLinkActivated` is the only caller: it resolves the href first, then reports `linkOpenRequested(url, displayText)` exactly as before, so `WindowController.openLink` and everything downstream of it needed no change at all. The palette's "links" mode, the `o` key and `Highlight.links` were already outside this specific gap, since they only ever find a bare autolinked URL already sitting in a message's raw text and pass that same string as both `url` and `displayText` - never a span's own href - so there was nothing for either of them to resolve by position or otherwise.

Nothing in this UI reads `TextEdit.hoveredLink` today - there is no hover tooltip naming a link's target before it is clicked - but anything that starts to must resolve it through `resolveClickedLink` first, the same as a click does: showing a raw `oma-link:<index>` href to a person would be meaningless at best, and showing the href as if it were the URL would silently undo this whole fix.

## A recovered panic's own value is never formatted with anything but %T

A review found `Server.call` logging `%v` of a recovered panic (`backend/internal/server/server.go`), and `HelperProcess.qml` copying the helper's stderr straight into the shell's own log on the strength of a comment ("the helper's diagnostics never hold message content") that this one call broke: Go lets any value be panicked with, including a connector's own error, a request's params, or anything else a bad handler happened to be holding, so `%v` could format message content straight into both the helper's own log and, through that comment's own assumption, the shell's log as well.

The fix is the one the comment already assumed held everywhere: `call`'s recover now logs only the method name and the recovered value's own type, through a new `server.PanicLogLine(method string, r any) string`, pulled out as its own function specifically so a test (`TestPanicLogLine_NeverIncludesTheRecoveredValuesOwnContent`) can prove it without needing to trigger a real panic through the RPC surface. `notify.Desktop.recoverPanic` already did this correctly (`%T` only), and `connector.runRecovered` logs nothing from the panic at all, mapping it to the fixed `errConnectorPanicked` instead - between the two, every `recover()` in the backend now treats whatever it caught as something that must never be read, only typed.

To close the class rather than one call site, `tools/nologcontent` gained a second check, `checkRecoveredFormatting`: it tracks every local variable assigned straight from `recover()` across a package, and reports one reaching any `fmt` or `log` call - Printf-family or not, and whether or not that particular call writes anywhere itself, since `fmt.Sprintf`/`fmt.Errorf` building a string from one typically feeds a log call immediately afterwards anyway - formatted with any verb but `%T`. A Print-family call with no format string at all, which still formats every argument with the default `%v`, and a non-literal format string, are both treated as unsafe outright, since neither can be verified. `tools/nologcontent/testdata/.../recover.go` adds fixtures for a safe `%T` use, `%v`, `%s`, a bare `Print` call, and the value formatted through a `fmt.Errorf` wrapper the check still has to look inside; `TestStandaloneRunOnRealPackages` (which runs the real checker over the whole backend) confirms zero findings against the fixed code, and the same run against the original `%v` line (checked by hand, not kept in the tree) reproduces exactly the finding this check exists to catch.

## A message stored before the GIF-classification fix is reclassified by a migration, not re-guessed by the UI

A user report found a real GIF document received the day before "A video's actual bytes decide whether it animates as a GIF, never its filename or attributes" (above) landed still showed as a plain file chip with a "GIF" extension badge and never animated, even after upgrading: that fix changed what a newly received document normalizes to (`telegram/media.go`'s and `whatsapp/normalize_media.go`'s own `isGIFImage` case, `MediaVideo` with `Animated` true), but a message already written to `messages.media` as JSON before the fix shipped keeps whatever `domain.Media` it was given at the time - `MediaFile` with just a file name - forever, since nothing re-normalizes a stored row on its own. Checking the fix end to end for a newly received document found every other step already correct: classification, `imageProfile`'s routing through `imagesafe.FullImage` on fetch, `app.Commands.DecodeAsForMedia`'s byte check, and `InlineVideo.qml`'s click-to-fetch, decode-once-confirmed rendering were all already in place and already tested (`backend/internal/connector/telegram/media_test.go`'s "gif image document", `app/media_decode_test.go`'s `TestDecodeAsForMedia_SanitizesAGenuineGIFAndReportsIt`). The one gap was old data.

The fix is a migration, not a runtime guess: `migrate.go`'s new step runs once per database, the same as every other migration, and updates every stored message whose media is valid JSON, `kind` is `"file"`, and `fileName` ends in `.gif` (case-insensitively) to `kind: "video"`, `animated: true` - exactly `isGIFImage`'s own fallback shape when a sender's mime type was never captured, which `domain.Media` never persists in the first place, so a stored row has only its file name left to judge by. It uses SQLite's own `json_set`/`json_extract`/`json_valid` (`modernc.org/sqlite` compiles the JSON1 extension in; confirmed directly rather than assumed) rather than a Go-side row-by-row rewrite, since every other migration is already plain SQL applied once under `migrate`'s own version gate, and this one needs no more than that. Reclassifying a row this way changes nothing about how it is ever decoded: the UI still only ever trusts `app.Commands.DecodeAsForMedia`'s check of the downloaded bytes themselves (see the entry above), so a message this migration reclassifies wrongly - there is no such case today, but the discipline holds regardless - can only ever fall back to opening externally, never animate anything unsafe. `TestMigrate_ReclassifiesAStoredGIFDocumentAsAnimatedVideo` runs the new step against a hand-inserted pre-fix row, an ordinary file, an ordinary video and a message with no media at all, and confirms running the same `UPDATE` a second time leaves an already-reclassified row untouched.

The fake connector's own seeded data got the same real GIF document it was missing before (`backend/internal/connector/fake/gif.go`'s `placeholderGIF`, a tiny genuine animated GIF generated the same way `placeholderPhoto` paints a procedural JPEG, since this module has a real GIF encoder unlike voice's Opus): Nadia's newest message in the default test fixture, and Design Team's in the README demo recording, so `make test-qml` and `make demo` both exercise the fetch-then-animate path through a real helper process, not only through Go unit tests. `tests/qml/Flows`'s smoke suite drives it end to end - opening Nadia's chat, clicking her GIF message once to fetch it, and confirming `InlineVideo`'s `realGifImage` becomes visible rather than its thumbnail or play mark - the one place this suite's own rule allows re-checking an outcome already proved in detail elsewhere (`tests/qml/InlineVideo`'s own component test), because it is the only layer that can prove the real helper's `media.fetch` response actually reaches a real, running component through a real click.

## A brief confirmation moved out of the banner row into its own toast, so it is not only an error that gets a dismissible notice

The top-of-window banner row (`errorBanner` in `ui/Panel.qml`) used to show two unrelated things in the same place: a helper error, and a brief, non-error confirmation ("Copied to clipboard", "Saved to …", the one-time "Updated to vX" hint), merged through `WindowController.bannerText`/`bannerIsError`. Tim reported the confirmation case was too easy to miss there - it sits at the very top of the window, where nobody is looking right after pressing `c` or `s` on a message lower down.

`ui/components/Toast.qml` is a small, rounded pill anchored above the composer instead, close to where the action that triggered it just happened. `WindowController.toastText` replaces `noticeText`, computed through a new pure function (`ui/lib/Toast.js`'s `pickText`, node-tested) that keeps the same priority the inline banner logic had - the update hint wins the one time it has something to say, falling back to `ConversationController.notice` otherwise - and `displayText` pairs the shown words with a leading checkmark glyph so the toast is never read by its (quiet, non-urgent) colour alone. The error banner keeps its row, now unconditionally red and tied only to `errorBannerText`: the two notices no longer compete for the same strip and can both be visible at once.

The toast owns its own auto-dismiss timer (`dismissDelayMs`, a property rather than a literal so a test can shrink it) rather than `WindowController` running a second timer alongside the error banner's: hovering the pill stops that timer outright and a fresh full delay starts once the pointer leaves, which is a close enough reading of "pauses" for a transient confirmation nobody is meant to study. Dismissing it by Escape needed a new rule the error banner never had: `Navigation.escapeAction`'s `dismiss-toast` step only fires while focus is not in a text field (`!composeFocused && !searchFocused`), so pressing Escape to leave the composer or clear a search is never swallowed by a toast that happens to be showing at the same time - the error banner, by contrast, stays unconditional, since an error demands attention regardless of what has focus.

## An animated GIF's total decoding work is bounded, not just each frame

`imagesafe` checked an animation's canvas and every frame against the profile, and capped the frame count at 1024, but nothing bounded frames times canvas. GIF's compression can carry a single-colour 40-megapixel frame in about 15 KB, so a file well under the download caps could hold a thousand such frames, and Qt's `AnimatedImage` decodes the whole canvas for every frame on the shell's own thread. Every profile now carries `MaxTotalPixels`, checked against canvas pixels times frame count for both GIF and animated WebP. Real GIF files get their own `AnimatedGIF` profile (at most 2048 pixels a side, about 4 megapixels a frame, 400 megapixels a loop), far below `FullImage`'s still-photo limits, which now allow a single frame only. In the UI, a real GIF animates only while it holds the single decoding slot every video shares, and neither `AnimatedImage` caches its decoded frames.

## A link preview's URL is the sender's, not the link the message shows

A link preview card's URL comes from the sender's own client (WhatsApp's `matchedText`) or from the linked page's own tags (Telegram), apart from the text the bubble shows and the card's own title. So a message reading "https://www.paypal.com/refund" could carry a PayPal-titled card that opens somewhere else entirely. WhatsApp's connector now keeps a preview's URL only when the message text itself contains it. In the UI, clicking a card whose URL the text never shows passes the card's title as what the person saw (`Links.previewDisplayText`), so the same "this link goes somewhere else" question a mismatched formatted link gets asks first. The open key (`o`) reaches only links visible in the text, never a preview's own URL.

## A composer's attachment preview only shows a file the helper has already sanitized, never guessed from its extension

"An outgoing photo attachment is sanitized before anything decodes it, the same as a downloaded one" (above) closed the gap at send time: `Send` now runs `imagesafe` over a picked file before it is ever decoded. A further review found the gap still open earlier: picking a file in the attach dialog put its path straight into `attachmentPath`, and `Composer.qml`'s chip decided whether to show a decoded `Image` preview from `Format.guessMediaKind`, a guess from the file's own extension - `imagesafe` never ran until the message was actually sent. A received file saved unchanged to Downloads (a crafted `photo.png` declaring huge dimensions, say) and then attached was decoded in the shell's own process before any check ran at all. The "Untrusted images are sanitized..." entry's claim that bounding `sourceSize` already covered the composer's own preview, corrected above, was the same mistake in miniature: `sourceSize` only scales what Qt keeps after its PNG, GIF or BMP decoder has already decoded the file at its own declared size, so it bounds nothing for a file that reaches it before any real check has run - only JPEG can be decoded pre-scaled, through libjpeg's own DCT scaling. A pasted image was not exposed to this, since `media.paste` already sanitized before returning a path; a picked file had nothing in front of it at all.

`media.attach` (`backend/internal/server/attach.go`'s `mediaAttach`, calling the new `app.Commands.AttachFile` in `backend/internal/app/attach.go`) gives a picked file `PasteImage`'s own treatment: it copies the file into the outgoing media area and, when it looks like a photo, runs it through `imagesafe`'s `FullImage` profile, reusing `prepareAttachment`, `storeAttachment` and `describeAttachment` - the same pipeline `Send` already ran at send time - rather than duplicating them. It returns the new path, the kind the file's bytes actually are, and the file's own picked name (the stored copy's own base name carries an internal id, not the name the user recognises). An oversized or unsafe image is refused outright with the same safe, fixed message `Send` already gives one attached straight off disk: one rule for every path an attachment can enter, rather than a refusal at send time but a silent decode at pick time for the same file.

`ComposerController.attachFile` calls `media.attach` as soon as a file is picked, before `attachmentPath` is ever set, with the same staleness guard `pasteImage` already uses for `media.paste`. `attachmentPath`, the new `attachmentName` (for `Send` to keep the file's real name once sent) and `attachmentKind` are set only once that finishes; a refused file reports through the open conversation's error banner instead. `Composer.qml`'s chip shows a decoded preview only when `attachmentKind` is `"photo"`, the helper's own verdict, never `Format.guessMediaKind`'s extension guess, now dead code and removed along with its test; `tests/unit/bounded-image-source.test.cjs` gained a guard against it coming back. `messages.send`'s `attachment` param gained an optional `name` field for this, additive to the existing `path`.

`Send` reuses whatever path `media.attach` or `media.paste` already prepared by moving it into place under the message's own id (`attachment.go`'s `reuseAttachment`), rather than copying and sanitizing it all over again: a path already inside the outgoing media area (`attachedFromDisk` false) is never treated as a fresh disk pick. This also fixes an existing inefficiency on the `media.paste` side, which `Send` was quietly copying and re-sanitizing a second time on every send; neither path keeps the original file to recopy from if the outgoing copy goes missing before the message is sent, the same as a pasted image already did not, so a retry in that one narrow case fails cleanly asking the user to attach again rather than resending something unverified.

## Notifications name no sender and show no text by default

Notifications go to Omarchy's notification service over D-Bus, never as process arguments. But that service then saves every notification it shows by starting a short-lived `bash` process with the whole notification, summary and body, as one of its arguments, and writes it to files under `~/.local/state/omarchy/notifications/`. Any other local user who can read `/proc/*/cmdline` could see a message's sender, chat and text that way. That is Omarchy's behaviour, not something this plugin can change from its side, so the default notification detail is now "Nothing": a generic "New message" with no name or text. The **Notification detail** setting still offers the sender, or the sender and the text, and its description says what Omarchy does with them.
