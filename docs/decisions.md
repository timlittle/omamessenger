# Decisions

Design choices that are not obvious from the code, and why they were made. Read the relevant entry before reversing one; if you do reverse it, update the entry.

## JSON-RPC over the helper's stdin and stdout

The UI and helper talk JSON-RPC 2.0, one object per line, over the helper's stdin and stdout. The alternative was a Unix socket.

- Quickshell's `Process` gives the UI the helper's stdio for free, and Omarchy's shell already owns the process. With stdio there is no socket file to place, protect or clean up, no address to discover, and no other local process can connect.
- A local pipe is as fast as a local socket. Traffic is a few messages a second at human pace, so neither would be the bottleneck.
- The helper lives exactly as long as the UI's process handle: when the shell stops it, stdin closes and the helper exits.

## sourcegraph/jsonrpc2 instead of our own framing

The helper uses `github.com/sourcegraph/jsonrpc2` rather than hand-written line framing and dispatch. A maintained library handles request ids, concurrent replies and notifications, and the UI speaks a documented standard.

Trade-off: a line that is not valid JSON closes the connection. The UI only sends `JSON.stringify` output, and the UI's service restarts the helper if it exits.

## A failed send is a message, not an error

`messages.send` returns the stored message with status `failed` when the service refuses it, instead of an error. The UI already shows failed messages with a retry action, so an error would report the same thing twice.

## The app layer uses the concrete store

`app` takes `*store.Store` rather than an interface. There is one store, and tests use a real SQLite database in a temporary directory, so an interface would only mirror its methods. Interfaces are used where there are real alternatives: connectors, desktop notifications and the UI connection.

## Real time in code, synctest in tests

There is no clock interface. Code uses the `time` package, and tests of timing (connector restarts, the fake connectors' delays) run inside `testing/synctest`, where time advances instantly and deterministically.

## Release binaries, installed automatically on first open

Helper binaries are published on GitHub Releases with `SHA256SUMS` and build provenance, never committed. `helper-version` names the release, and `scripts/install-helper.sh` downloads and verifies it.

`omarchy plugin add` only clones the repository; by Omarchy's design a plugin has no install hook to run afterwards. Asking the user to then run a script or press a separate "Install helper" button made OmaMessenger a two-step install when every other plugin is one — Omarchy's own Spotify plugin resolves the same gap the same way. So the window now runs the installer itself, the first time it opens and finds the helper missing or pinned to a different version than `helper-version` (a plugin update changes that file, and the launcher looks for a binary named after the new version, so it is "missing" again until the next open installs it). It shows a quiet "Installing the helper…" state and starts the helper on success. A failed install (offline, a bad checksum, no release yet) shows the error with a Retry button, the only remaining manual path; it does not retry on its own on the next open, and it never touches a working helper already in place, since the installer verifies into a version-named temporary file and only `mv`s it over the version-named destination after that check passes.

Verification — the release's `SHA256SUMS` and the binary's own reported version — stays mandatory either way. Loading the plugin itself still never downloads anything: the trigger is opening the window, never the shell starting. A local `make build` in `bin/dev/` still takes precedence, for development.

## No vendor directory

Go dependencies come from the module cache, pinned by `go.sum`. Committing `vendor/` added about 1,800 files to every review for little benefit.

## Existing tools before custom ones

Lint and coverage rules are configuration for golangci-lint (`.golangci.yml`) and go-test-coverage (`.testcoverage.yml`). The only custom check is `tools/nologcontent`, which keeps message content out of logs, because no existing tool knows which values are private.

## No compositor tests

Automated tests do not start Hyprland or Docker. They were slow and caught little that unit, offscreen QML and helper tests did not. Visual and window-manager behaviour is checked by hand in the installed plugin.

## A typed adapter for Omarchy's theme tokens

Omarchy declares nested token groups (`Style.font`, `Color.popups`, …) as plain `QtObject` properties, so Qt 6 qmllint reports every use as a missing property. `ui/theme/Theme.qml` re-exports them with types, which keeps lint at zero warnings and still catches typos. It is the only file allowed to suppress that warning.

## Fake accounts only in test builds

The scripted fake connectors that tests run against are compiled in only with the `fake` build tag (`make build-fake`). Release builds cannot show seeded data, so it can never mix with real messages, and the product has no demo mode to explain.

## Providers behind one interface

Adding an account used to mean `backend/accounts.go` and `app.AddAccount` both knowing Telegram's rules: its credential shape, its app keys, its id prefix. `connector.Provider` moves all of that behind one interface (`Service`, `Name`, `Prepare`, `Connect`, `Forget`) that each service's own package implements. The registry becomes a map of providers, keyed by service id, and `app.AddAccount` only maps a provider's `ErrInvalidSetup` or an unknown service to invalid input; it no longer validates API keys itself.

Prepare takes a plain `map[string]string` rather than a typed options struct, because each service's setup is different (Telegram's API id and hash today, something else tomorrow) and the protocol already carries them as JSON strings. The cost is that a provider must parse its own options and return `ErrInvalidSetup` with a safe message when they are wrong; that cost sits in the one package that knows what valid means for that service, which is the same trade `Provider` makes everywhere else.

`accounts.add`'s `apiId`/`apiHash` fields stay as they were, merged into `options` by the server before they reach `app.NewAccount`, so no existing UI build and no saved Telegram account's `tg-` id prefix breaks. New accounts get an id prefixed with their service name instead, since the registry no longer special-cases Telegram's.

## Clicking a notification: notify-send's "default" action, not D-Bus

A message notification carries its conversation id so clicking it can open that conversation. `notify-send -A default=Open` registers the freedesktop "default" action and blocks (`--wait` is implied) until the notification closes or an action is chosen, printing the chosen action's name to stdout. Omarchy's own notification daemon (`/usr/share/omarchy/shell/plugins/notifications/Service.qml`, `invokePopupDefault`) already treats a live notification's `default`-identified action as "clicked the body", falling back to focusing the sending app's window only when no such action is registered — so this needed no change on Omarchy's side.

The alternative was a D-Bus session connection from the helper, watching `org.freedesktop.Notifications.ActionInvoked` directly. notify-send's stdout is simpler: it is already the helper's only way to show a notification, needs no new dependency, and keeps the daemon itself unaware that OmaMessenger exists. The cost is one goroutine per notification, blocked in notify-send until it closes; `notify.Desktop` bounds that with a timeout so a notification that is somehow never closed cannot leak it.

## Sending photos and files

`domain.Media` gained a `Path` field, tagged `json:"-"`, rather than a separate type the server and connectors pass alongside a message. A dedicated field (as the brief suggested as an alternative) would mean threading a second value through `Commands.Send`, `Retry` and every `Dispatcher`, when the local file is really one more thing media about an outgoing message; `json:"-"` keeps it out of the wire protocol (the UI already knows the path it offered; a remote message has none) without adding a parameter everywhere Media already travels.

The outgoing media area (`cache.Outgoing`) names a stored file by the message's id and its original file name (`<id>-<name>`), set before the message is first stored by generating the id in `app` rather than letting the store assign one. `domain.Media.Path` cannot survive a reload from the store (it is deliberately excluded from the JSON column), so `Retry`, which re-reads the message from the store, recomputes the same path from the id and file name it does keep, instead of needing Path to persist.

A captionless attachment reuses the existing placeholder convention for media (`domain.MediaPlaceholder`, the same `"[Photo]"`/`"[Video]"`/`"[File]"` labels a connector already gives incoming media with no caption) rather than allowing an empty stored message. The UI already hides a caption that exactly matches its media's label, so this needed no UI change; the Telegram connector strips the placeholder back to an empty caption before sending, since it is a local display convention, not real text to deliver.

The file chooser is `QtQuick.Dialogs.FileDialog`, used directly from the composer. The plugin's manifest only offers `service`, `panel` and `bar` entry points, not a new Omarchy overlay like `image-picker` (which is also scoped to one fixed directory of images, not an arbitrary file), and `xdg-desktop-portal` is already running on the test machine with a Hyprland and a GTK backend registered; loading `FileDialog` under the offscreen platform showed Qt routing its `open()` straight at that portal (it only failed here on the portal's own sandbox permission check, not on anything Quickshell-specific). `FileDialog` needed no new helper method, so this is the simpler of the two options the brief allowed for.

Pasting an image goes through a new `media.paste` method instead of teaching the UI to read the clipboard, because Qt's QML has no cross-process way to read Wayland clipboard data (only `wl-paste`, a separate process, does); the helper already shells out to external processes for notify-send, so one more for `wl-paste` keeps that logic out of the UI. The composer always intercepts Ctrl+V while composing and asks the helper first; when the clipboard has no image, the composer is told to fall back to a plain native paste, rather than the key router trying to guess the clipboard's contents before deciding whether to intercept the key at all.

`PhotoView`'s "fall back to the blurred preview, or a quiet message when there isn't one" rule only ever triggered off `Image.onStatusChanged` reporting an error, which needs a non-empty `source` to begin with. A photo with neither a thumbnail (common for older or history-synced media) nor yet a successful download has an empty `source` (`""`), so that `Image` never attempts to load anything and never reports an error: the "unavailable" message never showed, leaving a plain empty box forever once the one silent, un-reported auto-fetch attempt (`ConversationController.fetchMedia`) had failed. The fix is a `mediaFailed` flag on the timeline row (`Timeline.row`, `MessageTimeline.setMediaFailed`), set whenever `downloadMedia`'s request errors regardless of whether the user asked for it or a photo was fetching itself quietly, and read by `PhotoView.failed`; `_unavailable` now also triggers off it rather than only off `Image`'s own load failure, so a thumbnail-less photo whose fetch is known to have failed shows "Photo unavailable" instead of staying blank. A photo that does have a thumbnail still falls back to it on the same failure, unchanged.

## Reactions: a Sink method of their own, one reaction per person, custom emoji skipped

Telegram reports a reaction change two ways: a full `UpdateEditMessage`, which carries the message's new text, media and reactions together, and `UpdateMessageReactions`, which carries only the peer, message id and the new reaction counts. The first already fits `Sink.Edited`, since `EditMessage` was going to need a `reactions` argument anyway. The second does not: `Edited`'s contract replaces a message's text and media unconditionally, so feeding it empty values from a reactions-only update would blank out a message's real content. Fetching the full message first to avoid that would cost a network round trip for every reaction click, just to reuse one method. `Sink` already accepts this kind of growth (`Organized` was added the same way for pin and archive sync), so a second method, `Reacted`, carries just the reaction chips, and the store gained `SetReactions` to match: it touches only the `reactions` column.

The UI sends one emoji per `messages.react` call, not a set, and `Reaction` has no way to say "pick several". Telegram's API allows more, but `messages.sendReaction` takes whatever list is given, so sending a single reaction already replaces any previous one from the same person; a second reaction would need its own chip, its own click target and its own place in the picker for a case most chat UIs do not offer either. `Reactions.emojiToSend` (`ui/lib/Reactions.js`) encodes the one-reaction choice: clicking a chip that is already the user's own clears it, and any other pick replaces it.

A custom emoji reaction (`tg.ReactionCustomEmoji`, a sticker rather than a character) is left out of `reactions` entirely rather than shown as a generic placeholder. Telegram's own clients render the actual sticker, which this UI has no way to draw; a placeholder chip would look like a real reaction with the wrong picture, which is worse than one chip fewer.

## WhatsApp's session database uses the same pure-Go SQLite driver as the message store

whatsmeow's `sqlstore.Container` normally opens its own `*sql.DB` by calling `sql.Open` with a dialect string that doubles as the database/sql driver name, which is how its own examples register `mattn/go-sqlite3` (cgo) or `sqlite3-fk-wal`. The helper is built with `CGO_ENABLED=0`, so that path is out. Reading `go.mau.fi/util/dbutil`'s source showed the fix needs no library change: `ParseDialect` only checks that the string has a `sqlite` prefix to pick its SQL quirks, and `sqlstore.NewWithDB` takes an already-open `*sql.DB` and that same string separately, never calling `sql.Open` itself. So the connector opens its own connection exactly as `store.Open` does, with `modernc.org/sqlite`'s pure-Go driver registered under the name `"sqlite"`, and hands both the `*sql.DB` and the string `"sqlite"` to `sqlstore.NewWithDB`; dbutil accepts it as a `sqlite` dialect and generates the right SQL, with no cgo anywhere in the build.

## WhatsApp pairing wraps whatsmeow's client behind a small `device` interface

Unlike gotd/td, which already exposes its lowest-level RPC transport as the `tg.Invoker` interface Telegram's own tests fake, `*whatsmeow.Client` has no such seam: `Connect`, `GetQRChannel`, `PairPhone` and the rest are concrete methods with no public way to substitute a fake network underneath them. `backend/internal/connector/whatsapp/device.go` defines `device`, an interface over exactly the whatsmeow calls the connector and its pairing sequence need (connect, disconnect, close the session database, check whether it is already paired, log out, start a pairing attempt and watch its QR codes, pair by phone, and watch for connected/disconnected/stopped status) so `Connector.Run`, `pair` and their tests drive a hand-written fake instead of ever reaching WhatsApp's servers; `waDevice` is the one production implementation, adapting a real client to it. This is the same shape `connector.Connector` itself and Telegram's `authAPI` already use.

QR and phone pairing share the one `device.qrCodes` channel rather than two separate interface methods, because that is how whatsmeow itself works: `GetQRChannel` keeps running and reports the same final "success" or "error" event no matter which way pairing actually finished, so `pair`'s loop just also watches for a phone number answer on the side and calls `pairPhone` when one arrives, instead of juggling two completion signals for one outcome.

## WhatsApp's account removal logs out the connected device, best effort, then deletes the local session

`connector.Provider.Forget(dir, accountID string) error` still carries no context and no live connection, so it only ever deletes local files, exactly as Telegram's `Forget` does. But a WhatsApp connector that is still running when the user removes it has a live connection worth using: `connector.LogoutOnRemove` is a capability interface with one method, `Logout(ctx) error`, that `Manager.Remove` type-asserts on the connector it is about to stop. When the running connector implements it, `Manager.Remove` calls `Logout` with a bounded `context.WithTimeout` before cancelling the connector's own context, since cancelling first would close the connection `Logout` needs; the result is ignored (commented at the call site), because the local session is deleted either way. WhatsApp's `Connector` tracks the `device` its `Run` is currently using in a mutex-guarded field and implements `Logout` by calling the device's `logOut`. This is why the capability is a new optional interface rather than a change to `Forget`'s signature or to `Connector`: `connector.Connector` and `connector.Sink` stay the stable, published boundary, and a connector that cannot log out (or is not running) just does not satisfy it.

Telegram has no such connection to use here and does not implement `LogoutOnRemove`; its account's session lapses from the server's own view once it stops being used, the same as before.

## WhatsApp's media references live in their own database, not whatsmeow's session

A message's photo, video or file carries a `mediaRef` (direct path, media key, file hashes, length and mimetype) that a later wave's `MediaFetcher` will need to download it, since WhatsApp's end-to-end messages have no server-side copy to re-fetch a reference from the way Telegram's do. This connector saves that reference as soon as a message arrives, in its own SQLite database beside the account's whatsmeow session (`<account>-media.db`, mode 0600, like the session itself) rather than as an extra table inside that session's database. whatsmeow's `sqlstore.Container` owns that schema and upgrades it on its own terms; adding a foreign table to it would work today but ties this connector's data to whatever whatsmeow's own migrations do next. `Provider.Forget` deletes this file alongside the session when an account is removed.

## WhatsApp's chat organizing and naming caches live in memory for the process's lifetime

Pin and archive events from the phone (`events.Pin`, `events.Archive`) each report only the one flag that changed, but `Sink.Organized` takes both, so the connector keeps a `remote id -> {pinned, archived}` cache, seeded from history sync and updated by each event, and always reports the merged pair. Reaction chips work the same way: WhatsApp reports one person's reaction change at a time, never a conversation's full tally, so a `remote id -> {sender -> emoji}` cache is kept and recomputed into the chip list `Sink.Reacted` expects on every change. Group and contact names resolved to fill in a blank title (see below) are cached too, so a group is never asked for its name twice.

All three caches are fields on `Connector`, surviving a reconnect within the same helper process, but starting empty again after the helper itself restarts, same as Telegram's own `remotes`/`sent` caches. A live organizing or reaction event arriving before anything has repopulated the cache falls back to the one flag it actually carries (the other defaults to false) or reports a fresh tally of just itself; a subsequent history sync corrects it. This was accepted rather than built out further because the store's own copy of pinned, archived and reactions is the durable one, and a transient, self-correcting gap right after a restart was judged cheaper than giving this connector a way to read state back out of the store it only ever writes to.

## WhatsApp's unnamed conversations fall back to a resolved or generic name, never to no name at all

`store.EnsureConversation` drops a conversation with no title rather than creating or updating one, since the UI has nowhere to show a nameless chat. History sync does not reliably carry every conversation's display name: a direct chat's name comes from a separate push name list in the same sync blob (processed first, so it is cached before the conversation list needs it), and a group's name is sometimes missing and has to be fetched with `GetGroupInfo`, bounded by a short timeout and cached so a slow or unreachable group is asked for once. When even that resolves to nothing, a group falls back to the literal title "Group" and a direct chat falls back to its phone number (`"+" + the JID's user part`), the way WhatsApp's own clients show an unsaved contact, unless the JID is a hidden id (a LID) rather than a phone number, which gets the neutral label "Unknown contact" instead: its digits are not a phone number, and showing them as one is worse than admitting the name is not known. The account's own self-chat is a third case, titled with the fixed label "Message yourself" rather than resolved at all, since nobody has themselves saved as a contact. The same resolution runs for a live message's chat when it arrives before any sync has reached it.

A JID on WhatsApp's default server is always a phone number, but one addressed by a LID (`@lid`) is a hidden id the server assigns instead, used increasingly often for both chats and group senders. `device.contactName` resolves a LID to its phone JID through whatsmeow's own LID store (`Store.LIDs.GetPNForLID`) and looks the result up in whatsmeow's local contact store (`Store.Contacts.GetContact`), trying the LID itself first since a few contacts are keyed by LID directly. Both are pure local reads already synced to this device by whatsmeow's own app-state processing; neither does network I/O, so resolving a title or a sender's name never blocks on it. `contactDisplayName` picks WhatsApp's own best name for a resolved contact: its saved full name, first name, verified business name, then its push name, in that order, before this connector's own `senderName` falls further back to the message's own push name and finally the generic "WhatsApp user".

Contacts and push names often finish syncing moments after history sync already titled a chat with a fallback: `events.Contact`, `events.PushName` and `events.AppStateSyncComplete` are handled in `contacts.go` to re-title the affected conversation once a better name is known, without needing to re-pair. A `remote id -> {name, rank}` cache (`Connector.names`, rank one of "push name" or "contact", the latter always winning) makes sure this can only ever improve a title, never replace a good one with a worse one, no matter how many times or in what order a conversation gets re-reported; `AppStateSyncComplete` carries no JID of its own, so it rechecks every direct chat this connector has ever reported (`Connector.chatKinds`), each check a local lookup, never a network call. Existing stored messages whose sender was saved as "WhatsApp user" before their contact resolved are not corrected retroactively: only a new report, live or re-synced, gets the better name, matching how `store.refreshConversation` only ever overwrites what the connector sends it next.

History sync also delivers entries for JIDs that are not a conversation with anyone: the status broadcast, old-style broadcast lists, newsletters, and WhatsApp's own "0" system account (`0@s.whatsapp.net`), which would otherwise title as the meaningless "+0". `isSystemJID` recognises these and they are dropped outright, in both history sync and a live message, rather than ever reaching `Sink.Conversation`.

## WhatsApp's own protocol and system notices, and a few content kinds this UI cannot render yet, never become a visible "[Message]"

WhatsApp's wire format carries many message kinds that are not something a person actually sent: besides a reaction, an edit and a revoke, which were already pulled out as their own events, a `ProtocolMessage` covers ephemeral-setting changes, app-state key shares, history-sync notices and a long tail of similar housekeeping, and a poll vote, a pin-in-chat and a keep-in-chat flag are likewise just state changes on an existing message. None of these carry text, a caption or any media, so without a check they fell through to `mediaPlaceholder`'s default case and showed as the content-free, confusing "[Message]", both as a stored message and as a list preview. `isContentless` recognises every one of these kinds; `historyMessage` drops them the same way it already drops a reaction, an edit or a revoke, and the live dispatch in `live.go` skips them before anything is reported at all, so none of them is stored or shown. A real content kind this UI does not render yet keeps its own specific placeholder instead of the generic one: a poll's question (`"[Poll: …]"`), a shared contact's name (`"[Contact: …]"`) or, with neither, the bare `"[Contact]"`/`"[Poll]"` already in use, and location sharing's existing `"[Location]"`.

## WhatsApp's self-chat ("Message yourself") is a real conversation, not an outgoing echo to skip

Every message in the account's chat with itself is, by WhatsApp's own protocol, "from me": there is no one else to have sent it. The live handler's existing rule — only ensure a chat exists for an *incoming* message, since an outgoing one WhatsApp echoes from another of this account's devices carries no reliable name and was never unread — meant the self-chat's conversation was never created from a live message at all, and a heavily used one (so OpenClaw's own notes, in this account's case) could end up with no conversation to store its messages in even once history sync had a chance to deliver it. `device.isSelfChat` reports whether a JID is this account's own phone JID or its LID (either may address it), checked ahead of that `IsFromMe` rule in both `handleContent` and `ensureChat`, and ahead of the regular title resolution in history sync's own `resolveConversation`, so the self-chat is always ensured and always titled with the fixed label "Message yourself" rather than whatever its (nonexistent) contact or push name would otherwise resolve to. Its messages still flow through the ordinary "outgoing, from me" path afterwards: reported as history, carrying `SenderName: "You"`, never counted as unread, exactly as any other message this account sent itself from another device already was. Sending to it goes through the ordinary `Send`, unchanged: WhatsApp addresses it like any other chat, and a message this connector sends is deduplicated against WhatsApp's own echo of it the same way every chat's own echoes already are, by the message's remote id.

## WhatsApp's older history on scroll is not implemented

`connector.HistoryLoader.LoadOlder` is left unimplemented for WhatsApp in this wave: scrolling past what history sync already delivered loads nothing more, the same as a connector with no `HistoryLoader` at all. whatsmeow exposes `BuildHistorySyncRequest`, but it is not a request/response call — it builds a protocol message that has to be sent to the user's own primary device, which replies, asynchronously and without a correlating id, with another `events.HistorySync` of type `ON_DEMAND` whenever the phone gets to it. Matching that reply back to the specific `LoadOlder` call that asked for it, across however many are in flight, is not a seam `whatsmeow` gives a caller; building one would mean guessing at protocol behaviour this package cannot verify without a live account, which the test suite cannot reach. History sync's own bootstrap already delivers a worthwhile amount of recent history per conversation, so this was judged not worth that risk for a first wave. The README notes the limit.

## WhatsApp's mute state from the phone is not synced

`events.Mute` is received and intentionally dropped rather than reported anywhere: `connector.Sink` has no method for it, by design. `Sink.Organized` carries pinned and archived because `store.SetOrganized` keeps both in step with the service; the store's `muted` column has no equivalent sync path at all; `store.refreshConversation`, which `EnsureConversation` uses to update an existing conversation, deliberately never touches it, and the only way to set it is the UI's own local `conversations.setMuted` command. Muted is, by this app's existing design, a local preference rather than a synced one, the same as `hidden`. Adding a new `Sink` method just for WhatsApp's mute changes would be a bigger change than this one connector's wave justifies, given `connector.Sink` is meant to stay stable once a real connector ships; if muting from the phone turns out to matter, it is a Sink change to make deliberately, with Telegram's own mute considered at the same time, not a one-off for WhatsApp.

## WhatsApp's reactions and replies need a message's sender, so that is persisted too, in the same database as media references

Reacting to a message or quoting it needs WhatsApp's own key for that message: its chat, its id, and, in a group, who sent it, since a group reaction or quote has to name the right participant. WhatsApp gives none of that back on demand the way Telegram's message ids alone are enough to build a reply or a reaction; it has to be captured from whichever event first reported the message. `backend/internal/connector/whatsapp/keys.go` adds a `message_keys` table (conversation id, message id, sender id, from-me) to the same per-account database `storage.go` already keeps media references in, rather than a third database file: it is written to from the same three places a media reference is (a live message, a synced one, and a message this account just sent), so sharing the file means one database to open, close and eventually delete per account instead of two. `React` and `Send`'s reply-quoting both read it through `targetKey`, which sets a group's `Participant` only when the message was not sent by this account, mirroring whatsmeow's own `BuildMessageKey`; a direct chat never sets it, since its two parties are already identified by the from-me flag alone.

A message from before this connector tracked keys, or one `putMessageKey` failed to save, has no row to find: `React` reports `errUnknownReactionTarget` rather than guessing at a key, and a reply falls back to quoting by stanza id alone, the way every reply worked before this. WhatsApp still threads that reply correctly, since the recipient's own client already holds a copy of the message being quoted; only the richer quote (participant and a snippet of the quoted text) is lost.

## Release binaries are GPL-3.0; this repository's source stays MIT

whatsmeow (MPL-2.0, WhatsApp support) depends on `go.mau.fi/libsignal`, which is GPL-3.0. Linking it statically into the helper binary makes that binary a combined work, which the GPL-3.0 requires to be distributed under its own terms, regardless of what license the rest of the code carries. MPL-2.0 is compatible with this (MPL-licensed files may be combined into a GPL-licensed work); MIT is permissive enough to be relicensed the same way. So this repository's own source stays MIT (`LICENSE`), since nothing stops it being used under those terms directly from the repository, but each release's built binary is distributed under GPL-3.0 (`LICENSE-GPL-3.0`), because that is what the combined work it contains requires. The corresponding source for a given release is simply this public repository at the tag that release was built from.

`THIRD_PARTY_NOTICES`, generated by `make third-party-notices` (`github.com/google/go-licenses/v2`, pinned in the Makefile, run against `./backend`, which is what the release binaries build) lists every third-party component actually linked into the helper and its license in full, and is published in each release next to the binaries. `make license-check` runs the same tool in `check` mode against an allow-list (MIT, BSD-2/3-Clause, Apache-2.0, ISC, MPL-2.0, GPL-3.0) as part of `make check`, so a newly added dependency with a license outside that list fails the build instead of silently shipping. One dependency, `github.com/segmentio/asm` (pulled in by Telegram's `gotd/td`), is excluded from both: its `LICENSE` file reads "MIT No Attribution", a permissive MIT variant go-licenses' classifier does not recognise, so it reports the package as unclassified rather than guessing. It is covered by hand in `scripts/third-party-notices.tmpl` after reading the file directly, which is the one place go-licenses could not do the job itself.

## Signal and Facebook Messenger: evaluated, parked

Signal was considered alongside Telegram and WhatsApp. Every Signal client builds on either `libsignal` itself (AGPL-3.0) or `signal-cli` (a separate Java process); the only route that stays a single Go process, `mautrix-signal`'s `signalmeow`, does so by wrapping `libsignal`'s own Rust library through cgo, which makes the helper AGPL-3.0 (a stronger copyleft than the GPL-3.0 WhatsApp already brings) and adds cgo and a Rust toolchain to the build and CI. Parked until there is real demand for it; write-up: https://pasteai.io/d/899b078e-31f4-411a-b326-33dc7f626f8c.

Facebook Messenger and Instagram have no personal-account API; the only library for them, `mautrix-meta`'s `messagix` (pure Go, no cgo), is AGPL-3.0, sign-in means pasting cookies out of a logged-in browser session rather than any sanctioned flow, Meta is known to flag clients that do this, and pin, archive and mute are unsupported. Declined; write-up: https://pasteai.io/d/3f42e370-cc0d-4489-a44f-1f541f69d2b9.

## WhatsApp's self-chat always canonicalizes to its phone JID, never its LID

A real account showed two "Message yourself" conversations: one keyed by the account's own phone JID with its real history, and a stray second one keyed by the account's own LID, empty of messages but wrongly retitled with a resolved contact name. Every place this connector turned a JID into a stored or reported remote id (`remoteID`) treated the phone JID and LID forms of the same self-chat as two different conversations, because nothing compared a JID against both before deciding its id. A bot that replies into the self-chat as another linked device (this account's own, same as any multi-device echo) can address either form depending on which of WhatsApp's internal paths delivered it, so the split was real, not synthetic.

`chatID(ctx, dev, jid)` is the fix: it calls `dev.isSelfChat` first, and when true, returns `dev.selfChatID()` (always the phone JID's remote id, since `Store.GetJID()` is reliably set once paired, unlike `Store.GetLID()`) instead of `remoteID(jid)`. Every call site that used to compute a conversation's remote id from a bare JID — `ensureChat`, the live reaction, revoke, edit, typing, receipt, pin and archive handlers, `receipt`'s outgoing-progress matching, and history sync's `syncConversation` — now goes through `chatID` instead. Message keys and media references, which are keyed by conversation remote id plus message id, automatically follow since they are saved under whatever remote id the caller already computed.

`isSelfChat` itself grew a fallback for the same reason `selfChatID` has to exist: `Store.GetLID()` is this device's own cached copy of its LID, which can still be empty for a while after pairing even once the account's LID is long since assigned; this is almost certainly what produced the stray conversation on first pairing, since `ensureChat`/`resolveConversation`'s self-chat check falls through to ordinary contact resolution when it answers false, which is also is why the stray conversation's title came from a resolved contact. `isSelfChat` now also tries whatsmeow's separate, independently-synced LID mapping store (`Store.LIDs.GetPNForLID`), the same local read `contactName` already relies on, before giving up — recognising the account's own LID a run earlier than relying on `Store.GetLID()` alone would.

Existing accounts that already have the stray LID-keyed conversation keep it: there is no store-level merge or migration in this change, since one would need UI and RPC surface of its own and risks merging two conversations incorrectly if guessed wrong. Going forward the stray conversation receives nothing further from this connector (every report now resolves to the phone JID's id instead), and the user can hide it by hand with the existing `conversations.setHidden` command; it is expected to stop mattering once the account is re-paired, or simply be visibly stale as a hidden leftover with its zero messages and its one wrong title, not the account's own leftover messages.

## `events.Receipt` always runs both lanes, and the connector finally listens for `events.UndecryptableMessage`

Two bugs compounded to make an account's own other-device messages (in particular a bot replying into the self-chat) look dropped. First, `live.go`'s `handleReceipt` — meant to mark a whole conversation read when this account reads it from another of its own devices — was written and tested but never wired into `handleEvents`'s switch on `*events.Receipt`; only `receipts.go`'s `receipt` (lane B: delivery and read progress for a message this account sent) ran. Both are safe to run unconditionally on every receipt, since each checks the one field (`IsFromMe`, or rank-zero for a kind it does not track) that is the other lane's job, so `handleEvents` now calls both for every `*events.Receipt`.

Second, and the more likely cause of messages actually vanishing: whatsmeow reports a message it could not decrypt as `events.UndecryptableMessage`, a case this connector's event switch had no branch for at all, so it fell into the same `default` as a genuinely unhandled event and nothing was ever stored or shown — not even a count. whatsmeow's own doc comment on the type says it already asks the sender to retry, and reports an ordinary `events.Message` with the same id if that succeeds. `handleUndecryptable` now reports a placeholder ("Waiting for this message", matching WhatsApp's own wording style) through the ordinary chat-ensuring and sink-reporting path `handleContent` uses, and records the conversation/message id pair in a new `Connector.undecryptable` set. `handleContent` checks that set first: if the incoming id matches a pending placeholder, it reports the real message through `Sink.Edited` instead of `Sink.Incoming`/`Sink.History`, replacing the placeholder in place rather than storing a duplicate. If whatsmeow's retry never succeeds, the placeholder simply stays, which was judged better than hiding the fact that something arrived at all.

## Diagnostics go straight to the stdlib `log` package, not an injected logger

The brief asked for privacy-safe stderr counters for dropped messages, undecryptable messages and unknown content kinds, "at a debug level the helper already supports" — but no such level exists: `main.go` builds one plain `*log.Logger` for `server.New` and nothing else in the helper takes a logger at all, and `connector.Provider.Connect(account, dir)` has no way to carry one to a connector without changing that interface for every provider, including Telegram, for a WhatsApp-only diagnostic. `backend/internal/connector/whatsapp/diagnostics.go` calls the standard library's package-level `log.Printf` directly instead: it already writes to stderr by default, protocol.md already treats stderr as the diagnostics channel regardless of mechanism, and every line it writes carries only a reason string, a count or a proto field name, never a JID, a name or message text, which `tools/nologcontent` still checks mechanically. If a real leveled-logger seam is built for the helper later, these calls move onto it then; a one-off logger parameter threaded through just this package was judged not worth the inconsistency with every other connector having none.

## A history-synced conversation needs at least one real message before it is created

Several conversations in a real account's list showed "Unknown contact" with a "[Message]" preview and never anything else: WhatsApp's history sync lists a conversation entry for chats this connector should never have shown — a LID shadow of a chat already known by its phone JID, or a chat whose only synced messages were reactions, edits, revokes or other housekeeping content (see `isContentless`) with nothing a person actually said. `syncConversation` used to call `reportConversation` unconditionally for every synced entry, regardless of what, if anything, its `Messages` carried.

`hasRealContent` reports whether at least one synced message is real content by the same filter `historyMessage` itself applies (not a reaction, revoke, edit or contentless kind), and `syncConversation` now skips reporting entirely when neither that is true nor `knownChat` says this connector has already reported the same remote id for real earlier in this run. The `knownChat` half matters because a later, smaller history sync (a "recent" or app-state-only resync) carries a conversation's updated pinned, archived or unread state with no messages of its own in that batch at all; without it, a real, already-shown conversation's organizing updates would stop landing the moment its synced `Messages` happened to be empty. A dropped sync entry logs `reasonNoRealContent` through the same diagnostics as everything else dropped on purpose.

## Group history messages fall back to this connector's own cached name, and a group's member count is always resolved

Two further symptoms of the same gap: a group's message bubbles kept showing the generic "WhatsApp user" after a fresh pairing even though the conversation list's own preview had the sender's real name, and a group titled straight from history sync's own `DisplayName` showed "0 members" forever. Both come from `resolveGroupName` and `message`/`historyMessage` only ever using what the *current* report carries, never what this connector already resolved from somewhere else.

`resolveGroupName` used to return as soon as it had a name from any source, which also returned whatever member count happened to be cached or synced (often 0, since a synced `DisplayName` with no participant list carries none) without ever asking WhatsApp for the real one; it now resolves name and member count independently, through the new `cachedGroupMembers` helper, and asks `dev.groupInfo` whenever either is still unknown, so a named-but-memberless group still gets a real count, while a group with both already known still never makes the call.

Naming a sender was similarly too narrow: `senderDisplayName` tries a resolved contact, then the message's own push name, but a synced group message's `WebMessageInfo` rarely carries that specific sender's push name the way a live `events.Message` does, even though the account-wide push name list from the same sync (`syncPushnames`, which runs first and populates `Connector.names`) already named that same person. `Connector.improvedSenderName` now checks that cache as a last resort, replacing the message's sender name only when it is exactly `genericSenderName` ("WhatsApp user"), so a message that already resolved a real name is left alone; it is applied after `message`, `edit` and `historyMessage` return, in `handleContent`, `handleEdit`, `handleUndecryptable` and `syncMessage`, rather than threading `Connector`'s own cache into those otherwise-pure normalizers.

## A few more WhatsApp content kinds get their own placeholder or are dropped as housekeeping, found by reading whatsmeow's proto schema

Auditing every field of `waE2E.Message` against what `isContentless`, `messageText` and `sharedContentPlaceholder` already recognised (see the new `unknownContentKind` diagnostic, which reports exactly this gap from a live account without guessing) turned up two kinds of gap. A shared group invite (`GroupInviteMessage`) and a shared sticker pack (`StickerPackMessage`) are real content a person sent, so they get their own placeholders, `"[Group invite]"` and `"[Sticker pack]"`, the same way a shared contact or location already does. WhatsApp has also shipped three more poll-creation versions since V3: V5 and V6 carry a `PollCreationMessage` field directly, like every earlier version, and are just added to `pollCreation`'s switch; V4 is different, wrapping its content in the same forward-compatible `FutureProofMessage` envelope as an ephemeral or view-once message rather than carrying the poll fields itself, so `unwrap` peels it the same way, and whatever poll version turns out to be nested inside falls through to the existing `pollCreation` switch unchanged.

The other gap was kinds that are not content at all but were falling through to the generic `"[Message]"` placeholder instead of being dropped: a call or its log entry (`Call`, `CallLogMesssage`, `BcallMessage`), a history-sync bundle or notice (`MessageHistoryBundle`, `MessageHistoryNotice`), and session or key housekeeping payloads (`PlaceholderMessage`, `SecretEncryptedMessage`, `GroupRootKeyShare`, `RootSecretDistributeMessage`). These are added to `isContentless` alongside the existing poll-vote, pin-in-chat and keep-in-chat cases, so none of them is ever stored or shown. Many further fields on `waE2E.Message` — WhatsApp Business templates, lists, buttons, payments, newsletters, statuses — are left exactly as they were, falling through to the generic placeholder: they were judged too speculative to commit a specific rendering to without a live account actually hitting them, which the new diagnostic line now makes possible to confirm cheaply if they turn out to matter.

## A history sync must not revert a pin or archive this process just set

A real account showed only its first pin ever actually persisted: pinning a second or third conversation moved it to the top of the list (the optimistic local store write `app.Commands.SetPinned` always makes) but the pin mark itself did not stick. The cause is `syncConversation`'s organize report: it always sent WhatsApp's own synced snapshot of a conversation's pinned and archived flags through `Sink.Organized`, which overwrites the store unconditionally (see `store.SetOrganized`). WhatsApp's app-state patches are eventually consistent — `dev.sendAppState` succeeding means the patch was accepted for delivery, not that every subsequent sync already reflects it — so a "recent" history resync arriving moments after `organize.go`'s `SetPinned` sent its patch can still carry the pre-patch, unpinned snapshot, and promptly revert the very pin the user just made.

`Connector.localOrganize` is a set of remote ids whose pinned or archived state was set locally more recently than any live confirmation. `SetPinned` and `SetArchived` add a remote id to it right after reporting their own change; `syncConversation`'s new `reportSyncedOrganize` skips its `Sink.Organized` call entirely for any remote id in that set, leaving the local value exactly as `SetPinned`/`SetArchived` left it, rather than letting a stale sync clobber it. The set is cleared by `handlePin` and `handleArchive`, the live echoes WhatsApp sends when a pin or archive change actually reaches its servers (including a change made from the phone instead): those are real-time updates, not a snapshot that might predate a pending patch, so they are trusted unconditionally and hand the remote id back to being freely updated by the next sync. The set, like this connector's other in-memory caches, is not persisted and starts empty again after the helper restarts, which only matters for the brief window between a local pin and its own confirming echo, the same self-correcting trade-off the pin, archive and reaction caches already make (see "WhatsApp's chat organizing and naming caches live in memory for the process's lifetime" above).

## Voice notes: an inline player behind a Loader, played by a controller that outlives the delegate

A voice note (WhatsApp's push-to-talk audio, Telegram's voice message) is its own `domain.Media` kind, `"voice"`, rather than staying `"file"`: both connectors already distinguished it internally (WhatsApp's `AudioMessage.PTT`, Telegram's `DocumentAttributeAudio.Voice`) only to label it, so giving the UI the same distinction costs one more constant and lets it draw a player instead of a generic file row. `domain.Media.Duration` already existed and both connectors already filled it in for a voice note; nothing new was needed there.

In-window playback needs Qt 6's QtMultimedia module (`MediaPlayer`/`AudioOutput`, with its ffmpeg backend decoding Opus/OGG), which is not a published dependency of this plugin: it happens to be installed on some Omarchy machines only because another app pulled it in. A QML file that imports a missing module fails to load outright, so nothing in this feature's main path may import it. The one file that does, `ui/components/VoiceNoteRuntime.qml`, holds nothing but a `MediaPlayer` and the handful of properties/functions callers need (`source`, `playing`, `rate`, `positionMs`, `durationMs`, `ended()`); `ui/controllers/VoiceNoteController.qml` loads it through a `Loader` and reads `Loader.status === Loader.Error` as "QtMultimedia is not here," exposed as `available`. Every playback method is a no-op when `available` is false, and the bubble's own component falls back to the same plain "open externally" row `FileView` already uses for an ordinary file, labelled "Voice message · open" rather than naming a missing dependency the user cannot act on.

The controller, not the message bubble, owns the one `MediaPlayer` and all playback state (`playingId`, `playing`, `positionMs`, `durationMs`), for the same reason `PhotoViewerController` is a controller rather than part of `PhotoView`: a `ListView` delegate is recycled or destroyed as the list scrolls, so a `MediaPlayer` living inside one would stop decoding the moment its row scrolled out of view. `ui/components/VoiceNotePlayer.qml` only ever reads this state through plain properties (`available`, `playing`, `positionMs`, `durationMs`) and reports intent with the same `wanted()`/`opened()` signals `PhotoView`/`FileView` already use; `MessageBubbleContent` and `MessageDelegate` thread a single plain summary object (`voiceNotes: {available, playingId, positionMs, durationMs}`) down from `ConversationController`, never the controller itself, so a view never calls into a controller, only reads data, matching the rest of `ui/components`.

Reusing `mediaWanted`/`mediaOpen` rather than inventing voice-specific signals keeps every file between the bubble and the controller unchanged apart from one added property: `ConversationController.openMedia` already branches on a message's media kind for photos; it gained one more branch that, when a `VoiceNoteController` is available, downloads the note if needed (voice notes are small, so this happens the moment it is seen, like a photo's thumbnail-to-full-image fetch) and calls `toggle(id, path, durationHintMs)`, which starts a different note (pausing whichever was playing), or pauses/resumes the same one, never playing two at once. Enter on a highlighted voice note reaches this through the same `message.open` action a photo or file already uses; `Highlight.hints` only changes its label from "Enter open" to "Enter play" when the highlighted message's media kind is `"voice"`.

Playback is not paused when the conversation closes or another one opens, and does not stop if the playing message's delegate scrolls out of view: both are deliberately left as "still playing," the same as a music player would, rather than adding more state transitions for behaviour nobody asked for. A scrubber drag and a 1x/1.5x/2x speed control were both left out: dragging needs a new signal threaded through every file between the bubble and the controller for an interaction a click-to-open already covers reasonably (seeing the bar fill is enough without being able to grab it), and a speed control needs the same threading for a feature the brief only asked for if cheap.

## A voice note's media is written once, so a message stored before the "voice" kind existed stays `"file"` forever, and the UI, not the helper, now covers for that

A real voice note showed as "Unavailable" after the player shipped: its audio file had actually reached `PhotoView`, which tried to decode it as a photo. `backend/internal/store/messages.go` encodes a message's `domain.Media` to JSON once, at insert, and never re-normalizes a stored row; a WhatsApp voice note received before the "voice" media kind existed was normalized as `domain.MediaFile` with `FileName: "voice-message.ogg"` (see `audioMedia`'s history before the commit that added `domain.MediaVoice`), and that JSON blob is what the row still carries, permanently, on any machine that received it before upgrading. The helper has no mechanism to re-normalize old rows, and `domain.Media` carries no mime type at all for the UI to fall back on instead.

`ui/lib/Media.js`'s `kindFor` covers for this on the UI side: a media item's `kind` is trusted as-is for `"photo"`, `"video"`, `"link"` and `"voice"`, but `"file"` is only taken at face value when the file name's extension is not one the in-window voice player can decode; a recognised audio extension (`.ogg`, `.oga`, `.opus`, `.mp3`, `.m4a`, `.wav`, `.aac`, `.amr`, `.weba`, `.flac`) routes to the voice player instead. This is a deliberate widening beyond just the legacy voice note shape: an ordinary audio file sent as a plain document plays exactly as well through the same player, so there is no reason to make the user leave the app for one. `MessageBubbleContent` and `ConversationController.openMedia` both call `kindFor` rather than reading `media.kind` directly, so the bubble's view choice and clicking it to play always agree.

The decode error itself had a second, independent cause worth fixing the same way: `MessageBubbleContent` bound every media view's `path` straight from the shared `message.mediaPath`, regardless of that view's own `visible`. An invisible `PhotoView` sitting beside the voice player would still pick up the same downloaded path once anything set it, and `Image` loads its `source` whether or not the item is visible — so even a correctly-tagged `"voice"` message was quietly triggering a wasted, logged decode attempt on its own audio file. Each view's `path` and `failed` are now gated on that same view's `visible`, so only the one view actually drawn for a message's media ever receives its downloaded path.


## List row glyphs are plain Unicode symbols, never an icon font's private-use codepoint

`ConversationRow`'s pin marker was an empty string, and its mute marker was a private-use-area codepoint (`U+F1F6`, from an icon font such as Font Awesome) drawn in `Theme.font.family`, the app's ordinary text font: neither renders anything, since the pin glyph was simply missing and the mute glyph's codepoint has no mapping outside the icon font it was copied from. Every other glyph in this UI (the composer's paperclip, the hover toolbar's reply arrow, the voice player's play/pause) is a plain Unicode symbol, which `Theme.font.family` draws through ordinary font fallback the same way it draws any other character; the pin and mute markers now use `"📌"` and `"🔇"` for the same reason, rather than adding an icon font as a dependency for two glyphs. A pinned row also carries a quiet "Pinned" text tag beside the glyph, so a chat sorted to the top of the list is not identifiable by the glyph alone, matching the existing "Hidden"/"Archived" tag a dimmed row already carries for the same reason.

## A placeholder that never gets a redelivery also asks the primary phone, not only the original sender

The earlier fix for `events.UndecryptableMessage` (see "`events.Receipt` always runs both lanes…" above) assumed whatsmeow's own retry-receipt request to the original sender was enough; a real account's self-chat showed this is not always true. OpenClaw, a bot replying into the self-chat as another of this account's own linked devices, left its placeholder as "Waiting for this message" forever: the diagnostic line showed `unavailable=false`, meaning whatsmeow did send the usual retry receipt, but the bot never answered it, so the redelivery that would replace the placeholder never arrived.

whatsmeow has a second path for exactly this: `Client.AutomaticMessageRerequestFromPhone`, off by default, which — once the first retry receipt goes unanswered for `RequestFromPhoneDelay` (5 seconds) — sends a peer-data request to this account's own primary phone instead, asking it to resend the message from its own copy. The phone's answer reaches this connector as an ordinary `*events.Message` with the same id, exactly like a successful sender retry, except its `UnavailableRequestID` field is set. `openDevice` (`device.go`) now sets this field to `true` on the client; nothing else about `handleContent`'s matching needed to change, since it already replaces a pending placeholder by comparing conversation and message id alone, regardless of which path produced the redelivery. `logPhoneResend` (`diagnostics.go`) logs a privacy-safe line — no JID, name or text — whenever `UnavailableRequestID` is set on a redelivery that resolves a placeholder, so a report of "the placeholder never clears" can be checked against whether the phone ever actually answered.

The reverse direction — another of this account's devices (such as the same bot) failing to decrypt a message *this* account sent, and asking for a resend — needs no code here: whatsmeow's `Client.SendMessage` already caches every outgoing message in a 256-entry in-memory ring buffer (`addRecentMessage`) and answers an incoming retry receipt from that cache automatically, through its own internal node handler, never surfaced as an event this connector would need to subscribe to. `Client.GetMessageForRetry`, the hook for when that cache has already evicted a message, defaults to returning nothing; it was left unset, since the ring buffer already covers a bot's retry window in practice, and wiring a second, persistent cache for the rare miss was not something the evidence in hand called for.

## WhatsApp albums unwrap to their individual photos; four Business kinds get their own text instead of the generic placeholder

The same diagnostic line mentioned above ("A few more WhatsApp content kinds…") turned real-account speculation into a confirmed list: `albumMessage` and `associatedChildMessage` (an album's header and its individual photos/videos), plus the Business kinds `interactiveMessage`, `buttonsMessage`, `templateMessage` and `templateButtonReplyMessage`, were all logged as unknown. An album's header (`AlbumMessage`, just an expected photo/video count) carries nothing a person actually wrote, so it joins `isContentless`'s switch and is dropped exactly like a call log or a history-sync notice; each photo or video in the album arrives as its own message wrapped in `associatedChildMessage` (a `FutureProofMessage`, the same forward-compatible envelope `ephemeralMessage`/`viewOnceMessage` already use), so `unwrap` peels it the same way those are peeled, and the inner image or video then shows, downloads and fetches media exactly like one sent on its own — no new rendering path needed, since the photos were always going to appear individually regardless of the header.

The four Business kinds are real content, so each gets its own visible text instead of falling through to `"[Message]"`: `interactiveMessage`'s body, falling back to its header's title and then its footer's text, since WhatsApp lets a business send any mix of the three and the body is the part actually meant to be read; `buttonsMessage`'s own `ContentText`; `templateMessage`'s hydrated content text, read from whichever of its two possible fields (the dedicated `HydratedTemplate`, or the older `Format` oneof's `HydratedFourRowTemplate`) WhatsApp populated; and `templateButtonReplyMessage`'s `SelectedDisplayText`, the option a person picked. None of these render a template's buttons, a carousel, or an interactive header's own image — only the text a person would actually read was judged worth the specific handling; a business message with none of these text fields set still falls through to the generic placeholder, the same as before.
